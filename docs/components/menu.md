# Menu

A list of actions and settings that opens from a button, such as the top bar's menu of kiosk mode, help and the map's display settings, moved through with the arrow keys and closed with Esc, a choice or a press outside it.

<!-- run notes -->

The design is deferred (ADR 0010, `docs/adr/0010-unattended-runs-with-design-deferred.md`): there is no read-back, code map or export, and this spec decides what the drawing would, from the contract, the foundations, the tokens and the Base UI reference. The extracted prototype component is not in any branch this run can reach, and no ROADMAP line names Menu. The [Dialog](dialog.md) spec gives the trigger and the open state their shape, the [Toolbar](toolbar.md) spec the compound components, the [SearchField](search-field.md) spec the rows of a popup, and the [Switch](switch.md) spec a checked state's props.

## Anatomy

Penpot page `Components/Menu`. Family: Popups, for the popup and the submenu's popup; Rows, for every item. Shared parts: `CheckboxIndicator`, in `Menu.CheckboxItemIndicator`, and `SelectedMark`, in `Menu.RadioItemIndicator`, as the contract's [Shared parts](README.md#shared-parts) table composes them.

Menu is nine components, `Menu`, `MenuItem`, `MenuLinkItem`, `MenuCheckboxItem`, `MenuRadioGroup`, `MenuRadioItem`, `MenuGroup`, `MenuSeparator` and `MenuSubmenu`, each exported with its props type from `Menu.tsx`, in the one `Menu` folder and the one registry entry, as the Toolbar spec's exception to the contract's "one component per folder". The contract makes a child the caller writes many times, such as a menu's item, a component of its own, and every Base UI part after `Menu.Root` reads `Menu.Root`'s context, so the items can't be built, shown or tested apart from a menu; the registry gives Menu one entry for all seventeen parts; MUI's Menu takes its items as `MenuItem` children; and a data prop, as SearchField's `items`, can't hold checkbox items, radio groups and submenus without a second, typed language for each. The `props` check reads every `*Props` `Menu.tsx` exports, and the `docs` check holds `MenuProps` alone to the first Props table, so the review holds the other eight to their tables.

`Menu` renders every part of the menu itself, `Menu.Root`, `Menu.Trigger`, `Menu.Portal`, `Menu.Positioner` and `Menu.Popup`, with the popup as its root, the element `ref`, `className`, `style` and the rest props reach, as Dialog does: `Menu.Root` renders no element, and the popup is the one element a caller would style or measure. `MenuSubmenu` does the same for a submenu, with its trigger row as its root, since that row is what sits in the parent menu. Each item component renders one Base UI part as its root.

The checkbox item's box is the `CheckboxIndicator` part and the radio item's tick the `SelectedMark` part, each in its own folder under `packages/perron/src/parts/`. The `CheckboxIndicator` part and the `tick` icon it draws are on `main`, drawn for [Checkbox](checkbox.md), and Menu composes the part unchanged. The `SelectedMark` part doesn't exist yet: Menu is the first component to need it, so its build adds it, drawing the same `tick` icon, and the submenu's `chevron-right` icon, following [Icons](../foundations/icons.md) and joining `icons.json` (CR-8).

Base UI already does: it opens the menu on a press of the trigger, or on Enter, Space, ArrowDown or ArrowUp with the trigger focused, and gives the trigger `aria-haspopup="menu"`, `aria-expanded` and `aria-controls`; it portals the positioner and the popup to `<body>`, and renders nothing there, on the server or the client, while the menu is closed, unless the portal's `keepMounted` is set; it places the popup against the trigger and flips it to the other side, or shifts it along, when there is no room; it names the popup from the trigger with `aria-labelledby`, unless the caller gives `aria-label` or `aria-labelledby`; opened from the keys it moves focus to the first item (to the last on ArrowUp), and opened by the pointer to the popup itself; it moves focus between the items with the arrow keys, wrapping at the ends while `loopFocus` is on, jumps to the first and last with Home and End, and to the next item whose text starts with the letters typed; moving the pointer over an item highlights and focuses it (`highlightItemOnHover`); a disabled item stays focusable and in the arrow-key order, with `aria-disabled`, and ignores presses; a press of an item, by the pointer, Enter or Space, runs its `onClick` and closes the menu (`closeOnClick` is `true` on `Menu.Item` and `false` on the checkbox, radio and link items); a checkbox item toggles itself and a radio item chooses itself, each keeping the menu open; a radio group keeps one value for its items; a submenu opens on ArrowRight, Enter or Space on its row, or on hover after `delay`, and closes on ArrowLeft or Esc, which closes only the submenu unless `closeParentOnEsc` is set; Esc closes the menu, as do a press outside it and Tab; while open the modal menu locks the page's scroll and blocks the pointer outside it; on close it returns focus to the trigger, unless `finalFocus` says otherwise; it reports each change of open with its reason (`trigger-press`, `trigger-hover`, `outside-press`, `escape-key`, `item-press`, `focus-out`, `list-navigation`, `close-press`, `sibling-open`, `cancel-open`, `imperative-action`, `none`) and a `cancel()` that keeps the menu as it is; Left and Right swap only under Base UI's `DirectionProvider` set to `rtl`, not from the `dir` attribute, and Perron doesn't set one up yet, as all four locales run left to right.

## Props

In MUI's layout, as MUI's Menu takes `open` and `onClose` with `MenuItem` children, and with the trigger as a prop, as Dialog takes it. Every prop a props type declares gets this description as its JSDoc; every inherited one keeps Base UI's. Slots come last.

Menu leaves out `Menu.Root`'s `modal`, `loopFocus`, `orientation`, `highlightItemOnHover`, `closeParentOnEsc`, `onItemHighlighted`, `actionsRef`, `handle`, `onOpenChangeComplete`, `triggerId` and `defaultTriggerId` (the last two set by Menu itself from the trigger, CR-5), and `MenuSubmenu` leaves out every prop of `Menu.SubmenuRoot`, its open state included. Menu leaves these out, each keeping Base UI's default (a modal, vertical menu that wraps, highlights on hover and closes one submenu at a time on Esc): no Mylder screen asks for any of them yet, each changes behaviour the contract's checklist relies on rather than the look, the Dialog spec leaves out the same kind of root props, and each can join later as a new optional prop, which the contract's [Change](README.md#change) rule allows.

Menu takes `disabled`, given to `Menu.Root`, which Base UI passes to the trigger so the menu can't open. A caller's `trigger` element is rendered through `Menu.Trigger`, whose own `disabled` decides whether it opens and sets `data-disabled`, so a `disabled` on the caller's Button alone would leave Base UI's trigger enabled; the contract names `disabled` among its booleans; and it matches Toolbar's and Switch's `disabled`.

`MenuGroup` and `MenuRadioGroup` take their heading as `label: ReactNode`, rendered in `Menu.GroupLabel`, and `MenuSubmenu` its row's words as `label: ReactNode`, leaving out `Menu.SubmenuTrigger`'s own `label`, while `MenuItem`, `MenuLinkItem`, `MenuCheckboxItem` and `MenuRadioItem` inherit Base UI's `label: string`, the text for typeahead. The Base UI part is a group's label, and SearchField and Field call a control's visible name `label`; a submenu's row has no `children` of its own, since its `children` are the submenu's items; Base UI's typeahead reads a row's rendered text when its `label` is absent, so the submenu loses nothing by leaving it out; and an item's words are its `children`, as a Button's are, so its inherited `label` only ever overrides typeahead, as Base UI's JSDoc says.

`MenuRadioGroup`'s `value` and `defaultValue`, the `value` of its `onChange` and `MenuRadioItem`'s `value` are typed `string`, where Base UI takes `any`. A menu's choices, a theme or a language, are names, a string types the `onChange` a caller writes without a cast, and the API only grows, so a wider type can join later without a break; Switch's `value` is a string too.

A row offers only `startIcon` (on `MenuItem`, `MenuLinkItem` and `MenuSubmenu`), with no `endIcon`, `color`, `description` or shortcut, and the checkbox and radio items no `startIcon`. The end of a row holds the box, the tick or the chevron; the [brand](../foundations/README.md#the-brand) keeps the interface to ink and glass, and no Mylder menu holds a destructive action that a `danger` row would mark; a start icon beside the box would put two marks on one row; and each can join later as a new optional prop.

`MenuCheckboxItem` takes Switch's state, `checked`, `defaultChecked` and `onChange(event, value, details)`, whose `value` is the new `checked`, and `MenuRadioGroup` the contract's `value`, `defaultValue` and `onChange(event, value, details)`: the contract's [State and events](README.md#state-and-events) and the [Switch](switch.md) spec, with Base UI's `onCheckedChange` and `onValueChange` adapted inside (CR-4). No item takes `name`: a menu's choices act at once and submit no form.

No label-override props: Menu owns no strings ([Owned strings](#owned-strings)).

## Tokens

One row per part, state and property. States are the contract's design states: rest is no selector; hover is `:hover` inside `@media (hover: hover)`; highlighted is `[data-highlighted]`, a row under the pointer or the keys; focus is `:focus-visible`; disabled is `[data-disabled]`; selected is `[data-checked]` on a checkbox or radio item; open is `[data-open]` on a popup and `[data-popup-open]` on a submenu's row. The trigger is the caller's element and keeps its own tokens in every state, open included: Menu styles no `[data-popup-open]` on it. The portals and positioners are never seen; the positioners carry only the stacking.

The popup and the submenu's popup take the Popups family's treatment ([Families](README.md#families)): `color.surface.overlay` with a `backdrop-filter` of `effect.glass-blur` and `effect.glass-saturate`, `shadow.panel`, a `border.width.025` edge in `color.border.subtle`, and `radius.lg` padded `space.100`, so the rows' `radius.md` nests. Both popups share one rule, `.pn-Menu, .pn-MenuSubmenu-popup`.

The popup is at least as wide as its trigger and at most as wide and as tall as the room Base UI measures, scrolling inside when taller: `min-inline-size: var(--anchor-width)`, `max-inline-size: var(--available-width)` and `max-block-size: var(--available-height)`, over Base UI's variables, with `overflow-y: auto` and `overscroll-behavior: contain`. A menu as wide as the button above it reads as that button's own, as SearchField's list does; Base UI already keeps `collisionPadding` from the viewport's edge in the room it measures, so the popup never runs off a 320 px screen; no width token fits a menu, and [Layout](../foundations/layout.md#other-layout-properties) keeps a measure only one component reads in that component's CSS; and the popup grows with its longest label until the room runs out, where the labels wrap (CR-11).

Every row, `MenuItem`, `MenuLinkItem`, `MenuCheckboxItem`, `MenuRadioItem` and `MenuSubmenu`, takes the Rows family's treatment and SearchField's row metrics, in one rule over the five classes: `space.150` above and below and `space.200` at its sides, `space.200` between its parts, `radius.md`, `typography.label` in `color.text.primary`, at least `size.target-min` tall, transparent at rest, `color.surface.hover` on hover and while highlighted, `color.surface.selected` while checked. Rows of `typography.label` at `space.150` stand about 29 px tall, above `size.target-min`, and the same metrics in SearchField's list and here make Perron's popups read as one family.

A disabled row is `color.text.tertiary` and takes no hover, highlighted or pressed fill, as the contract makes disabled a colour; it stays focusable (Base UI's `focusableWhenDisabled`), so the focus ring still shows where the keys are. A checked row that is highlighted lays `color.surface.hover` over `color.surface.selected` as a `linear-gradient` background-image, as the Fields family lays hover over a fill, so the highlight shows on a chosen row too. A submenu's row keeps the highlighted fill while its submenu is open, so the path from the menu to the submenu shows.

The focus ring is `perron.css`'s, kept on a focused row beside the highlighted fill: [Accessibility](../foundations/accessibility.md#rules) asks for the ring on every interactive element unless another mark reaches 3:1, and `color.surface.hover` doesn't. The popup's `space.100` padding leaves the ring, `focus.offset` plus `focus.width` out from the row, inside the popup's scrolling box, as the Toolbar spec's CR-7 does for its bar. The popups draw no ring of their own, `outline: none` on their `:focus-visible`: Base UI focuses the popup itself when the pointer opens it or at first render, and a ring round the whole menu marks no row the keys would act on, so the rows alone draw it.

The checkbox item's box and the radio item's tick sit at the row's end, after the label, with the label growing between them and the row's start. Every label in a menu then starts at one edge, whether the row is an action, a setting or an option, and a tick that appears and disappears shifts no words; a menu's settings read as a list of settings with their state at the end, as the submenu's chevron sits at the end; and Select and Combobox, which compose the same `SelectedMark`, can place it to suit a list of options.

The checkbox item's box is the `CheckboxIndicator` part as `main` draws it for Checkbox ([Checkbox](checkbox.md)), unchanged: a `size.checkbox` square with a `border.width.025` `color.border.control` edge and `radius.xs` on `color.surface.raised` while unticked, `color.surface.inverse` with the `tick` icon in `color.text.inverse` while ticked, and its disabled colours; Menu sets none of its tokens. The contract draws a shared part once and has every component compose it, so a menu's setting and a form's checkbox read as one control, and the part already reads its states from the attributes `Menu.CheckboxItemIndicator` sets, as `Checkbox.Indicator` does. The `SelectedMark` draws the same `tick` icon.

The group label is `typography.overline` in `color.text.secondary`, set in capitals with `text-transform: uppercase`, `space.200` at its sides as a row's text is, with `space.200` above and `space.100` below. [Typography](../foundations/typography.md) gives `overline` to section headings, which a group's label is; `color.text.secondary` is supporting text that still reaches 4.5:1; the label lines up with the rows' labels below it; and the space above parts it from the group before more than from its own rows.

`MenuSeparator` is a `border.width.025` hairline in `color.border.subtle`, drawn as a border so forced colours keep it, across the popup's padding box with `space.100` above and below: the Toolbar spec's separator, and `color.border.subtle` is the dividers' colour, a divider only decorating.

The chevron is `chevron-right` at `icon.size.400` in `color.text.secondary`, `color.text.tertiary` on a disabled row; the start icon is the caller's at `icon.size.400`, taking the row's colour; the tick is the `SelectedMark` part's `tick` at `icon.size.325`, the step its 14 px grid is drawn for ([Icons](../foundations/icons.md)), in the row's colour: the same drawing at the same size as the box's tick.

## Component rules

Rules for this component alone, numbered so the build and the review can cite them.

- **CR-1.** Base UI's menu already gives the opening, the placing, the arrow keys, Home and End, typeahead, the highlight on hover, the checkbox and radio state, the submenus, Esc, the outside press, the focus return and every role and state, so the components rebuild none of it and add no key or pointer handlers.
- **CR-2.** `Menu` renders `Menu.Root` around `Menu.Trigger` (`render={trigger}`) and `Menu.Portal`, which holds `Menu.Positioner` and then `Menu.Popup`, which holds the caller's `children`. `MenuSubmenu` renders `Menu.SubmenuRoot` around `Menu.SubmenuTrigger` (the start icon, the label and the chevron) and `Menu.Portal`, `Menu.Positioner` and `Menu.Popup`, which holds its `children`. `MenuGroup` and `MenuRadioGroup` render `Menu.GroupLabel` first, when `label` is given, then their `children`. `MenuCheckboxItem` and `MenuRadioItem` render their label span, then their indicator. The DOM order is the reading order and the order on screen.
- **CR-3.** Each of the nine takes `{...rest}` before its own attributes, and its own props out of `rest` first, so none reaches the DOM: Menu's `trigger`, `children`, `open`, `defaultOpen`, `onOpen`, `onClose`, `disabled` and `slotProps`; a row's `startIcon`, `children` and `disabled`, and a submenu's `label`; the checkbox item's `checked`, `defaultChecked`, `onChange` and `slotProps`; the radio group's `label`, `value`, `defaultValue`, `onChange`, `disabled` and `slotProps`; the radio item's `value`, `disabled` and `slotProps`; the group's `label` and `slotProps`. Inherited Base UI props, such as `finalFocus`, `closeOnClick` and `openOnHover`, stay in `rest`, keeping Base UI's defaults. `ref`, `style` and `data-testid` land on each component's root, and `className` is merged after its `pn-` class. Each `slotProps` value is merged with Base UI's `mergeProps` (`@base-ui/react/merge-props`), the component's own props last, so a caller's class sits beside the part's `pn-` class.
- **CR-4.** Menu turns Base UI's `onOpenChange(open, details)` into `onOpen(details.event, details)` when `open` is `true` and `onClose(details.event, details.reason, details)` when it is `false`; `MenuCheckboxItem` turns `onCheckedChange(checked, details)` into `onChange(details.event, checked, details)`, and `MenuRadioGroup` `onValueChange(value, details)` into `onChange(details.event, value, details)`. None exposes Base UI's `onOpenChange`, `onCheckedChange` or `onValueChange`.
- **CR-5.** Menu gives `Menu.Trigger` an id (the `trigger` element's own `id`, then `slotProps.trigger.id`, or one from React's `useId`) and passes it to `Menu.Root` as `defaultTriggerId`, or as `triggerId` when `open` is set, as the Base UI reference says for a menu open at first render or controlled, so the popup is named by the trigger and focus returns to it when such a menu closes.
- **CR-6.** `MenuItem`, `MenuLinkItem`, `MenuCheckboxItem`, `MenuRadioItem`, `MenuSeparator`, `MenuGroup`, `MenuRadioGroup` and `MenuSubmenu` only render inside a `Menu`'s popup or a `MenuSubmenu`'s, and `MenuRadioItem` only inside a `MenuRadioGroup`: Base UI's parts read their context. Every story renders them there.
- **CR-7.** The five rows share one look, written once over their five classes; the states keep a row's geometry: hover, highlighted, selected, open and disabled change colours only, never the height, padding, gap or radius. Hover is read inside `@media (hover: hover)`; the highlighted fill is on `[data-highlighted]` outside it, so the keys and a touch show it; neither applies to a disabled row, since a row focusable when disabled still matches `:hover` and takes `data-highlighted`.
- **CR-8.** The box is the `CheckboxIndicator` part, in `packages/perron/src/parts/CheckboxIndicator/` as Checkbox's build left it, and the tick the new `SelectedMark` part, in a `SelectedMark` folder of its own under `packages/perron/src/parts/`, each rendered through its Base UI part's `render`. The box is `<Menu.CheckboxItemIndicator keepMounted render={(props, state) => <CheckboxIndicator {...props} mark={state.checked ? 'tick' : undefined} />} />`, written once outside the component, as the [Checkbox](checkbox.md) spec's CR-4 renders it, the part unchanged: it reads `data-checked`, `data-unchecked` and `data-disabled` from the props Base UI passes, and its hover from the row that holds it (`[role]:hover >`, the row's `menuitemcheckbox` role), so the box is a direct child of the row. The tick is `<Menu.RadioItemIndicator render={<SelectedMark />} />`, a `<span class="pn-SelectedMark">` holding the `tick` icon inlined from its file, unchanged but for `width` and `height`, with `perron-icon`, `aria-hidden="true"` and `focusable="false"`, at `icon.size.325` in `currentColor`, as the `CheckboxIndicator` draws its mark. Only the parts' folders hold `pn-CheckboxIndicator`, `pn-SelectedMark` and the `tick` icon, which the contract's [Shared parts](README.md#shared-parts) table gives to both, and Menu's CSS sets only their place in the row (`margin-inline-start: auto` at the row's end, `flex: none`), never their colours or their size. The contract's "Composed in" cells already name `Menu.CheckboxItemIndicator` and `Menu.RadioItemIndicator`. The build adds the `chevron-right` icon to `packages/perron/icons/` and `icons.json`, drawn on the 16 px grid for `icon.size.400`, and widens the `tick` entry's use in `icons.json` to name the chosen option the `SelectedMark` marks.
- **CR-9.** The popup opens below its trigger aligned to the trigger's start edge, `space.100` away, with a submenu at the end of its row whose first item lines up with that row. Menu passes `align: 'start'` and `sideOffset` of `space.100` to `Menu.Positioner`, and `MenuSubmenu` passes `alignOffset` of minus `space.100` plus `border.width.025` to its positioner, keeping Base UI's `side` (`'bottom'`, and `'inline-end'` for a submenu) and the submenu's `sideOffset` of 0, each read once with `tokenValue('--perron-…')` and kept, with Base UI's own defaults until they can be read, and a caller's `slotProps.positioner` value winning over each. A menu reads as its trigger's when the two share an edge, where Base UI's default `'center'` sets it off from a button at the screen's edge; the gap is the Popups' own `space.100` padding and MapTooltip reads its offset the same way; a submenu pulled up by its popup's padding and edge puts its first row level with the row that opened it; and Base UI flips either side when there is no room.
- **CR-10.** The positioners take `z-index.dialog`, as everything in a portal does, so a submenu opened last paints over its menu. Menu's CSS never redefines a token: the portals sit outside every themed container but `<body>`.
- **CR-11.** A row's label grows (`flex: 1`, `min-inline-size: 0`) and its start icon, box, tick and chevron keep their size (`flex: none`). Long words wrap in a label and a group label (`overflow-wrap: anywhere`), so a long Danish word fits a 320 px screen: the popup grows with its longest label until `--available-width` runs out, and the label then wraps inside it.
- **CR-12.** The menu opens and closes at once: no `duration.*` token fits a popup's entrance, so the CSS has no transition and styles neither `data-starting-style` nor `data-ending-style`, as Dialog and SearchField.
- **CR-13.** The popups draw their `border.width.025` edge as a border, and the separator its hairline as a border, so Windows' forced colours keep an edge round each popup and between groups when they drop the glass; a highlighted row takes `Highlight` and `HighlightText` there; the box keeps the `CheckboxIndicator` part's own forced-colours rules, `Highlight` with a `HighlightText` tick while ticked and `GrayText` while disabled ([Checkbox](checkbox.md)'s CR-11); and the radio item's tick, drawn in `currentColor`, takes the row's system colour.
- **CR-14.** The portal renders nothing on the server, so the contract story's owned-strings check, which renders to static markup, sees only the trigger. Menu's own stories check the open popup's words in the live DOM instead: `expectOwnedStrings(popup.outerHTML, locale, callerWords)` in English and in Danish, which finds no word of Menu's own.
- **CR-15.** The stories' meta sets `parameters: { docs: { story: { inline: false, height: '480px' } } }`, as the contract's [Stories](README.md#stories) asks of an overlay, and each story but `Disabled` opens its menu at first render with `defaultOpen`, beside the trigger that opens it again. Each `play` finds the popup through `screen` and ends with the menu closed and focus on the trigger.

Menu's root, the popup, portals to `<body>`, and only after the portal mounts, so it is not inside the story's canvas. Menu meets the contract story's Root rule with no exception: the contract story looks the root up in the whole document, as it does for Dialog.

## Do and don't

For a caller using the component, with the reason.

| Do                                                                                                                                            | Don't                                                                                                                                        |
| --------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| Pass the button that opens the menu as `trigger`, with words that name the menu, such as "Map options", or an IconButton with an `aria-label` | Open a menu from a button placed beside it with `open` alone: the button loses `aria-haspopup` and `aria-expanded`, and the menu its name    |
| Set `slotProps.trigger.nativeButton` to `false` when `trigger` is not a `<button>`, as Base UI warns                                          | Pass a link as the trigger: a link goes somewhere, and a menu opens over the screen                                                          |
| Disable the menu with `disabled` on the Menu                                                                                                  | Disable only the trigger element: Base UI's trigger stays enabled and the menu still opens                                                   |
| Put actions in `MenuItem`s, links in `MenuLinkItem`s, settings in `MenuCheckboxItem`s and one choice in a `MenuRadioGroup` with a `label`     | Put a Button, a Switch or a plain `<a>` in the popup: it falls out of the arrow-key order and gets no menu role                              |
| Keep a checkbox item's words the same on and off, such as "Show stop names", and let its box and `aria-checked` say the state                 | Change a setting's words when it turns on, or use a checkbox item for an action                                                              |
| Name each group with `label`, in sentence case, and divide groups with `MenuSeparator`                                                        | Put a heading or a styled `<div>` in the popup as a label: it isn't tied to its group, and the arrow keys would skip a group they can't name |
| Keep a disabled item in place, so the person learns it exists, and keep menus short, a submenu one level deep at most                         | Hide and show items as the state changes, or nest submenus: rows that move and deep paths are hard to follow on a phone                      |
| Use a menu for a short list of actions and settings that open from one button                                                                 | Use a menu to choose a form's value or to search a long list: that is a Select or a SearchField, which submit and filter                     |
| Open a menu from a toolbar by passing a `ToolbarButton` as `trigger`, so it joins the toolbar's arrow-key order                               | Put a Menu's trigger beside a toolbar's buttons as a plain Button: it adds a tab stop and falls out of the toolbar's arrow keys              |
| Let the menu take `z-index.dialog`, its place against the trigger and its glass                                                               | Set a `z-index`, a position or a background on the popup: it would fall under another overlay or leave the Popups family                     |
