# Tooltip

A short visual label beside a control, such as "Zoom in" over the map's zoom button, shown while a mouse pointer rests on the control or the keyboard focuses it, for sighted mouse and keyboard users.

The design is deferred (ADR 0010, `docs/adr/0010-unattended-runs-with-design-deferred.md`): there is no read-back, code map or export, and this spec decides what the drawing would, from the contract, the foundations, the tokens and the Base UI reference. The ROADMAP names no Tooltip line of its own: Base UI's Tooltip is the part under the MapTooltip line of Wave 3, and this component is its trigger-bound sibling. The extracted prototype component is not in any branch this run can reach. It shares the Tooltips family's treatment with [MapTooltip](map-tooltip.md), which places a card against a point the caller holds, where this one sits against the control it labels.

## Anatomy

Penpot page `Components/Tooltip`. Family: Tooltips. Shared parts: none (the popup holds the caller's words and draws no mark of its own).

Tooltip is one component that takes its trigger as a `trigger` prop (a `ReactElement`, required) and its words as `children`, with the popup as its root, the way [Dialog](dialog.md) and [Sheet](sheet.md) take `trigger` and [MapTooltip](map-tooltip.md) takes `children` as the card's words, rather than MUI's `title` for the words and `children` for the trigger. In Perron `title` is already a heading (Dialog, Sheet, Section, EmptyState) and `children` is what an overlay shows, so one name keeps one meaning across the Overlays category; the trigger is required because a tooltip with nothing to label is MapTooltip's job; and the popup is the root, as in its three siblings, so `ref`, `className`, `style` and the rest props reach the element the eye sees.

Tooltip renders `Tooltip.Root`, `Tooltip.Trigger`, `Tooltip.Portal`, `Tooltip.Positioner` and `Tooltip.Popup`. It leaves out `Tooltip.Arrow`, which the entry's `baseUiParts` don't name: the Tooltips family draws no arrow, and MapTooltip, its other member, has none, so the family keeps one treatment. It leaves out `Tooltip.Viewport` too, which the entry doesn't name: one tooltip has one trigger, and its words swap with no transition for a viewport to run.

`PerronProvider` (`packages/perron/src/PerronProvider.tsx`) wraps its children in `Tooltip.Provider`, with Base UI's own delays, so that once one tooltip is open the next one the pointer reaches opens at once, while Tooltip itself renders no provider. A provider around each tooltip groups nothing, and a second exported component would need a spec and a registry entry of its own; the map's controls set three tooltips side by side, and Base UI's demos wrap such a row in one provider. `Tooltip.Provider` renders no element, so the app's markup doesn't change; the entry keeps `Tooltip.Provider` in its `baseUiParts`, since Tooltip relies on it.

| Part (Penpot layer) | What it is                                                                                                                             | Base UI part         | Class                   | `slotProps` key |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------------- | -------------------- | ----------------------- | --------------- |
| `root`              | The popup: an inverse box that holds the caller's `children`, a block that wraps its text; rendered only while open                    | `Tooltip.Popup`      | `pn-Tooltip`            | none            |
| `trigger`           | The caller's `trigger`, such as an [IconButton](icon-button.md), rendered in place of the tooltip through `Tooltip.Trigger`'s `render` | `Tooltip.Trigger`    | `pn-Tooltip-trigger`    | `trigger`       |
| `positioner`        | Not drawn: the box Base UI places against the trigger, above it by default, and that carries the stacking                              | `Tooltip.Positioner` | `pn-Tooltip-positioner` | `positioner`    |
| `portal`            | Not drawn: the `<div>` Base UI appends to `<body>` while the tooltip is open, so no panel's overflow or stacking clips it              | `Tooltip.Portal`     | `pn-Tooltip-portal`     | `portal`        |
| `provider`          | Not drawn: the shared delay group, rendered once by `PerronProvider` around the app, never by Tooltip                                  | `Tooltip.Provider`   | none                    | none            |

`Tooltip.Root` groups the parts and holds the open state; it renders no element, so it has no layer, class or `slotProps` key. The trigger keeps the caller's element and its look: Tooltip adds its class beside the element's own and no style.

Base UI already does: it opens the tooltip when a mouse pointer rests on the trigger for the open delay, 600 ms unless the trigger's or the provider's `delay` says otherwise, and never on touch, since its hover listens to the mouse only; it opens it at once when the trigger takes keyboard focus that matches `:focus-visible`, and not on a tap or a click that focuses it; inside a provider, once one tooltip is open, the next trigger the pointer reaches within the provider's 400 ms `timeout` opens its tooltip at once, marked `data-instant="delay"`; it keeps the tooltip open while the pointer travels from the trigger onto the popup and rests there, so its words can be read and selected; it closes it when the pointer leaves both, when the trigger loses focus, on Esc from anywhere in the document, on a press outside, and on a press of the trigger itself while `closeOnClick` is on, its default; it reports each change with its reason (`trigger-hover`, `trigger-focus`, `trigger-press`, `outside-press`, `escape-key`, `disabled`, `imperative-action`, `none`) and a `cancel()` that keeps it as it is; it portals the popup to `<body>` and renders nothing there while closed; it places the popup against the trigger, above it by default, flipping to the opposite side when that one has no room and shifting it along the edge so it stays inside the viewport, and re-reads the trigger when an ancestor scrolls, either one resizes or the layout shifts; it marks the positioner `data-anchor-hidden` when the trigger is scrolled out of view; it leaves the popup out of the tab order (`tabindex="-1"`) and makes the positioner `inert` while closed; and it sets the variables `--available-width` and `--available-height`, the room between the trigger and the viewport's edge. Base UI sets no role on the popup and no `aria-describedby` on the trigger: its guidelines make a tooltip a visual label only, with the trigger named on its own.

## Props

In MUI's layout. Every prop the component declares gets this description as its JSDoc; the inherited rows keep Base UI's. Slots come last.

Tooltip offers only `open`, `defaultOpen`, `onOpen` and `onClose` of `Tooltip.Root`'s props, and leaves out `disabled`, `trackCursorAxis`, `disableHoverablePopup`, `actionsRef`, `handle` and `onOpenChangeComplete` (with `triggerId` and `defaultTriggerId` set by Tooltip itself, CR-5). A tooltip that should not open is one the caller doesn't render, or one whose `slotProps.trigger.disabled` is set; a popup that can't be hovered fails [Accessibility](../foundations/accessibility.md#rules)'s rule that a hover card stays while the pointer is over it; cursor tracking, detached triggers and exit animations serve no Mylder screen yet; and each can join later as a new optional prop, which the contract's [Change](README.md#change) rule allows.

Tooltip sets two positioner defaults read in script, since Base UI takes numbers: a `sideOffset` of `space.200` and a `collisionPadding` of `size.panel-gap`, as [MapTooltip](map-tooltip.md) does, so the Tooltips family sits the same distance from what it labels and from the screen's edge. It keeps Base UI's `side` of `'top'` and `align` of `'center'`, and Base UI's open and close delays, for which no token exists; a caller changes any of them through `slotProps.positioner` or `slotProps.trigger`. Both read the two lengths through one shared helper, `positionerOffsets` (CR-6).

## Tokens

One row per part, state and property. The popup has one design state, open: it renders only while open, and takes no hover, focus, press, selection or disabled look, since it holds no control. Rest below is the open popup. The trigger is the caller's element and keeps its own tokens in every state.

The popup takes the Tooltips family's treatment, as MapTooltip does: `color.surface.inverse` with `color.text.inverse`, no shadow, no border, `radius.md`, text in `typography.label-sm`, padded `space.150` on the block axis and `space.200` on the inline axis, its width following its content up to `--available-width`, Base UI's room between the trigger and the viewport's edge. The positioner takes `z-index.dialog`, as the contract's CSS section asks of everything that renders in a portal; the screen's `z-index.tooltip` is a pattern's token, outside a component's [families](README.md#token-families). In forced colours the popup draws a `border.width.025` outline in `CanvasText`, since the inverse fill becomes `Canvas`; an outline keeps its size. While Base UI marks the positioner `data-anchor-hidden`, the popup is hidden with `visibility: hidden`: it labels a control the reader can no longer see.

Hover, highlighted, focus, pressed, disabled, selected and invalid don't apply to the popup: it is not a control. Base UI's `data-starting-style`, `data-ending-style` and `data-instant` take no look, as the popup has no transition (CR-10).

The trigger takes no look of Tooltip's own in either, keeping its own component's look: it is the caller's Button, IconButton or ToolbarButton, whose spec already gives its hover and focus; a tooltip labels it and changes nothing about it, and the Tooltips family's Hover and Selected columns are None.

## Keyboard and ARIA

From the Base UI reference for `Tooltip` and the installed `TooltipRoot`, `TooltipTrigger`, `TooltipPopup` and the focus, hover and dismiss hooks they build on. "From" says who does it.

| Key                         | Does                                                                                                                                                                         | From                                   |
| --------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------- |
| `Tab`, `Shift+Tab`          | Moving focus onto the trigger opens its tooltip at once, calling `onOpen` with `'trigger-focus'`; moving it off closes the tooltip, calling `onClose` with `'trigger-focus'` | The browser moves focus; Base UI opens |
| `Escape`                    | While the tooltip is open, from anywhere in the document: calls `onClose(event, 'escape-key', details)`, and focus stays on the trigger                                      | Base UI                                |
| `Enter`, `Space` on trigger | Run the trigger's own action, and close the tooltip with `'trigger-press'` while `closeOnClick` is on                                                                        | The browser, the trigger; Base UI      |

No other key: the popup is out of the tab order (`tabindex="-1"`) and holds no control, so Tab passes it by.

Tooltip adds no ARIA of its own, neither `role="tooltip"` on the popup nor `aria-describedby` or `aria-label` on the trigger, leaving the trigger named by its own words, as Base UI's guidelines ask. Perron's triggers already carry their names (an IconButton's required `label`, a Button's text), so a description that repeats the name would be read twice; `aria-describedby` would point at a popup that exists only while open, so the description would come and go with the hover; and the contract's first checklist line holds because the tooltip's words match the trigger's name, which the `Default` story checks. A word that says more than the name belongs in visible text or a popover, as the Do and don't table says.

| Element      | Role                                       | Accessible name from                                          | States announced                      |
| ------------ | ------------------------------------------ | ------------------------------------------------------------- | ------------------------------------- |
| `trigger`    | The caller's element's own, such as button | Its own content or `aria-label`, such as IconButton's `label` | Its own, such as disabled; none added |
| `positioner` | `presentation`, from Base UI               | none                                                          | none                                  |
| `root`       | none: a `<div>` that reads as its text     | none: its `children` are read as text                         | none                                  |

What axe won't catch, from the contract, each with how this component meets it:

- [ ] Everything the eye is told, the ear is told, for every shape each prop accepts: the tooltip's words match the trigger's accessible name, which the trigger carries whether the tooltip is open or not; the popup draws no mark.
- [ ] Every landmark and named region has an accessible name: none here; the popup is not a landmark or a region.
- [ ] Every default label can be overridden: none here; Tooltip owns no strings.
- [ ] Every shape the type accepts renders, in every variant: `children` renders a string, an element and a list alike, as the `Content` story shows.
- [ ] A hidden copy kept for animation is `aria-hidden`, and a collapsed region is `inert`: none here; the popup leaves the document when it closes, and Base UI makes the positioner `inert` while it is closed.
- [ ] Native semantics first: the trigger is the caller's native `<button>` or Base UI button, and the popup a plain `<div>` for words, with no role.
- [ ] Focus moves in reading order and returns on close: the popup never takes focus, so opening and closing it leaves focus on the trigger.
- [ ] Every target is at least `size.target-min` square: the trigger, the caller's control, such as IconButton's `size.control` square; the popup takes no press.
- [ ] Loops stop when the system asks for less motion: none here; the popup has no loop and no transition.

## Owned strings

No owned strings: every word in the popup comes from the caller, as `children`, and the trigger's name from the trigger.

## Component rules

Rules for this component alone, numbered so the build and the review can cite them.

- **CR-1.** Tooltip renders `Tooltip.Root`, then `Tooltip.Trigger` and `Tooltip.Portal`, `Tooltip.Positioner` and `Tooltip.Popup`, and no `Tooltip.Provider`, `Tooltip.Arrow` or `Tooltip.Viewport`; the entry's `baseUiParts` name neither `Tooltip.Arrow` nor `Tooltip.Viewport`. `PerronProvider` renders one `Tooltip.Provider` with no props around its children, inside its locale context, so every tooltip under it shares Base UI's delay group.
- **CR-2.** Base UI already opens the tooltip on a resting mouse pointer and on `:focus-visible` focus, never on touch, keeps it open while the pointer is over the popup, closes it on leave, blur, Esc, a press outside and a press of the trigger, places, flips and shifts it inside the viewport, and marks the hidden trigger, so the component rebuilds none of it and adds no pointer or key handlers of its own.
- **CR-3.** The popup is the root: `{...rest}` comes before its own attributes, `ref` reaches it, and `className` is merged after `pn-Tooltip`. `children`, `trigger`, `open`, `defaultOpen`, `onOpen`, `onClose` and `slotProps` are taken out of `rest` first, so none reaches the `<div>`.
- **CR-4.** `onOpenChange(open, details)` is adapted once, inside the component: `onOpen(details.event, details)` when `open` is `true` and `onClose(details.event, details.reason, details)` when it is `false`. Tooltip exposes no `onOpenChange`.
- **CR-5.** Tooltip gives `Tooltip.Trigger` an id, the `trigger` element's own `id`, then `slotProps.trigger.id`, or one from React's `useId`, and passes it to `Tooltip.Root` as `defaultTriggerId`, or as `triggerId` when `open` is set, as the Base UI reference says for a tooltip open at first render or controlled, so such a tooltip sits against its trigger. The trigger renders through `Tooltip.Trigger`'s `render`, with `pn-Tooltip-trigger` beside the element's own class.
- **CR-6.** `slotProps.trigger`, `slotProps.portal` and `slotProps.positioner` are spread through `mergeProps` (`@base-ui/react/merge-props`), the component's own props last; each part's class is set after the merge by `withClass`, the part's class first, then the caller's `className`, a string or a function of the part's state. The positioner's `sideOffset` and `collisionPadding` are defaults: the component passes `space.200` and `size.panel-gap` only when `slotProps.positioner` gives none, reading their pixel lengths in script from `--perron-space-200` and `--perron-size-panel-gap` with `tokenValue`, never a literal, and with no document or before a token stylesheet gives both in pixels it passes neither, so Base UI's defaults apply. The reading is the shared helper `positionerOffsets`, in `packages/perron/src/internal/tokens.ts` beside `tokenValue` and in the contract's Shared helpers table, once MapTooltip's own; MapTooltip and Tooltip both import it, and neither declares it again.
- **CR-7.** The positioner takes `z-index.dialog`, and hides the popup with `visibility: hidden` while it carries `[data-anchor-hidden]`.
- **CR-8.** The popup's look is the Tooltips family's and MapTooltip's, and nothing more: `color.surface.inverse`, `color.text.inverse`, `radius.md`, `typography.label-sm` with its tracking twin, no shadow and no border, padded `space.150` on the block axis and `space.200` on the inline axis. Its text wraps (`overflow-wrap: break-word`, for a box that sizes to its content) inside `max-inline-size: var(--available-width)`, with `box-sizing: border-box` so the padding stays inside that cap.
- **CR-9.** The popup is a block: `children` flow as the caller writes them, and the component sets no flex or grid on them. Content takes the popup's colour through `currentColor`.
- **CR-10.** Opening and closing are immediate: no `duration.*` token fits a tooltip, so the CSS has no transition or animation, and `data-starting-style`, `data-ending-style` and `data-instant` take no look, as in MapTooltip.
- **CR-11.** In forced colours the popup draws a `border.width.025` solid `CanvasText` outline, inside `@media (forced-colors: active)`, so its geometry doesn't change.
- **CR-12.** The component adds no role or `aria-hidden` to the popup, and no `aria-describedby` or `aria-label` to the trigger, and gives the trigger no style of its own in any state, `[data-popup-open]` and `[data-trigger-disabled]` included.

## Stories

The deferred drawing has no variant property and no `State`: the popup has one look and one design state, open, so its one variant is `Default` (`penpot/README.md`, "Conventions"). The other stories are behaviour, which the `play` tests check.

The meta sets `parameters: { docs: { story: { inline: false, height: '480px' } } }`, since the popup portals to `<body>`, and each story renders in its own frame, with its trigger away from the frame's edges except in `NearTopEdge`. A trigger in a story is an [IconButton](icon-button.md) with the `plus`, `minus` or `locate` icon from `packages/perron/icons/`, its `label` the tooltip's words. Each `play` finds the popup through `screen`, outside `canvasElement`, and ends with it closed and focus back where it started.

| `NearTopEdge`     | The tooltip open (`defaultOpen`) on a trigger at the top of the frame, where there is no room above it                                                            | The positioner flips to `data-side="bottom"`, and the popup's top edge sits below the trigger's bottom                                                                                                                                                                                                                                                                                                          |
| `DisabledTrigger` | The tooltip on a disabled IconButton labelled "Zoom in", with `focusableWhenDisabled`, closed at first                                                            | Tab focuses the disabled trigger and its tooltip opens; Esc closes it; the trigger keeps `data-disabled` and its own look                                                                                                                                                                                                                                                                                       |

## Do and don't

For a caller using the component, with the reason.

| Do                                                                                                                                         | Don't                                                                                                                                      |
| ------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------ |
| Give an icon-only control a tooltip with the same words as its accessible name: an IconButton labelled "Zoom in" and the tooltip "Zoom in" | Write tooltip words that differ from the trigger's name: a screen reader hears only the name                                               |
| Keep the words to a short label, in sentence case                                                                                          | Put a sentence the reader needs in a tooltip: touch and screen reader users never see it, so put it in visible text or a popover           |
| Pass a control that takes a ref and spreads its props as `trigger`, such as a Button, an IconButton or a ToolbarButton                     | Pass a component that drops the props it is given: Base UI's hover and focus handlers never reach the element, and the tooltip never opens |
| Keep a disabled trigger focusable with `focusableWhenDisabled`, so its tooltip still opens from the keys                                   | Put the tooltip on a natively `disabled` button: it leaves the tab order, so the keyboard can't reach the tooltip                          |
| Put a button in a toolbar in a tooltip with `trigger={<ToolbarButton … />}`, the way round [Toolbar](toolbar.md) gives                     | Pass the tooltip's trigger to the button's `render`, as for popups                                                                         |
| Keep the app inside one `PerronProvider`, so a row of tooltips opens at once after the first                                               | Add a provider per tooltip: each waits the full delay again                                                                                |
| Use [MapTooltip](map-tooltip.md) for a card against a point on the map                                                                     | Wrap the map canvas in a Tooltip: it has one trigger, the whole canvas, not the vehicle under the pointer                                  |
| Put only words in the tooltip                                                                                                              | Put a link, a button or a field in it: the popup is out of the tab order, so the keys can't reach them                                     |
| Change the side through `slotProps.positioner`, such as `side: 'bottom'`                                                                   | Move the popup with a margin or a `transform`: Base UI's placement and flipping no longer match what is drawn                              |
