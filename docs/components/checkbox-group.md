# CheckboxGroup

A named set of checkboxes that answer one question together, such as which modes the map shows, holding the ticked values as one list, with a line of help and an error message tied to the set, submitted with a form under one name, and, where the set needs one, a parent checkbox that ticks or unticks them all.

<!-- run notes -->

The design is deferred (ADR 0010, `docs/adr/0010-unattended-runs-with-design-deferred.md`): there is no read-back, code map or export, and this spec decides what the drawing would, from the [contract](README.md), the [foundations](../foundations/README.md), [content design](../content-design.md), the tokens, the Base UI reference for `CheckboxGroup`, `Field` and `Fieldset` (`@base-ui/react` 1.9.0, installed) and the specs of the entries in its `dependsOn`, [Checkbox](checkbox.md) and [Fieldset](fieldset.md), and RadioGroup's spec on its own branch, for the group's prop names. No ROADMAP line names CheckboxGroup, and the extracted prototype component is not in any branch this run can reach, so nothing here rests on it.

Fieldset's spec already says how a group builds on it: CheckboxGroup renders Fieldset with Base UI's `CheckboxGroup` through `render`, so the group takes Fieldset's legend, its name and its disabled state (Fieldset's CR-5), and takes its description and error through Base UI's `Field`, as Base UI's forms guide puts `<Fieldset.Root render={<CheckboxGroup />}>` inside a `Field.Root`.

## Anatomy

Penpot page `Components/CheckboxGroup`. Family: none, as Fieldset's: the group draws no box, fill or border, and its checkboxes keep their own look. Shared parts: `VisuallyHidden`, through Fieldset, for a hidden legend.

The drawing has a `root` board, a vertical flex column holding, in reading order, a `legend` text layer, a `description` text layer, the caller's checkboxes, each an instance of [Checkbox](checkbox.md) in a layer named `checkbox`, a parent checkbox first among them where the group has one, and an `error` text layer. Its one variant property is `State`, with the values `default`, `disabled` and `invalid`, so its variants are `Default`, `Disabled` and `Invalid`. There is no `variant`, `color` or `size` property, as Checkbox and Fieldset have none.

The root is one element that is Base UI's `Field.Root`, Perron's Fieldset and Base UI's `CheckboxGroup` at once: `Field.Root` renders through `render` as the Fieldset, and the Fieldset renders through `render` as Base UI's `CheckboxGroup`, a `<div role="group">` (CR-2). The legend is Fieldset's own part, the description and the error are `Field.Description` and `Field.Error` inside the group, and the checkboxes are the caller's `children`, straight inside the root with no wrapper, as Fieldset's CR-2 asks.

The root is one element, the `role="group"` `<div>` that `Field.Root`, the Fieldset and Base UI's `CheckboxGroup` all render as, with the description and the error inside it. One element takes the `ref`, the `className`, the `data-testid` and the caller's `aria-*` and `id`, so they land on the group itself, which the contract story and a caller's `aria-describedby` need; Base UI's `Field.Root` gives its context to whatever it renders, and every Base UI part renders its `render` element inside its own provider, so the group and its checkboxes still read the field's name, validity and disabled state; and the forms guide's outer `<div>` round the `<fieldset>` would put the caller's props on an element with no role, while the group inside it went without them.

Base UI already does: the group keeps the list of ticked values, controlled by `value` or seeded by `defaultValue` (default `[]`), and each `Checkbox.Root` inside it with a `value` is ticked while that value is in the list, whatever its own `checked` says; a click or Space on a checkbox adds its `value` to the list or takes it out and calls the group's `onValueChange(value, details)` with `details.reason` `'none'` before it commits, so `details.cancel()` keeps the list as it was; the group's `disabled`, a `Field.Root`'s `disabled` and a `Fieldset` round it disable every checkbox inside, which then take `aria-disabled`, `tabIndex` −1 and `data-disabled`; `Field.Root`'s `name` becomes each checkbox's hidden input's `name`, so a native `<form>` and `FormData` get one entry per ticked box, its `value`, under that name, and a disabled box submits nothing; inside a Base UI `Form`, the group registers its list as the field's value; the field runs `validate` on the list when `validationMode` says (on submit by default, then on every change after a submit), marks the group and each checkbox invalid, sets `aria-invalid` on each checkbox, and shows the first failing message in the error part; it ties the description and the mounted error to the group and to each checkbox through `aria-describedby`; Fieldset names the group by its legend through `aria-labelledby`; and Base UI's `CheckboxGroup` keeps a checkbox inside it from claiming the field's control id, so no two share one. With `allValues` given, a `Checkbox.Root` with `parent` inside the group is ticked while the list holds as many values as `allValues`, indeterminate, with `aria-checked="mixed"` and `data-indeterminate`, while it holds some, and unticked while it holds none; it sets `aria-controls` to the ids of the group's other checkboxes whose values `allValues` lists, and `data-parent` on itself, and leaves its hidden input without a `name`, so a form never submits it; a click or Space on it ticks every enabled box, or unticks them all once all are ticked, a disabled box keeping its state; and when the set the person last left by ticking boxes is some but not all, it ticks all, then unticks all, then gives that set back, round again; each change calls the group's `onValueChange` with the new list, and `details.cancel()` keeps the list and the parent's place in that cycle as they were.

## Props

In MUI's layout. Every prop CheckboxGroup declares gets this description as its JSDoc; every one it inherits from Base UI keeps Base UI's, which the inherited rows give. Slots come last.

The group's state takes the contract's names: `value` and `defaultValue`, inherited from Base UI's `CheckboxGroup` as they are, and `onChange(event, value, details)`, adapted from its `onValueChange`, its `value` the new list of ticked values and `event` being `details.event`. Its name is `label`, with `hiddenLabel`, passed to Fieldset as its `legend` and `hiddenLegend`; its help and its error take Field's, `description` and `error`, with Field's behaviour (CR-4); its form name is `name`, as the contract asks of every composite control; and it inherits Field's validation props from `Field.Root.Props` as Field does, so a form library's controller and a `validate` reach Base UI with no prop of its own.

CheckboxGroup takes `description` and `error`, with Field's names and behaviour, and inherits Field's `invalid`, `validate`, `validationMode`, `validationDebounceTime`, `dirty`, `touched` and `actionsRef` from `Field.Root.Props`. Fieldset's spec left a group's description and error to CheckboxGroup and RadioGroup, through Base UI's `Field`; a set of checkboxes in a form is the common place for "Choose at least one mode", which only a `validate` on the list or a caller's `error` can say, and [Accessibility](../foundations/accessibility.md#rules) wants that said in words, never by the boxes' red edge alone; the contract's `name` on a group needs `Field.Root` anyway, since Base UI's `CheckboxGroup` has no `name` and gives its checkboxes the field's, so the group renders its own `Field.Root` and a caller can't wrap one round it, as a caller of RadioGroup, whose Base UI root takes `name` itself, can; and the same names as Field's keep one form vocabulary across the library.

The group's name is the `label` prop, with `hiddenLabel` to hear it without seeing it, as RadioGroup's and SearchField's are, passed to Fieldset as its `legend` and `hiddenLegend`. A checkbox group and a radio group are the two sets of choices that answer one question, and the `api-consistency` skill holds a new member to its siblings' names, so a caller who swaps one for the other changes only the component; a group with one value list is named as a field is, and a caller reads `label` on every named form control in the library; and the legend stays the part's name, its `slotProps` key and its class, where the markup shows it.

CheckboxGroup takes Base UI's `allValues`, the value of every checkbox in the set, and [Checkbox](checkbox.md) takes Base UI's `parent`, so a parent checkbox inside the group ticks or unticks the whole set and shows the indeterminate dash while some are ticked. Perron's Checkbox left `parent` out, saying CheckboxGroup "can add then", and this is that spec; a "Select all" over a list of modes or lines is the common case a group of checkboxes meets, and Base UI already keeps the parent's state, its `aria-controls` and the dash; Checkbox's indeterminate look is already drawn, so the parent needs no new state; and adding `parent` to Checkbox is additive, so no caller breaks. `allValues` is inherited as it is, and Checkbox's `parent` row, rule and the removal of `parent` from its omitted props are in [Checkbox](checkbox.md)'s spec (its CR-14), built with this component (CR-12).

The group lays its checkboxes out in one column only, with no `row` or orientation prop, as RadioGroup does. Checkbox labels are sentences of different lengths that wrap ([Checkbox](checkbox.md)'s CR-9), and a row of them wraps raggedly at 320 px; a row of filters applied at once is FilterChip's, pressed and seen at once; and a `row` boolean, MUI's `FormGroup` name, can join later without a break.

The group takes no `optional` mark, unlike Field. A set of checkboxes with nothing ticked is usually an answer of its own, "none of these", so the mark would sit on almost every group and say little; a group that needs at least one says so in its `description` and its `validate`; and leaving it out keeps CheckboxGroup free of owned strings, while `optional` and `optionalLabel` can join later without a break.

`CheckboxGroupProps` extends `Omit<CheckboxGroup.Props, 'onValueChange' | 'onChange' | 'disabled' | 'children' | 'className' | 'style' | 'ref'>` and `Pick<Field.Root.Props, 'invalid' | 'validate' | 'validationMode' | 'validationDebounceTime' | 'dirty' | 'touched' | 'actionsRef'>`, so `value`, `defaultValue`, `allValues`, `render` and Field's validation props are inherited with Base UI's JSDoc, and declares `label`, `hiddenLabel`, `description`, `error`, `disabled`, `name`, `onChange`, `children`, `className`, `style`, `ref` and `slotProps`. `disabled` and `name` are declared again for their JSDoc, since each reaches more than one Base UI part. `id`, the `aria-*` attributes and the `<div>`'s others reach the root through `{...rest}` and get no row. CheckboxGroup takes no `variant`, `color` or `size`, so its root carries no `data-variant`, `data-color` or `data-size`, and Base UI's state attributes are its data attributes. No name here is one the contract's [Names from other libraries](README.md#names-from-other-libraries) table bans: `onChange` stands in for `onValueChange`, and `render` for `component` and `as`.

## Tokens

One row per part, state and property. States are the contract's design states; the deferred design's `State` values map so: `default` is rest, `disabled` is `[data-disabled]` and `invalid` is `[data-invalid]`, with the error mounted. The group takes no pointer or focus, so hover, focus, pressed and selected are its checkboxes' looks, drawn by [Checkbox](checkbox.md), never the group's; highlighted and open don't apply.

The root keeps Fieldset's column, its reset of the browser's frame and its one `space.200` gap, and adds `align-items: flex-start`, so each checkbox keeps its own width. Fieldset's column stretches its children across it, and a stretched Checkbox, whose root is an inline flex row with `justify-content: center` so a label-less box sits centred in its 24 px square, would centre its box and label in the group's width; the legend, the description and the error then size to their text, up to the group's width, where they wrap.

The group keeps Fieldset's one `space.200` gap between every part, the legend, the description, each checkbox and the error, and sets no gap of its own. Each checkbox row is already `size.target-min` tall with its label centred in it, so 8 px between rows gives 32 px a row, room for a finger between targets without loosening the set; one gap on the root keeps the parts the root's own children, as Fieldset's CR-2 asks, where Field's `space.100` between its label and its help would need a negative margin or a wrapper; and Fieldset's CR-5 leaves a group's spacing to its own class, which can tighten it later with no change to the API.

The description and the error take Field's look: `typography.body-sm`, the description in `color.text.secondary` and the error in `color.text.danger`, each `color.text.tertiary` while disabled, Base UI's list of several messages with no margin and `space.400` before its items, and no `warning` icon before the error. A group's help and error read as a field's do on the same form; `typography.body-sm` is for supporting sentences; `color.text.danger` reaches 4.5:1 on every surface in both themes ([Accessibility](../foundations/accessibility.md)); and the error's words carry its meaning, the checkboxes' danger edges beside them. Field's look is written again in the group's own CSS, on its own classes, since Field's classes are Field's (CR-7).

An invalid group keeps its legend and description as they are and marks each checkbox: Base UI sets `data-invalid` and `aria-invalid` on every `Checkbox.Root` inside an invalid field, and Checkbox's `CheckboxIndicator` draws its box's edge in `color.status.danger` on `[data-invalid]`, ticked or not. A disabled group's checkboxes take Checkbox's disabled look, and its legend Fieldset's. The group keeps its rest look while Base UI marks it `data-focused`, `data-filled`, `data-dirty`, `data-touched` or `data-valid`, as Field does: none is a design state the contract names, each focused checkbox already shows its ring, and a "valid" look would claim more than a check knows.

A parent checkbox takes Checkbox's own looks, ticked, unticked or its indeterminate dash, and sits in the group's one column with the boxes it controls, at the same start edge and the same `space.200` gap, with no indent. Fieldset's CR-2 keeps every checkbox the root's own child, with no wrapper to indent, and an indent drawn on the boxes after the parent would need a sibling selector, which the contract's "Selectors: one class, then attributes" rules out; the parent's label, first in the column and naming the set, "All modes", says what it ticks, and its `aria-controls` tells the ear.

- [ ] Everything the eye is told, the ear is told, for every shape each prop accepts: the label the eye reads above the set is the group's name, and still is when hidden; the description and the error are the group's and each checkbox's description; each checkbox's tick is its `aria-checked`, and a parent's dash its `aria-checked="mixed"`, with `aria-controls` naming the boxes it ticks; the danger edges of an invalid group are its error's words and each checkbox's `aria-invalid`; the tertiary colour of a disabled group is each checkbox's `aria-disabled`.
- [ ] Every landmark and named region has an accessible name: the root is a `group`, not a landmark, and is always named by its legend, since `label` is required.
- [ ] Every default label can be overridden: none here; CheckboxGroup owns no strings.
- [ ] Every shape the type accepts renders, in every variant: `label`, `description` and `error` each render a string, an element and a list alike, at rest, disabled and invalid; `description` and `error` that render nothing leave their part out, by the `given` helper and by Base UI's `Field.Error` mounting only with a message.
- [ ] A hidden copy kept for animation is `aria-hidden`, and a collapsed region is `inert`: none here; nothing animates or collapses, and the error is unmounted, not hidden, while there is none.
- [ ] Native semantics first: Base UI's `role="group"` named through `aria-labelledby`, a `<p>` for the help, each checkbox Base UI's `role="checkbox"` with its native hidden input; rendered as a `<div>`, not a `<fieldset>`, since Base UI's group renders the element, and Base UI's context, not the browser, disables the checkboxes (Fieldset's CR-5).
- [ ] Focus moves in reading order and returns on close: the legend, the description, the checkboxes in the caller's order, a parent first, then the error, in the DOM and on screen; each checkbox, a parent among them, is one tab stop; the group never moves focus, and nothing in it closes.

- [ ] Loops stop when the system asks for less motion: none here; nothing moves.

## Owned strings

No owned strings: every word the group shows or announces comes from the caller, through `label`, `description`, `error`, the `validate` messages and each checkbox's label, a parent's among them, and each checkbox's state is heard from `aria-checked`, in the screen reader's own words.

## Component rules

Rules for this component alone, numbered so the build and the review can cite them.

- **CR-1.** Base UI's `CheckboxGroup`, `Field` and `Checkbox` already keep the list of ticked values, tick each checkbox by its `value`, adapt the click and Space, give the form one entry per ticked box, run the validation, mark the boxes invalid, tie the description and the error to the group and to each box, and disable the boxes; Fieldset names the group. CheckboxGroup rebuilds none of it and adds no key, pointer or validation handler.
- **CR-2.** CheckboxGroup renders `Field.Root` with `render` set to Perron's Fieldset, and the Fieldset with `render` set to Base UI's `CheckboxGroup`, so the three are one element, the `<div role="group">`. `Field.Root`'s children are, in order, `Field.Description` (only when `description` renders something, by the shared `given` helper from `packages/perron/src/internal/nodes.ts`), the caller's `children` as given, with no wrapper, and `Field.Error`, always rendered, since Base UI mounts it only while there is a message to show; Fieldset puts its legend before them, so the order is legend, description, checkboxes, error.
- **CR-3.** CheckboxGroup adapts Base UI's `onValueChange(value, details)` into `onChange(details.event, value, details)` inside itself, and exposes neither `onValueChange` nor the `<div>`'s native `onChange`. Its own props are taken out of `rest` first (`label`, `hiddenLabel`, `description`, `error`, `disabled`, `name`, `onChange`, `children`, `className`, `style`, `invalid`, `validate`, `validationMode`, `validationDebounceTime`, `dirty`, `touched`, `actionsRef`, `slotProps`); `{...rest}`, holding `value`, `defaultValue`, `allValues`, `render`, `id` and the `<div>`'s attributes, reaches Base UI's `CheckboxGroup` before the component's own props. `name`, `invalid`, Field's validation props, `className` (`pn-CheckboxGroup`, then the caller's), `style` and `ref` go to `Field.Root`, which hands `className`, `style` and `ref` on to the element; `disabled` goes to both `Field.Root` and the Fieldset, which hands it to the group; `label` and `hiddenLabel` go to the Fieldset as its `legend` and `hiddenLegend`. The root carries `pn-Fieldset`, then `pn-CheckboxGroup`, then the caller's class, and `ref` and `data-testid` land on the `<div role="group">`.
- **CR-4.** With `error` given, CheckboxGroup passes `invalid={invalid ?? true}` to `Field.Root`, and `match={true}` and `error` as children to `Field.Error`; with `error` left out, it passes `invalid` as given and sets neither `match` nor children, so a caller's `slotProps.error` `match` and children reach the part, and with neither Base UI shows the `validate` message. A key CheckboxGroup doesn't set is left out of its props, never set to `undefined`, so it never overrides the caller's. This is Field's CR-4, word for word in behaviour.
- **CR-5.** `slotProps.legend` goes to Fieldset's own `slotProps.legend`, with `pn-CheckboxGroup-legend` joined after the caller's class through the shared `withClass` helper, so Fieldset sets `pn-Fieldset-legend` first; `slotProps.description` and `slotProps.error` are merged with Base UI's `mergeProps` (`@base-ui/react/merge-props`), CheckboxGroup's own props last, and each part's class is set after the merge with `withClass`, `pn-CheckboxGroup-description` or `pn-CheckboxGroup-error` first, then the caller's `className`, a string or a function of the part's state.
- **CR-6.** The root sets `align-items: flex-start` on `.pn-CheckboxGroup`, and nothing else of the layout: Fieldset's CSS gives the column, the reset and the `space.200` gap, so each checkbox keeps the width of its own row, and its box and label sit on the start side, not centred across the group. CheckboxGroup sets no `gap`, `background`, `inline-size` or `overflow`, so a focused checkbox's ring, drawn `focus.offset` outside it, is never cut.
- **CR-7.** The description and the error take Field's tokens on CheckboxGroup's own classes, `.pn-CheckboxGroup-description` and `.pn-CheckboxGroup-error`, never Field's classes or Field's CSS file: `typography.body-sm`, `color.text.secondary` for the description, `color.text.danger` for the error, `margin: 0`, `overflow-wrap: anywhere`, and `color.text.tertiary` on `[data-disabled]`. Base UI's several messages, a bare `<ul>` of `<li>`s inside `Field.Error`, are styled by `.pn-CheckboxGroup-error ul`, setting only `margin` (`0`) and `padding-inline-start` (`space.400`), the named exception to the contract's "Selectors: one class, then attributes" that Field's CR-13 makes for the same list. The error appears and goes at once: no transition or animation, and neither `data-starting-style` nor `data-ending-style` is styled.
- **CR-8.** The checkboxes are the caller's Perron Checkboxes, each but a parent with a `value` unique in the group: Base UI ticks a checkbox in a group by whether its `value` is in the group's list, and a checkbox with no `value` falls back to its `name`, which inside the group is the group's, so every box would share one. The group's `value` decides which are ticked, whatever a checkbox's own `checked` or `defaultChecked` says, and a checkbox's `uncheckedValue` submits nothing inside a group. Each checkbox keeps its own label as its name, so CheckboxGroup composes no `Field.Item` and no `Field.Label`.
- **CR-9.** Disabled is Base UI's: `disabled` on the group, or a Fieldset round it, disables every checkbox through Base UI's context, and sets `data-disabled` on the root, the legend, the description and the error. The root is a `<div>`, so the browser's own disabling of a `<fieldset>`'s native controls doesn't apply, and needs not to: each checkbox is Base UI's and reads the context.
- **CR-10.** CheckboxGroup never moves focus, sets no `tabindex`, and adds no ARIA beyond Base UI's and Fieldset's.
- **CR-11.** The build adds `Field.Root`, `Field.Description` and `Field.Error` after `CheckboxGroup` in the entry's `baseUiParts` in `packages/perron/components.json`, since the group composes them, and keeps `dependsOn` as `Checkbox` and `Fieldset`: the group renders Fieldset, its stories and docs render Checkbox, and it composes Base UI's `Field`, not Perron's.
- **CR-12.** The parent checkbox is Base UI's: `allValues` passes through `{...rest}` to Base UI's `CheckboxGroup` unchanged, and a Perron Checkbox with `parent` and no `value` inside the group takes its ticked, unticked and indeterminate state, its `aria-controls`, its click on the set and its absence from the form from Base UI, so CheckboxGroup adds no handler, state or ARIA for it and its CSS sets nothing on `[data-parent]`. The build removes `parent` from the props Checkbox omits in `packages/perron/src/components/Checkbox/Checkbox.tsx`, by Checkbox's CR-2 and CR-14, so it is inherited with Base UI's JSDoc; the `SelectAll` story is the parent's, for Checkbox and for the group.

## Do and don't

For a caller using the component, with the reason.

| Do                                                                                                                                                                   | Don't                                                                                                                                                                                                     |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Use CheckboxGroup for several answers to one question that are applied when the form is sent, such as which modes a report covers                                    | Use it for filters on the map that take effect at once: those are FilterChips, pressed and seen at once                                                                                                   |
| Give every checkbox a `value` of its own, and read and set the ticked set through the group's `value` and `onChange`                                                 | Give the checkboxes `checked`, `defaultChecked` or `onChange` of their own to keep the set: the group's `value` overrides them, and a box with no `value` takes the group's name                          |
| Write the legend in sentence case as the question the set answers, "Show on the map", and each label as an answer, "Bus"                                             | Repeat the legend's words in every label ("Show bus on the map"): the screen reader reads the group's name before each box already                                                                        |
| Give `name` so the ticked values reach the form, and connect a form library through its controller                                                                   | Keep a hidden input of your own for the list: Base UI's hidden inputs already submit each ticked box                                                                                                      |
| Say what is wrong in words, through `error` or a `validate` that returns the message, such as "Choose at least one mode"                                             | Rely on the checkboxes' danger edges alone: colour is never the only sign ([Accessibility](../foundations/accessibility.md#rules))                                                                        |
| Use `description` for help about the whole set, such as what ticking means                                                                                           | Put help or an error as plain text among the checkboxes: nothing ties it to the group for the ear                                                                                                         |
| Disable the whole group with `disabled`, so every box goes together                                                                                                  | Disable each box by hand in a group that stays enabled: the legend then looks live over dead boxes                                                                                                        |
| Use a radio group or a SegmentedControl for one choice among several                                                                                                 | Use a CheckboxGroup for one choice: a set of checkboxes says any number may be ticked, none included                                                                                                      |
| Put a parent Checkbox, with `parent` and no `value`, first in the group and name it for the set, "All modes", and list every other checkbox's `value` in `allValues` | Leave a value out of `allValues`, or indent the boxes under the parent with a wrapper of your own: the parent counts only what `allValues` lists, and a wrapper takes the boxes out of the group's column |
| Use a single Checkbox for one on-or-off setting                                                                                                                      | Wrap one checkbox in a CheckboxGroup: a group of one adds a name the checkbox's own label already gives                                                                                                   |
