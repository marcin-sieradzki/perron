# AlertDialog

A modal question over the map and a `color.scrim` backdrop, such as "Clear all filters?", that one of its actions or Esc answers: it moves focus to the first of its actions, Cancel, wraps Tab inside the popup while focus is in it, and on close gives focus back to the button that opened it.

<!-- run notes -->

The design is deferred (ADR 0010, `docs/adr/0010-unattended-runs-with-design-deferred.md`): there is no read-back, code map or export, and this spec decides what the drawing would, from the contract, the foundations, the tokens, the Base UI reference for `AlertDialog` and its installed source (`node_modules/@base-ui/react/dialog/root/useRenderDialogRoot.js`, which gives the popup the `alertdialog` role, keeps it modal and turns off dismissal by a press outside), the [Button](button.md) spec, whose component AlertDialog's stories render as the trigger and the actions (its `dependsOn` is empty, since the component's code imports no other component), and the [Dialog](dialog.md) spec, the built member of the same family, whose treatment AlertDialog shares. No ROADMAP line names AlertDialog: it joined the registry with twenty other components, all `designing`, in one commit.

## Anatomy

Penpot page `Components/AlertDialog`. Family: Panels (the contract's [Families](README.md#families): an alert dialog is a dialog, glass like the Popups, over `color.scrim`, `radius.xl`). Shared parts: none: it has no close button, so no `CloseButton`, and its buttons are the caller's, in `actions`.

AlertDialog is one component that takes its words and its controls as props, `title`, `description`, `actions` and `trigger`, and renders every Base UI part itself, with the popup as its root, the element `ref`, `className`, `style` and the rest props reach, as [Dialog](dialog.md) does and for the same reasons: the registry gives it one entry for all its parts, `AlertDialog.Root` renders no element of its own, and the popup is the one element a caller would style or measure.

The alert dialog leaves out a close button (the `CloseButton` part) beside the title, its ways out being the caller's Cancel in `actions` and Esc: an alert dialog asks for an answer, Base UI's own demo has none, a third way out beside Cancel and Esc says the same thing twice, and Cancel, the first action, is the button touch screen readers leave by, which the Dialog spec's CR-6 asks a close button for.

`AlertDialog.Root` renders no element: it holds the open state and the props of [Props](#props) that map to it. Base UI's `AlertDialog.Viewport` is not used: the registry doesn't name it, and the popup positions and scrolls itself (CR-8). Base UI's `AlertDialog.Close` is not rendered either, and the registry's `baseUiParts` doesn't name it: the alert dialog has no close button, and the buttons in `actions` are the caller's, closed by the caller setting `open` to `false`, as [Dialog](dialog.md)'s actions are (CR-6). The `actions` part has no `slotProps` key, since its buttons are the caller's own elements and take their props there.

Base UI already does: it opens the alert dialog on a press of `AlertDialog.Trigger` and gives the trigger `aria-haspopup="dialog"`, `aria-expanded` and `aria-controls`; it portals the backdrop and the popup to `<body>`, and renders nothing there, on the server or the client, while the alert dialog is closed, unless the portal's `keepMounted` is set; it gives the popup the `alertdialog` role, names it from `AlertDialog.Title` and describes it from `AlertDialog.Description` through ids it generates; it keeps the alert dialog modal whatever it is given, and ignores a press outside the popup, on the backdrop or anywhere else, and a focus that leaves it, so only Esc, the caller setting `open` to `false`, or a press of the trigger while open, which the keyboard reaches only after a press on the backdrop, closes it; when it opens it moves focus to the first tabbable element in the popup, the first button in `actions`, Cancel, or to the popup itself when opened by touch, so no virtual keyboard opens, unless `initialFocus` says otherwise; while open it wraps Tab and Shift+Tab inside the popup while focus is in it, but a press on the backdrop moves focus to `<body>`, from where Tab lands on the last button in `actions` and Shift+Tab on the trigger, outside the popup and still focusable though hidden, where Enter or Space closes the alert dialog with reason `trigger-press`; it hides everything outside it from assistive technology with `aria-hidden`, blocks the pointer outside it and locks the page's scroll; Esc closes the topmost dialog only; on close it returns focus to the trigger, or to the element focused before it opened, unless `finalFocus` says otherwise; it reports each change it makes with its reason (`trigger-press` and `escape-key`, and `close-press`, `outside-press`, `focus-out`, `imperative-action` and `none`, which an alert dialog with no `AlertDialog.Close`, no `actionsRef` and no handle never gives) and a `cancel()` that keeps the alert dialog as it is, and reports none when the caller's `open` changes, though it returns focus on that close as on any other; it merges the props of the element given to `AlertDialog.Trigger`'s `render` over its own, the element's last.

## Props

In MUI's layout, as MUI's Dialog takes `open` and `onClose`, with the trigger, the words and the actions as props in place of MUI's `DialogTitle`, `DialogContentText` and `DialogActions` children. Every prop the component declares gets this description as its JSDoc; the inherited rows keep Base UI's. Slots come last.

AlertDialog leaves out `AlertDialog.Root`'s `actionsRef`, `handle`, `onOpenChangeComplete`, `triggerId` and `defaultTriggerId` (the last two set by AlertDialog itself from the trigger, CR-5), as Dialog does: no Mylder screen asks for them yet, and each can join later as a new optional prop, which the contract's [Change](README.md#change) rule allows. Base UI's alert dialog takes no `modal` and no `disablePointerDismissal`: it is always modal and never dismissed by a press outside.

AlertDialog takes its buttons as [Dialog](dialog.md)'s `actions` do, `actions`, any nodes such as Buttons in a row at its end, the least destructive one, Cancel, first and the confirming one last, and the caller closes it by setting `open` to `false` in an action's `onClick`, which calls no `onClose`: the two are one family, and one prop of one shape for the same row keeps the library's API alike (the `api-consistency` skill). With no close button, Cancel is the popup's first tabbable element, so Base UI's default initial focus lands on it, the answer that changes nothing. `actions` is required, where Dialog's is optional: with no close button, a button in it is the only way out of the alert dialog for touch screen readers, which have no Esc.

`description` is required: an alert dialog's description is its message, what answering does, and WAI-ARIA's alertdialog pattern asks for it through `aria-describedby`, which Base UI sets only when `AlertDialog.Description` renders.

AlertDialog takes no `children`, no body under the description: an alert dialog asks one question in a title and one sentence, a body with controls or a list is a [Dialog](dialog.md)'s, and `children` can join later as a new optional prop.

## Tokens

One row per part, state and property. States are the contract's design states: rest is no selector, open is `[data-open]` on the backdrop and the popup, hover is `:hover` inside `@media (hover: hover)`, pressed is `:active`, focus is `:focus-visible`. The trigger and the buttons in `actions` are the caller's elements and keep their own tokens in every state: AlertDialog styles none of them, nor the trigger's `[data-popup-open]`, and has no part of its own a pointer presses, so no hover, pressed or cursor rows. The portal is never seen and has no tokens.

The popup takes the Panels family's treatment ([Families](README.md#families)) as [Dialog](dialog.md)'s does, written again in `AlertDialog.css`, since Base UI renders the popup ([Families](README.md#families), "Glass"): `color.surface.overlay` with a `backdrop-filter` of `effect.glass-blur` and `effect.glass-saturate` and `shadow.panel`, a `border.width.025` edge in `color.border.subtle`, and `radius.xl`, over the `color.scrim` backdrop. It is padded `space.600`, its parts `space.300` apart, with the actions a further `space.300` from the description (`space.600` in all, the distance between blocks), end-aligned and `space.200` apart, wrapping; the title is in `typography.heading-lg`, which [Typography](../foundations/typography.md) gives to dialog titles, and the description in `typography.body-sm` in `color.text.secondary`, "the line under a title", as Dialog's.

The popup is as wide as Dialog's, at most 440 px and never wider than the viewport less `size.panel-gap` at each side, the 440 px written in `AlertDialog.css` as a raw length under a `perron-allow(component-css)` comment of its own: the two are one family and open over the same screens, one width keeps them alike, and [Layout](../foundations/layout.md#other-layout-properties) and the `design-tokens` skill keep a measure only a component's own CSS reads in that CSS, so it takes no `size.*` token until a third component needs it.

The buttons in `actions`, such as an `outline` `neutral` Cancel and a `brand` action, are the [Button](button.md) component's, which draws them in its own CSS (CR-7); the focus row is `perron.css`'s.

What axe won't catch, from the contract, each with how this component meets it:

- [ ] Everything the eye is told, the ear is told, for every shape each prop accepts: the alert dialog is announced as an alert dialog with its `title` as its name and its `description`, the buttons in `actions` show their own words, and the scrim only dims what the `aria-hidden` outside the popup already removes.
- [ ] Every landmark and named region has an accessible name: the alert dialog is named by its own heading, the `title`, through `aria-labelledby`, and `title` is required.
- [ ] Every default label can be overridden: none here; AlertDialog owns no string, and every word, Cancel's included, is the caller's.
- [ ] Every shape the type accepts renders, in every variant: `title`, `description` and `actions` render a string, an element and a list alike; a long word in the title or the description wraps, and the buttons in `actions` wrap onto more lines when the row is too narrow (CR-9).
- [ ] A hidden copy kept for animation is `aria-hidden`, and a collapsed region is `inert`: none here; the closed alert dialog renders nothing, and Base UI hides the page behind the open one with `aria-hidden`.
- [ ] Native semantics first: Base UI's `alertdialog` role, a native `<h2>` for the title, native `<button>`s for the trigger and the caller's Buttons in `actions`, and no ARIA of Perron's own.
- [ ] Focus moves in reading order and returns on close: the title comes first in the DOM, then the description and the buttons in `actions`, Cancel first, as on screen; opening moves focus to Cancel, the answer that changes nothing, and closing, by Esc or by the caller's `open`, returns it to the trigger, also for an alert dialog open at first render (CR-5). After a press on the backdrop, Base UI moves focus to `<body>`, and the next Tab lands on the last button in `actions`, not on Cancel, and Shift+Tab on the trigger (Keyboard and ARIA).
- [ ] Every target is at least `size.target-min` square: the buttons in `actions` are the caller's, and a [Button](button.md) at its `medium` size is `size.button` (36 px) tall and wider than tall.
- [ ] Loops stop when the system asks for less motion: none here; the alert dialog has no loop and no transition (CR-10).

## Owned strings

No owned strings: every word is the caller's, through `title`, `description`, `actions` and `trigger`, Cancel's words included, as in [Dialog](dialog.md)'s actions, so AlertDialog adds no key to `packages/perron/src/locale/en.ts` and takes no `<key>Label` prop.

## Component rules

Rules for this component alone, numbered so the build and the review can cite them.

- **CR-1.** Base UI's alert dialog already gives the `alertdialog` role, the modality, Tab wrapping inside the popup, the initial focus, the focus return, Esc, the ignored outside press, the scroll lock, the `aria-hidden` on the page behind and the popup's name and description, so the component rebuilds none of it and adds no key or pointer handlers.
- **CR-2.** AlertDialog renders `AlertDialog.Root` around `AlertDialog.Trigger` (only when `trigger` is given, with `render={trigger}`) and `AlertDialog.Portal`, which holds `AlertDialog.Backdrop` and then `AlertDialog.Popup`. The popup holds, in this order: `AlertDialog.Title`, `AlertDialog.Description`, and the actions `<div>` with the caller's `actions` as given. It renders no close button and no `AlertDialog.Close`. The DOM order is the reading order and the order on screen, so Base UI's initial focus lands on the first button in `actions`, which the caller makes Cancel.
- **CR-3.** `{...rest}` reaches `AlertDialog.Popup` before AlertDialog's own attributes, and AlertDialog's own props are taken out of `rest` first (`title`, `description`, `actions`, `trigger`, `open`, `defaultOpen`, `onOpen`, `onClose`, `slotProps`), so none reaches the DOM; `initialFocus`, `finalFocus` and `render` stay in `rest`, keeping Base UI's defaults. `ref`, `style` and `data-testid` land on the popup, and `className` is merged after `pn-AlertDialog`. `slotProps.trigger` is merged with Base UI's `mergeProps` (`@base-ui/react/merge-props`), AlertDialog's own `render` and `id` last. `slotProps.portal`, `backdrop`, `title` and `description` go to parts AlertDialog sets nothing on but their class, and the title's and the description's children, so each is spread as it is, `{...slotProps?.portal}`, as the contract's [Customising](README.md#customising) allows. On every part, the class is set after the caller's props with `withClass`, so a caller's class sits beside the part's `pn-AlertDialog-<part>`.
- **CR-4.** AlertDialog turns Base UI's `onOpenChange(open, details)` into `onOpen(details.event, details)` when `open` is `true` and `onClose(details.event, details.reason, details)` when it is `false`, and exposes neither `onOpenChange` nor any root prop of Base UI's beyond `open` and `defaultOpen`.
- **CR-5.** When `trigger` is given, AlertDialog gives `AlertDialog.Trigger` an id (the `trigger` element's own `id`, then `slotProps.trigger.id`, or one from React's `useId`) and passes it to `AlertDialog.Root` as `defaultTriggerId`, or as `triggerId` when `open` is set, as the Base UI reference says for a dialog open at first render or controlled, so focus returns to the trigger when such an alert dialog closes.
- **CR-6.** `actions` is required, a `ReactNode` as [Dialog](dialog.md)'s `actions` is, and renders as given inside the actions `<div>`: AlertDialog wraps no element, handler or class of its own around the caller's buttons. A button in it closes the alert dialog by the caller setting `open` to `false` in its `onClick`, which calls no `onClose`, and Base UI returns focus to the trigger as for any close. With no close button, a button in `actions` is the only way out for touch screen readers, which have no Esc.
- **CR-7.** The buttons in `actions` keep Button's look and states; AlertDialog's CSS sets nothing on them, and the actions row only lays them out.
- **CR-8.** The backdrop and the popup are `position: fixed`, the backdrop at `inset: 0`, both at `z-index.dialog`, the popup after the backdrop in the portal so it paints on top. The popup is centred in the viewport (`inset-block-start` and `inset-inline-start` at 50%, `translate: -50% -50%`, turned to `50% -50%` in right-to-left text), as wide as the smaller of 440 px and the viewport less `size.panel-gap` at each side, at most the viewport's height less `size.panel-gap` at each end, and scrolls as a whole (`overflow-y: auto`, `overscroll-behavior: contain`) when its content is taller. AlertDialog's CSS never redefines a token: the portal sits outside every themed container but `<body>`.
- **CR-9.** The title and the description have no margin of their own (the browser's `<h2>` and `<p>` margins are reset), the popup's `gap` spacing the parts. Long words wrap in the title and the description (`overflow-wrap: anywhere`), so a long Danish word fits a 320 px screen. The actions row is a flex row, end-aligned, that wraps (`flex-wrap: wrap`), so the buttons stack when their words don't fit side by side; each button keeps Button's own long-word rule.
- **CR-10.** The alert dialog opens and closes at once: no `duration.*` token fits a dialog's entrance, so the CSS has no transition and styles neither `data-starting-style` nor `data-ending-style`.
- **CR-11.** The popup draws its `border.width.025` edge as a border, so Windows' forced colours keep an edge round the alert dialog when they drop its glass and its shadow.
- **CR-12.** The portal renders nothing on the server, so the contract story's owned-strings check, which renders to static markup, sees only the trigger. AlertDialog's own stories check the open popup's words in the live DOM instead, that it shows no word the caller didn't give: `expectOwnedStrings(popup.outerHTML, locale, callerWords)` in English, and in Danish.
- **CR-13.** The stories' meta sets `parameters: { docs: { story: { inline: false, height: '480px' } } }`, as the contract's [Stories](README.md#stories) asks of an overlay, and each story opens its alert dialog at first render with `defaultOpen` or `open`, beside the trigger that opens it again.

AlertDialog's root, the popup, portals to `<body>`, and only after the portal mounts, so it is not inside the story's canvas. AlertDialog meets the contract story's Root rule with no exception: the contract story looks the root up in the whole document, as it does for every portalled component.

## Stories

AlertDialog has no variant property, so its deferred drawing has one variant, `Default`, the open alert dialog, and no `State` (`penpot/README.md`, "Conventions"): the buttons' hover, pressed and focus looks are Button's. The other stories show the behaviour beside it, which their `play` tests check.

Each story renders the alert dialog open at first render beside its trigger, a [Button](button.md), in a `PerronProvider` in English unless the story says otherwise, with `fn()` handlers for `onOpen` and `onClose`. Its `actions` are two Buttons, Cancel, `outline` and `neutral`, and then the `brand` action. The `Default` story is the subject story, and its args, which the contract story renders, hold every word the caller gives: the trigger "Clear all filters", the title "Clear all filters?", the description "The map shows every line again." and the actions "Cancel" and "Clear filters" ([Content design](../content-design.md)).

## Do and don't

For a caller using the component, with the reason.

| Do                                                                                                                                               | Don't                                                                                                                                           |
| ------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| Ask one question in the `title`, in sentence case, such as "Clear all filters?", and say in the `description` what answering does                | Write a title that isn't a question, such as "Warning", or leave the consequence out: the person can't answer what they weren't asked           |
| Name the action by what it does, such as "Clear filters", and make it the one `brand` Button, last in `actions`                                  | Name it "OK" or "Yes": the button must say what pressing it does, read on its own                                                               |
| Use an alert dialog for an answer that must come before anything else, such as before clearing or removing something                             | Use it for help, a form or a list: those are a [Dialog](dialog.md)'s, which a press outside closes                                              |
| Put Cancel first in `actions`, an `outline` `neutral` Button, so it takes focus when the alert dialog opens and Enter on its own changes nothing | Put the action first, or set `initialFocus` to it: a stray Enter would act at once                                                              |
| Control the alert dialog with `open`, and close it from each button's `onClick` by setting `open` to `false`, once the action's work is done     | Leave Cancel out, disable it or hide it with a `className`: with no close button, it is the way out for touch screen readers, which have no Esc |
| Pass the button that opens the alert dialog as `trigger`, so it is announced as opening a dialog and gets focus back                             | Open an alert dialog on its own, with no press from the person, to tell them something: a notice that needs no answer is an Alert or a Toast    |
| Name Cancel by what it keeps when that reads better, such as "Keep filters", in the screen's locale                                              | Add a close button or a second cancelling button to `actions`: Cancel and Esc already leave without acting                                      |
| Let the alert dialog take `z-index.dialog` and its place in the middle of the screen                                                             | Set a `z-index`, a position or an opacity on it: it would fall under another overlay or leave its scrim                                         |
