# Switch

A two-state control that turns one setting on or off at once, such as showing vehicle trails on the map.

<!-- run notes -->

The design is deferred (ADR 0010, `docs/adr/0010-unattended-runs-with-design-deferred.md`): there is no read-back, code map or export, and this spec decides what the drawing would, from the [contract](README.md), the [foundations](../foundations/README.md), [content design](../content-design.md), the tokens and the Base UI reference for `@base-ui/react` 1.9.0. No ROADMAP line names Switch; it joined the registry with the form components, with `baseUiParts` `Switch.Root` and `Switch.Thumb` and nothing in `dependsOn`. The extracted prototype component is not in any branch this run can reach, so nothing here rests on it. The foundations already name its look: [Elevation](../foundations/elevation.md#surfaces) puts tracks on `color.surface.inset` and pressed toggles on `color.surface.inverse`, [Accessibility](../foundations/accessibility.md#rules) asks every target to be `size.target-min` and every control's edge to reach 3:1, which `color.border.control` does, and [Semantic spacing](../foundations/semantic-spacing.md#radius) gives pills `radius.full`.

## Anatomy

Penpot page `Components/Switch`. Family: none (the contract's [Families](README.md#families) have no two-state track; its surfaces come from [Elevation](../foundations/elevation.md#surfaces), as FilterChip's do). Shared parts: none (every word is the caller's, and the state is told by `role="switch"` with `aria-checked`, not by a hidden word).

A second hidden input, `type="hidden"`, renders while the switch is off and both `name` and `uncheckedValue` are given, so the form submits the off value.

Base UI already does: `role="switch"` and `aria-checked` following the state; one tab stop, through `tabIndex` 0 on the `<span>`; Space (on release) and Enter (on press) toggle it, as a click does, through the hidden input's click, so `onCheckedChange` fires once with the new state and its details; a `<label>` wrapping the switch, or one whose `htmlFor` names its `id`, gives it `aria-labelledby` and toggles it when clicked, since the `id` lands on the hidden input; `aria-label` wins over an associated label, as on native inputs; a disabled switch sets `aria-disabled`, leaves the tab order (`tabIndex` −1) and ignores clicks and keys; a read-only one keeps focus but ignores clicks and keys, and sets `aria-readonly`; `details.cancel()` in `onCheckedChange` keeps an uncontrolled switch as it was; the hidden input submits `value` (default `"on"`) when on, and `uncheckedValue` when off and given; inside a Base UI `Field.Root` it takes the field's name, disabled state, label and validation, setting `aria-invalid` and `data-invalid` when the field is invalid.

## Props

In MUI's layout. Every prop the props type declares gets this description as its JSDoc; every inherited one keeps Base UI's. Slots come last. The props type extends `Switch.Root.Props` without `checked`, `defaultChecked`, `onCheckedChange`, `disabled`, `readOnly`, `required`, `name`, `className`, `style`, `children` and `ref`: it declares its own `checked`, `defaultChecked`, `disabled`, `readOnly`, `required`, `name`, `className`, `style` and `ref`, with the descriptions below, maps `onCheckedChange` to `onChange`, and renders the thumb as the only child.

The switch's state is `checked`, `defaultChecked` and `onChange(event, value, details)`, whose `value` argument is the new `checked`, and the `value` prop stays the value a form submits when it is on. These are MUI's Switch names and Base UI's own `checked` and `defaultChecked`; the contract's [State and events](README.md#state-and-events) keeps `value`, `defaultValue` and `onChange` for a value a control chooses, but a switch's value is a boolean, and MUI and Base UI both give `value` to the submitted string, so a caller coming from either reads them as they do there; `onChange` keeps the contract's `(event, value, details)` shape, its value the new `checked`; and the contract's [Names from other libraries](README.md#names-from-other-libraries) leave all three free, where FilterChip's `selected` names a toggle button's pressed state, not a switch's.

The switch takes no label of its own: the caller names it with a `<label>` around it or beside it, a Field's label, or `aria-label` or `aria-labelledby`. MUI's Switch takes no label (its `FormControlLabel` adds one) and Base UI's `Switch.Root` takes none, labelling itself from a native `<label>` or a `Field.Label`; Field, registered beside Switch, is where a label, a description and an error sit for every form control; one switch's setting row, a label at the start and the switch at the end, varies between a settings list and a panel; and the API only grows, so a `label` prop can join later without a break.

The switch comes in one look, with no `variant`, `size` or `color`. The [brand](../foundations/README.md#the-brand) keeps the interface to ink, glass and neutral surfaces, with yellow for the one main action, which a switch never is; the on track is `color.surface.inverse`, the pressed toggle's fill, as FilterChip's selected fill is; the track is `size.target-min` tall, the smallest target, so a `small` would miss it; and each prop can join later without a break.

The switch passes every other prop of `Switch.Root` through unchanged (`value`, `uncheckedValue`, `form`, `inputRef`, `id`, `nativeButton` and `render`), and declares `readOnly`, `required` and `name` with Perron's own descriptions. Each is a form or labelling hook a caller of Base UI's switch has, none changes the look, the contract asks `name` of every control a form submits and names `required` and `readOnly` among its booleans, and leaving one out now would only make a caller wrap the switch to reach it.

Switch takes no `children`: its one child is the thumb, which it renders itself, and the caller's words go in the label beside it. No label-override props: the switch owns no strings.

## Tokens

One row per part, state and property. States are the contract's design states: rest is no selector (the switch off, `[data-unchecked]`), hover is `:hover` inside `@media (hover: hover)`, pressed is `:active`, focus is `:focus-visible`, disabled is `[data-disabled]`, selected is Base UI's `[data-checked]` (the switch on), and invalid is `[data-invalid]`, which Base UI sets only inside a `Field.Root` whose field is invalid. Highlighted and open don't apply: the switch takes focus rather than `data-highlighted`, and opens nothing.

The track is 40 × 24 px and the thumb 18 px, from the tokens with no new size token: the root is `size.target-min` tall and `size.target-min` plus `space.400` wide, with a `border.width.025` border and `space.050` padding inside it, so the thumb is `size.target-min` less twice the padding and the border, and travels `space.400`. The track is the target, so `size.target-min` tall meets [Accessibility](../foundations/accessibility.md#rules) on its own; the width is the height plus the travel, a common switch's proportion beside `typography.label` text; the thumb is 18 px inside a 1 px edge and a 2 px gap, so it reads as a separate mark; the travel, 40 − 6 − 18, is exactly `space.400`; and [Layout](../foundations/layout.md#other-layout-properties) keeps a measure only one component reads in that component's CSS, as `calc()` over the tokens.

The switch off is a `color.surface.inset` track with a `border.width.025` edge in `color.border.control` and a `color.text.secondary` thumb, and on a `color.surface.inverse` track and edge with a `color.surface.raised` thumb; hover and pressed lay `color.surface.hover` over the off track and turn the on track `color.surface.inverse-hover`, and there is no shadow. [Elevation](../foundations/elevation.md#surfaces) puts tracks on `color.surface.inset` and pressed toggles on `color.surface.inverse`; `color.surface.inset` stands only 1.17:1 from `color.surface.raised`, so the off track needs `color.border.control`'s 3:1 edge to show where it is ([Accessibility](../foundations/accessibility.md#controls-focus-and-status-fills-on-surfaces)); the thumb's colour reaches well past 3:1 on its track in both states and both themes (`color.text.secondary` is 6.77:1 on light inset and 5.71:1 on dark), so on and off differ in the thumb's place, the thumb's colour and the track's fill, never in colour alone; the hover fills are the ones FilterChip and the Fields take; the edge keeps its width when on, in the fill's colour, so the geometry holds (CR-5); and [Elevation](../foundations/elevation.md#shadows) gives `shadow.thumb` to the selected segment alone, where the thumb needs no shadow to stand out.

A disabled switch off is a `color.surface.inset` track with a `color.border.subtle` edge and a `color.text.tertiary` thumb, and on a `color.text.tertiary` track and edge with a `color.surface.raised` thumb, with no hover or pressed layer. The contract makes disabled a colour, `color.text.tertiary`, never an opacity; a disabled control is exempt from 3:1, so the edge steps down to the decorative `color.border.subtle`; and a disabled switch still shows whether its setting is on, by the thumb's place and the track's fill, as a disabled segmented control keeps its choice.

Inside an invalid Base UI `Field.Root`, a state Base UI produces (`data-invalid`) that no drawing shows, the track's edge turns `color.status.danger`, on and off, with the fills unchanged. The contract's [Families](README.md#families) give the Fields' edge `color.status.danger` when invalid, a switch sits in a Field beside them, and the message that says why is the Field's, not the switch's. Disabled wins over invalid: a disabled switch in an invalid Field keeps its disabled edge, `color.border.subtle` or `color.text.tertiary`, since Base UI drops `aria-invalid` while the control is disabled (`field/root/useFieldValidation.js`), and a disabled control is exempt from 3:1 and shows no error.

## Owned strings

The switch shows no "On" or "Off" word, though [Accessibility](../foundations/accessibility.md#rules) asks toggles to say their state in words as well as in looks. That rule is for a toggle whose label is an action and its only word, such as "Follow" and "Following"; a switch's label names the setting and stays the same, Base UI's `role="switch"` says on or off to the ear in every locale with no word of Perron's, and the eye gets the thumb's place as well as the fill, so the state never rests on colour alone. A word beside every switch would also lengthen each settings row in Danish, and the caller can still write one in the label.

No owned strings: every word comes from the caller, as the label or `aria-label`.

## Component rules

Rules for this component alone, numbered so the build and the review can cite them.

- **CR-1.** Base UI's switch already gives the role, `aria-checked`, the tab stop, Space and Enter, the label's click and its `aria-labelledby`, disabled and read-only, the hidden input and the Field integration, so the component rebuilds none of it and adds no key or click handlers.
- **CR-2.** Switch adapts Base UI's `onCheckedChange(checked, details)` into `onChange(details.event, checked, details)` inside itself and exposes no `onCheckedChange`. It passes `checked` only when given, so a switch given neither `checked` nor `defaultChecked` is uncontrolled and off.
- **CR-3.** The switch is always named by the caller, by one of the ways the Keyboard and ARIA table gives, and the `Default` story's args hold an `aria-label`, "Show vehicle trails", so the contract story renders it alone with a name. Every other story names its switch the same way or with a `<label>`.
- **CR-4.** Switch takes `{...rest}` before its own attributes and its own props out of `rest` first (`checked`, `defaultChecked`, `onChange`, `disabled`, `readOnly`, `required`, `name`, `className`, `slotProps`; an inherited Base UI prop such as `value`, `form` or `nativeButton` stays in `rest`, keeping Base UI's default), merges `className` after `pn-Switch`, and renders the thumb as Base UI's `Switch.Thumb`, so it keeps the root's state attributes, with `slotProps.thumb` merged under its own props by `mergeProps` and its class `pn-Switch-thumb` first by `withClass`, as Dialog's parts do (`usePart` renders a plain element, which would drop them); `ref` reaches the root `<span>`.
- **CR-5.** The states keep the geometry: hover, pressed, focus, selected, disabled, read-only and invalid change the fills, the edge's colour and the thumb's place only, never the track's size, the edge's width, the padding or the thumb's size, and the root never shrinks in a flex row (`flex-shrink: 0`), so a long label beside it wraps rather than squeezing the track.
- **CR-6.** The thumb moves by `margin-inline-start`, from `0` to `space.400`, so it goes to the inline end in right-to-left text with no `DirectionProvider`; it and the track's fill and edge change over `duration.switch` with `easing.standard`, which reduced motion shortens to 0.01 ms with no query in the component. The first render does not animate, since a transition only runs on a change.
- **CR-7.** Hover is read inside `@media (hover: hover)`; pressed (`:active`) takes the hover fill in a rule outside it, so a touch press shows. Neither applies to a disabled or a read-only switch: both rules exclude `[data-disabled]` and `[data-readonly]`. Selected is `.pn-Switch[data-checked]`, one class then attributes, and the thumb's is `.pn-Switch-thumb[data-checked]`, from its own state attributes.
- **CR-8.** A read-only switch, a state Base UI produces (`data-readonly`) that no drawing shows, looks as at rest, on or off, with no hover or pressed layer and the default cursor. It still shows its state, which is what read-only is for; a dimmed look would read as disabled, which it isn't, since it keeps its tab stop; and the label or the Field's description says why it can't change.
- **CR-9.** The cursor is `pointer` on the root, and `default` while disabled or read-only, as on Tabs and SegmentedControl.
- **CR-10.** Focus uses the ring `perron.css` draws on `:focus-visible`, which follows the pill's `radius.full`; the component draws no ring of its own and never removes the outline.
- **CR-11.** In `@media (forced-colors: active)`, where the browser drops the fills, the root sets `forced-color-adjust: none` and draws its states in system colours: off, a `Canvas` track with a `ButtonText` edge and thumb; on, a `Highlight` track and edge with a `HighlightText` thumb; disabled, a `GrayText` edge and thumb off, and a `GrayText` track and edge with a `Canvas` thumb on; and the focus ring's `outline-color` is `CanvasText`, which the browser no longer forces once the root opts out. So the thumb, which would otherwise vanish into the forced `Canvas`, and the on and disabled states still show, as [Accessibility](../foundations/accessibility.md#what-a-person-checks) asks.

## Stories

The deferred design's page draws one variant property, `State` (`default`, `hover`, `focus`, `checked`, `disabled`), and each of its stories is named by its variant name (`penpot/README.md`, "Conventions"). Every state story renders one switch named with `aria-label` "Show vehicle trails"; the hover and focus stories render at rest: the visual check drives the state, and their `play` tests check it. `Default` is the [subject story](README.md#root), which the contract story renders, and its args pass every rule alone.

The on state is the `State` value `checked`, its story `Checked`, rather than a second variant property or the contract's design-state name `selected`. One `State` property keeps the drawing's variants named by state alone, as FilterChip's are, where a `checked` property beside `State` would name them `TrueHover`; and `checked` is the prop and Base UI's `data-checked`, the word a caller looks for, where `selected` is a row's.

The on switch's hover and its disabled look, which Base UI's `data-checked` produces beside `:hover` and `data-disabled` but the single `State` property can't show, get the `CheckedDisabled` story and a hover check in `Checked`'s `play`, with no Penpot variant of their own; read-only and invalid get stories of their own for the same reason.

## Do and don't

For a caller using the component, with the reason.

| Do                                                                                                                                                | Don't                                                                                                                                                        |
| ------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Use a Switch for a setting that takes effect the moment it changes, such as showing vehicle trails or the stations on the map                     | Use it for an answer a form sends later with a button: a checkbox says "choose now, apply on submit", where a switch says "this is on now"                   |
| Name it with a visible `<label>` or a Field's label that names the setting, in sentence case: "Show vehicle trails"                               | Leave it unnamed, or name it with `aria-label` where there is room for a visible label: a sighted person can't tell what an unlabelled switch turns on       |
| Keep the label the same whether the switch is on or off                                                                                           | Write the state in the label, "Trails on", or swap it when the switch flips: the switch already says on or off, and a changing label reads as a second state |
| Put the label before the switch in a settings row, and let a long label wrap                                                                      | Squeeze the switch to fit a long label, or cut the label off: the track keeps its size, and a Danish label is longer than its English                        |
| Filter the map's vehicles with a [FilterChip](filter-chip.md), and pick one way of showing a view with a [SegmentedControl](segmented-control.md) | Use a row of switches for one choice of several, or for the top bar's filters: switches each turn their own setting on, and a chip shows its count           |
| Run an action, such as following a vehicle, with a [Button](button.md)                                                                            | Use a switch to start something that then runs on its own: a switch holds a state, it doesn't trigger one                                                    |
| Say why a switch is disabled or read-only, in its label or the Field's description                                                                | Disable a switch with no word of why: a dimmed switch can't explain itself                                                                                   |
