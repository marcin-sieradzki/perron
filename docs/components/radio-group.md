# RadioGroup

A named set of two to six choices of which exactly one holds at a time, such as the theme the map is drawn in, each a round mark beside its words.

The design is deferred (ADR 0010, `docs/adr/0010-unattended-runs-with-design-deferred.md`): there is no read-back, code map or export, and this spec decides what the drawing would, from the [contract](README.md), the [foundations](../foundations/README.md), [content design](../content-design.md), the tokens, the Base UI reference for `RadioGroup` and `Radio` (`@base-ui/react` 1.9.0, installed) and the spec of the one entry in `dependsOn`, [Fieldset](fieldset.md). No ROADMAP line names RadioGroup; it joined the registry with the form components, with `baseUiParts` `RadioGroup`, `Radio.Root` and `Radio.Indicator`. The extracted prototype component is not in any branch this run can reach, so nothing here rests on it. [Switch](switch.md), the other two-state form control, and [Field](field.md), the frame round one form control, have shipped and are in this branch: the radio's look follows Switch's where the two meet (the on fill, the hover, the disabled, read-only and invalid looks, the cursor), and what Field means for the group is in Anatomy.

The foundations already name most of the look: [Elevation](../foundations/elevation.md#surfaces) puts inputs on `color.surface.raised` and pressed toggles on `color.surface.inverse`; [Accessibility](../foundations/accessibility.md#rules) asks every target to be `size.target-min` and every control's edge to reach 3:1, which `color.border.control` does; [Semantic spacing](../foundations/semantic-spacing.md) gives round marks `radius.full`; and Fieldset's spec says RadioGroup renders Fieldset with Base UI's `RadioGroup` through `render`, so the group takes Fieldset's legend, its name and its disabled state (Fieldset CR-5).

## Anatomy

Penpot page `Components/RadioGroup`. Family: none (the contract's [Families](README.md#families) have no round choice mark; a radio is not a Row, since it takes no fill on hover, and its mark's surfaces come from [Elevation](../foundations/elevation.md#surfaces)). Shared parts: `VisuallyHidden`, through Fieldset, for a hidden label.

The control is written as two components, `RadioGroup` for the named group and `Radio` for each choice, both exported with their props types from `RadioGroup.tsx`, an exception to the contract's "one component per folder" as SegmentedControl, Tabs and Toolbar are. Base UI's `Radio.Root` reads `RadioGroup`'s context for its checked state, so a radio can't be shown apart from its group; the caller writes a radio many times, so it is a component of its own; a child component takes a `ReactNode` label where an `options` array would need a shape of its own; MUI writes `<RadioGroup>` round its radios too; and the registry's one entry, with `baseUiParts` `RadioGroup`, `Radio.Root` and `Radio.Indicator`, stays one entry. The `props` check reads both props types, and the `api-compatibility` check only `RadioGroupProps`, so the review holds `RadioProps` to the contract's Change rules.

A radio's root is Base UI's `Radio.Root` itself, the `<span role="radio">` holding the round mark and the words as one row, rather than a `<label>` wrapped round a bare `Radio.Root`, as Checkbox's root, still designing, is to be its `Checkbox.Root`. The row is then the radio: one element takes the `ref`, the class, the rest props, `render` and the focus ring; a click anywhere on it, mark or words, selects it through Base UI's own click; its words are its accessible name, as a radio's role takes its name from its content; the whole row is the target, so it passes `size.target-min` with room to spare; and `slotProps` has one key, `indicator`, named for the one inner Base UI part. A wrapping `<label>` would be an element with no Base UI part as the component's root, which takes `className` and `ref` while `render` and the rest props would reach a part inside it.

The indicator is the whole circle, not only its dot: Base UI's `Radio.Indicator` with `keepMounted` stays in the DOM while the radio is unchecked and carries the radio's state attributes (`data-checked`, `data-unchecked`, `data-disabled`, `data-readonly`, `data-invalid`), so the mark is drawn by one element whose own attributes select each state, one class then attributes; the dot is its `::before`, drawn only on `[data-checked]`. The `input` has no class and no `slotProps` key: Base UI renders it inside `Radio.Root`'s fragment and gives the caller `inputRef`, `id` and the group's `name` and `form` to reach it.

RadioGroup takes no description and no error of its own, though Perron's [Field](field.md) has shipped with a required `label` it always renders as `Field.Label`: a caller who needs either wraps the group in Base UI's `Field.Root` with `Field.Description` and `Field.Error` and no `Field.Label`, never in Perron's Field, until Field can frame a group. In the installed Base UI a `Field.Label` at the field's root names the group and every radio in it: the group's `aria-labelledby` takes the field's label id before the legend's (`radio-group/RadioGroup.js`), and each `Radio.Root` takes the same id before its own words (`radio/root/RadioRoot.js`, through `useAriaLabelledBy`), so inside Perron's Field every radio would be heard as the field's label; Base UI's forms guide frames a radio group with a `Field.Root` and no label at its root, which keeps the legend the group's name and each radio's words its own, while Base UI still ties the description and the error to the group and marks each radio invalid; a `description` and an `error` on RadioGroup would build Field's parts, look and validation props a second time, and again on CheckboxGroup, where one change to Field would serve both; and either prop can join RadioGroup later without a break. The `Invalid` story uses Base UI's `Field.Root` that way.

Base UI already does: `role="radiogroup"` on the group and `role="radio"` with `aria-checked` on each radio; one tab stop for the whole group, a roving `tabIndex` that rests on the checked radio, or the first enabled one while none is checked; the four arrow keys move focus to the next or the previous enabled radio, wrapping at the ends, and check it as focus lands (the installed group runs its composite root with `orientation` `'both'`, `loopFocus` on and `enableHomeAndEndKeys` off); Space checks the focused radio, through the hidden input's click, and Enter does nothing, since the installed `Radio.Root` stops Enter's click; a click anywhere on the radio checks it; a disabled radio sets `aria-disabled`, is skipped by the arrow keys and ignores clicks and keys, and a disabled group disables every radio in it; a disabled group, or a checked radio disabled alone, keeps the group's one tab stop, a focusable radio announced as dimmed that Space and a click don't change (the installed `RadioGroup` keeps its roving `tabIndex` of 0 while disabled), and from a checked radio disabled alone the arrow keys move on to the enabled radios; a read-only group keeps its tab stop and lets the arrows move focus but checks nothing, and sets `aria-readonly`; `onValueChange` passes `details` whose `cancel()` keeps an uncontrolled group as it was; each hidden input carries the group's `name`, so a native `<form>` submits the checked radio's `value` and `FormData` reads it; `required` makes the hidden inputs required, so a native form won't submit with none checked; the group takes the legend's id as its `aria-labelledby` from the Fieldset round it; inside a Base UI `Field.Root` it takes the field's name, disabled state and validation, joins the field's description and error into each radio's `aria-describedby`, and sets `aria-invalid` and `data-invalid` on each radio while the field is invalid; a `Field.Label` at that field's root becomes the `aria-labelledby` of the group, before the legend's id, and of each radio, before its own words; Left and Right swap only under Base UI's `DirectionProvider` set to `rtl`, which Perron doesn't set up, as all four locales run left to right.

## Props

In MUI's layout. Every prop the props types declare gets this description as its JSDoc; every inherited one keeps Base UI's. Slots come last.

The group's name is the `label` prop, with `hiddenLabel` to hear it without seeing it, as SearchField's are, passed to Fieldset as its `legend` and `hiddenLegend`. A radio group is one form control with one value, named as a field is, and SearchField already ships `label` and `hiddenLabel` for a field's name; MUI's form controls take `label` for their name; Fieldset's spec expects RadioGroup to pass its own `hiddenLabel` straight to Fieldset's `hiddenLegend`; and `legend` would name the group by the HTML element it renders through, which a caller of a radio group never writes. The prop is required, as Fieldset's `legend` is, so the group is never announced unnamed.

The value is a `string`, and no radio is checked while neither `value` nor `defaultValue` is given. Base UI's `RadioGroup` takes any value, but a `string` is what a hidden input submits and what `onChange` narrows without a cast, as SegmentedControl's value is; Base UI checks nothing by default and has no fallback, and building one would mean reading the radios' values out of `children`; and a group with nothing checked is the caller's choice, such as a question not yet answered, which `required` then holds to an answer.

The group comes in one look, a vertical column, with no `variant`, `size`, `color` or `orientation`. The [brand](../foundations/README.md#the-brand) keeps the interface to ink and neutral surfaces, and a radio is never the main action, so it takes no `brand`; a row is `size.target-min` tall, the smallest target, so a `small` would miss it; Mylder's choices sit in panels and sheets, where a column reads each choice in full and wraps a long Danish one, and a row of radios is what SegmentedControl draws better; Base UI's group takes no orientation of its own and its arrow keys already run all four ways; and each prop can join later without a break.

The group passes Base UI's `form` and `inputRef` through unchanged and declares `name`, `disabled`, `readOnly` and `required` with Perron's own descriptions: the contract's [State and events](README.md#state-and-events) asks a radio group for `name`, and names `required` and `readOnly` among its booleans. A radio passes Base UI's `nativeButton`, `readOnly`, `required` and `inputRef` through; a radio's own `readOnly` or `required` adds to the group's, which Base UI joins with an "or". No label-override props: the component owns no strings.

RadioGroup takes no `description` and no `error`: a hint or an error reaches the group through Base UI's `Field.Root` round it, with `Field.Description` and `Field.Error` and no `Field.Label`, as Anatomy says, never through Perron's [Field](field.md), whose required label would rename the group and every radio in it (CR-12); either prop can join later without a break.

`Radio` takes no description line of its own: `children` is phrasing content in one span, so a caller who needs a second line can set one in it, and a `description` prop, with its own typography and `aria-describedby`, can join later without a break.

## Tokens

One row per part, state and property. States are the contract's design states: rest is no selector (an unchecked radio, `[data-unchecked]`), hover is `:hover` on the radio inside `@media (hover: hover)`, pressed is `:active` on the radio, focus is `:focus-visible` on the radio, disabled is `[data-disabled]`, selected is Base UI's `[data-checked]` (the radio checked), and invalid is `[data-invalid]`, which Base UI sets only inside a `Field.Root` whose field is invalid. Highlighted and open don't apply: a radio takes focus rather than `data-highlighted`, and opens nothing. The indicator reads its own state attributes; hover and pressed are the radio's, read on the indicator inside it (`.pn-Radio:hover > .pn-Radio-indicator`), so hovering the words lights the mark.

The group itself sets nothing Fieldset doesn't: Fieldset's root is the flex column with its `space.200` gap between the legend and each radio, and its legend is `typography.label` in `color.text.primary`, tertiary while disabled. RadioGroup's CSS draws the radios.

The indicator is a 16 px circle, `icon.size.400`, with a dot half its size, centred on the first line of the label in `typography.body`. `icon.size.400` is the size of the marks inside Perron's controls, and a radio's circle is one; 16 px beside 14 px body text is the size Base UI's own demo and most systems draw, and the size Checkbox's box, still designing, is to take, so the two marks agree; a dot of half the circle, `calc()` over the same token, keeps the proportion if the token changes; and `margin-block` of half the line less half the circle (`1lh`, the contract's one line of the element's own typography) keeps the mark on the first line when a long label wraps. A size token of its own, such as `size.choice-mark`, would go through the `design-tokens` skill instead.

A checked radio is a `color.surface.inverse` circle and edge with a `color.surface.raised` dot, and an unchecked one a `color.surface.raised` circle with a `border.width.025` edge in `color.border.control`. [Elevation](../foundations/elevation.md#surfaces) puts inputs on `color.surface.raised` and pressed toggles on `color.surface.inverse`, the fill FilterChip's selected state and Switch's on track take, as Checkbox's ticked box is to; `color.border.control` is the edge that shows where a control is, 3:1 or better on every surface ([Accessibility](../foundations/accessibility.md#controls-focus-and-status-fills-on-surfaces)), so an unchecked circle shows on a raised panel; a checked radio differs in its fill and in its dot, never in colour alone; and the edge keeps its width when checked, in the fill's colour, so the geometry holds (CR-6). A thick ink ring with an ink dot, the classic look `border.width.050` could give, would be a second way to show a pressed control.

A disabled radio unchecked is a `color.surface.inset` circle with a `color.border.subtle` edge, and checked a `color.text.tertiary` circle and edge with a `color.surface.raised` dot, its words `color.text.tertiary`, with no hover or pressed layer. The contract makes disabled a colour, `color.text.tertiary`, never an opacity; a disabled control is exempt from 3:1, so the edge steps down to the decorative `color.border.subtle`; and a disabled group still shows which choice it holds, as a disabled segmented control keeps its choice.

Read-only and invalid are states Base UI's parts produce (`data-readonly`, `data-invalid`) that no drawing shows: a read-only radio looks as at rest, checked or not, with no hover or pressed layer and the default cursor, and an invalid one turns its edge `color.status.danger`, checked or not, with its fills unchanged and disabled winning over it, as Switch's are and Checkbox's are to be. A read-only group keeps its tab stop, so a dimmed look would read as disabled, which it isn't; the contract's [Families](README.md#families) give the Fields' edge `color.status.danger` when invalid, a radio group sits in a Field beside them, and the message that says why is the Field's; and Base UI drops `aria-invalid` while a control is disabled, which is exempt from 3:1 and shows no error.

The focus ring goes round the radio's whole row, the outline `perron.css` draws on its `:focus-visible`, with the row's `radius.md`, rather than round the circle alone. The row is the element that takes focus and the target a click lands on, so the ring shows what Space will check; `perron.css` already draws it, so the component draws no ring of its own and removes no outline, as [Accessibility](../foundations/accessibility.md#rules) asks; and `radius.md` is the radius of a button and a row, so the ring reads as theirs. A ring round the circle alone would hide the row's outline and draw a second ring on the indicator with `focus.width`, `focus.offset` and `color.border.focus`.

Required changes no look: Base UI's `data-required` sets nothing, and the label or the Field says the choice is required. Base UI's other field attributes, `data-dirty`, `data-touched`, `data-filled` and `data-focused`, set nothing either.

Nothing moves: a radio's fill and dot change at once. [Motion](../foundations/motion.md) says motion explains a change of place, and nothing in a radio changes place, where a switch's thumb slides to its other end; the contract's [CSS](README.md#css) says a state with no fitting duration changes at once; and `duration.switch`, the one short duration, is described as the switch's thumb slide and track fill.

What axe won't catch, from the contract, each with how this component meets it:

- [ ] Everything the eye is told, the ear is told, for every shape each prop accepts: the checked radio's filled circle and dot are `aria-checked="true"` and every other radio's `"false"`; a disabled radio's tertiary colours are `aria-disabled`, heard as dimmed, on each radio of a disabled group; a read-only group is `aria-readonly`; an invalid radio's danger edge is `aria-invalid`, with the Field's message as its description; the label the eye reads above the radios is the group's name, and a hidden label still is.
- [ ] Every landmark and named region has an accessible name: the root is a `radiogroup`, not a landmark, and is always named by its `label`, which is required (CR-2).
- [ ] Every default label can be overridden: none here; the component owns no strings.
- [ ] Every shape the type accepts renders, in every variant: `label` and a radio's `children` render a string, an element and a list alike; a radio's words sit in one span, so text and elements flow and wrap as one run beside the mark, as the `LabelShapes` story shows.
- [ ] A hidden copy kept for animation is `aria-hidden`, and a collapsed region is `inert`: the hidden inputs are Base UI's, `aria-hidden` and out of the tab order; the indicator kept mounted while unchecked holds no text, so it adds nothing to the tree; nothing collapses.
- [ ] Native semantics first: Base UI's `radiogroup` and `radio` roles with `aria-checked`, with a native `<input type="radio">` beside each for the form; with `render` and `nativeButton`, a native `<button>`. Perron adds no ARIA.
- [ ] Focus moves in reading order and returns on close: the arrow keys move through the radios in document order, below their label, and Tab leaves the group after its one stop; focus stays on the radio it checks; the group opens nothing to return from.
- [ ] Every target is at least `size.target-min` square: the smallest target is a radio with a one-letter label, `size.target-min` (24 px) tall and the 16 px circle, the `space.200` gap and the letter (at least 24 px) wide.
- [ ] Loops stop when the system asks for less motion: no loop, and no transition; a radio's state changes at once.

## Owned strings

No owned strings: every word RadioGroup shows or announces comes from the caller, through `label` and each radio's `children`. Base UI's roles say checked or not checked, and a radio's place in its group, in every locale with no word of Perron's.

## Component rules

Rules for this component alone, numbered so the build and the review can cite them.

- **CR-1.** Base UI's group and radios already give the roles, `aria-checked`, the one tab stop and its roving `tabIndex`, the arrow keys that move and check, Space, the click, disabled and read-only, the hidden inputs and the Field integration, so the component rebuilds none of it and adds no key or click handlers. Perron forces no `tabIndex`: a disabled group, or a checked radio disabled alone, keeps Base UI's one focusable stop, announced as dimmed, that changes nothing, and the arrow keys skip disabled radios.
- **CR-2.** RadioGroup renders Perron's [Fieldset](fieldset.md) with Base UI's `RadioGroup` as its `render`, as Base UI's forms guide composes `<Fieldset.Root render={<RadioGroup />}>`: `label` is Fieldset's required `legend` and `hiddenLabel` its `hiddenLegend`, so the group is always named by its legend's id through `aria-labelledby` and a hidden label stays in the tree; `disabled` reaches Fieldset, which hands it to the group and shares it through Base UI's context. The root keeps Fieldset's `pn-Fieldset` and its column and gap, and RadioGroup's CSS sets no `gap`, `padding` or `border` on it.
- **CR-3.** RadioGroup adapts Base UI's `onValueChange(value, details)` into `onChange(details.event, value, details)` inside itself and exposes no `onValueChange`. It passes `value` only when given, so a group given neither `value` nor `defaultValue` is uncontrolled with nothing checked. A click on the radio already checked changes nothing and calls no `onChange`, as Base UI's hidden input fires no change.
- **CR-4.** Each component takes `{...rest}` before its own attributes and its own props out of `rest` first: RadioGroup takes `label`, `hiddenLabel`, `value`, `defaultValue`, `onChange`, `name`, `disabled`, `readOnly`, `required`, `children`, `className`, `slotProps` and `ref`, and gives `rest` (with `form`, `inputRef`, `render` and the caller's `aria-*`) to Base UI's `RadioGroup`; Radio takes `value`, `disabled`, `children`, `className` and `slotProps`, and gives `rest` (with `readOnly`, `required`, `inputRef`, `nativeButton` and `render`) to `Radio.Root`. `ref` reaches the root of each: the `<div role="radiogroup">` and the `<span role="radio">`. Class order is the component's own first, then the caller's: `pn-RadioGroup` (with Fieldset's `pn-Fieldset`), `pn-RadioGroup-legend` (with Fieldset's `pn-Fieldset-legend`), `pn-Radio`, `pn-Radio-indicator`, through `withClass` where the caller's `className` may be a function of the state.
- **CR-5.** A radio renders `Radio.Indicator` with `keepMounted`, so the circle is drawn while the radio is unchecked, from the indicator's own state attributes; `slotProps.indicator` merges under Perron's props with `mergeProps`, Perron's `keepMounted` last. After the indicator comes the label span holding `children`; the radio's root has no other child.
- **CR-6.** The states keep the geometry: hover, pressed, focus, selected, disabled, read-only and invalid change the indicator's fill, its edge's colour and the dot only, never the circle's size, the edge's width or the row's padding, and the indicator never shrinks in its row (`flex-shrink: 0`), so a long label wraps beside it rather than squeezing it.
- **CR-7.** A radio's words break a word longer than their line (`overflow-wrap: anywhere`, on `.pn-Radio`, which sets the typography): a radio is never wider than its group, and "Realtidsdataforsinkelser", wider than 120 px in `typography.body`, wraps beside the circle in a 120 px group, the circle staying on the first line.
- **CR-8.** Hover is read inside `@media (hover: hover)`; pressed (`:active`) takes the hover fill in a rule outside it, so a touch press shows. Neither applies to a disabled or a read-only radio: both rules exclude `[data-disabled]` and `[data-readonly]`. Selected is `.pn-Radio-indicator[data-checked]`, one class then attributes, from the indicator's own state attributes.
- **CR-9.** A read-only radio looks as at rest, checked or not, with no hover or pressed layer and the default cursor; the label or the Field's description says why it can't change. An invalid one turns its indicator's edge `color.status.danger`, checked or not, and a disabled one keeps its disabled edge even inside an invalid Field.
- **CR-10.** Focus uses the ring `perron.css` draws on the radio's `:focus-visible`, which follows its `radius.md`; the component draws no ring of its own and never removes the outline. Nothing in RadioGroup or Radio sets `overflow`, so a ring drawn `focus.offset` outside a radio is never cut at the group's edge.
- **CR-11.** In `@media (forced-colors: active)`, where the browser drops the fills, the indicator sets `forced-color-adjust: none` and draws its states in system colours: unchecked, a `Canvas` circle with a `ButtonText` edge; checked, a `Highlight` circle and edge with a `HighlightText` dot; disabled, a `GrayText` edge unchecked, and a `GrayText` circle and edge with a `Canvas` dot checked. So the checked state, which would otherwise vanish into the forced `Canvas`, still shows, as [Accessibility](../foundations/accessibility.md#what-a-person-checks) asks.
- **CR-12.** RadioGroup declares no `description` or `error` prop and renders no Field of its own, Perron's or Base UI's. A hint or an error comes from a Base UI `Field.Root` the caller puts round the group, with `Field.Description` and `Field.Error` and no `Field.Label`, as the `Invalid` story does: inside it the group keeps its legend as its name and each radio its own words, while Base UI joins the description and the error into each radio's `aria-describedby` and marks each radio invalid. No story and no example wraps the group in Perron's [Field](field.md), whose `Field.Label` would become the `aria-labelledby` of the group and of every radio.

## Do and don't

For a caller using the component, with the reason.

| Do                                                                                                                                            | Don't                                                                                                                                                                 |
| --------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Use a RadioGroup for one answer of two to six that a person reads in full before choosing, such as the theme or the language                  | Use it for more choices than fit a panel, or for choices that need a search: a select or a search field keeps a long list out of the way                              |
| Switch how one view shows its content with a [SegmentedControl](segmented-control.md), and filter the map with a [FilterChip](filter-chip.md) | Use a row of radios for a view's mode or the top bar's filters: a radio is a form answer, read down a column                                                          |
| Name the group with `label`, in sentence case, a word or a short question: "Theme"                                                            | Leave out the label, or name the group with `aria-label` where there is room to show one: a sighted person can't tell what an unnamed set of choices answers          |
| Write each radio's words as a short noun phrase in sentence case, of a similar length and shape: "Match the system", "Light", "Dark"          | Put a link or a button inside a radio's words: a radio's content is presentational, so a screen reader never reaches it, and a click on it checks the radio too       |
| Check the safest or most common choice with `defaultValue`, or leave all unchecked with `required` when the person must decide                | Check a choice the person never made and then treat it as their answer: a pre-checked radio is easy to pass by                                                        |
| Disable the whole group with `disabled`, or one radio that can't be chosen now, and say why in the label or the Field's description           | Disable a radio with no word of why, or hide it: a dimmed choice can't explain itself, and a missing one moves the others                                             |
| Give a hint or an error through Base UI's `Field.Root` round the group, with `Field.Description` and `Field.Error` and no `Field.Label`       | Put a hint or an error as plain text among the radios: nothing ties it to the group for the ear, and the arrow keys never reach it                                    |
| Name the group with its own `label`                                                                                                           | Wrap the group in Perron's [Field](field.md): its label renames the group and every radio in it, so each radio is heard as the field's label, never its own words     |
| Use a checkbox for a choice that can be on or off on its own, or several at once                                                              | Use a RadioGroup of one radio, or of "Yes" and "No" for a setting that takes effect at once: one radio can't be unchecked, and a setting that applies now is a switch |
