# Toast

A short message that floats in at the bottom of the screen to confirm what just happened, such as "Link copied", in Alert's look and intents, and leaves again on its own after a few seconds, with an optional title, an action and a close button.

## Anatomy

Penpot page `Components/Toast`. Family: none, as Alert's: a toast is an Alert that floats, and joins no family's treatment (its glass-free tinted surface is Alert's, not the Popups'). Shared parts: `IntentIcon`, Alert's, for the intent's icon; `CloseButton`, and `VisuallyHidden` through it.

The drawing has Alert's one variant property, `color`, with the values the [Props](#props) table gives, so its variants are `Neutral`, `Success`, `Warning`, `Danger` and `Info`. There is no `State` property: the toast takes focus but has no pressed look of its own, its focus ring is the one `perron.css` draws, and its close button keeps the `CloseButton` part's states.

A toast does not render where the caller writes it. Base UI keeps every toast of an app in one list, in a provider, and renders them in one region, its viewport, so they stack and share one live region and one F6 stop.

Toast is declarative, `<Toast open={copied} onClose={() => setCopied(false)} color="success" title="Link copied" />`: it adds itself to Base UI's list when `open` turns true and leaves it when `open` turns false, rather than being an imperative `useToast().add({ … })` beside a toast region the caller places. The contract's `open`, `defaultOpen` and `onClose(event, reason, details)` and its overlay stories (opened by `defaultOpen`) then hold as they do for Dialog and Tooltip, every option is a prop the docs page's props table lists and the `docs` and `props` gates check, the props are Alert's plus what a transient message needs, and an imperative manager could join later as an addition without a break.

`PerronProvider` holds the app's one `Toast.Provider` and renders the one region (`Toast.Portal`, then `Toast.Viewport`, holding every open toast), as it holds `Tooltip.Provider`, while a Toast with no `PerronProvider` around it renders a provider and a region of its own. Toasts from anywhere in the app must stack in one place and be read by one live region, a region already on the page when a toast arrives is announced reliably where one added with it is not (Alert's CR-8), the region is empty and takes no room until a toast arrives, and the fallback lets a Toast render alone, as the contract story renders it; without a provider, two toasts open at once overlap, so the docs page asks for `PerronProvider` at the app's root.

The `viewport`, `portal` and `provider` are shared by every toast inside one `PerronProvider`.

Toast leaves `portal` and `viewport` out of `slotProps`, an exception to the contract's Customising rule of one `slotProps` key per inner Base UI part: one region serves every toast inside a `PerronProvider`, so a `slotProps.viewport` on one toast would restyle, or fight over, every other's region, and the region's one owned word is overridden on `PerronProvider` (see [Owned strings](#owned-strings)); a caller restyles the region through `.pn-Toast-viewport` with the tokens.

The parts from `icon` to `close` are Alert's, with Alert's names, classes under `pn-Toast-`, and Alert's reasons: the title is a `p` and not Base UI's default `<h2>`, made a heading by `slotProps.title.render` (a toast sits at the end of `<body>`, under no heading of its own, and Alert keeps its title a `p` for the same outline reason), and the description is a `div` and not Base UI's `<p>`, so block content such as a list is valid inside it.

The `action` part is a `div` holding the caller's `action`, as Alert's is, so Toast renders no `Toast.Action`, and the build drops `Toast.Action` from the entry's `baseUiParts`: `Toast.Action` renders a `<button>` of its own from Base UI's `actionProps`, so a Perron Button inside it would nest a button in a button, Alert's `action` is a caller's control such as a Button or a LinkButton, and Base UI's own swipe already ignores a press that starts on a `button` or an `a`, so a `div` loses nothing.

## Props

In MUI's layout, as MUI's Snackbar and Alert take them: Alert's props, `open`, `defaultOpen` and `onClose` as the contract shapes them, and the auto-hide time. Every prop Toast declares gets this description as its JSDoc; `swipeDirection`, `render`, `className` and `style` are inherited from `Toast.Root` with Base UI's. Slots come last.

Toast has no `onOpen`: no press of the person's opens a toast, only the caller's `open`, so Base UI never asks to open one. Base UI's `priority` is left out: every toast is polite, read by the region as it arrives, and never interrupts (CR-4).

The time before a toast hides itself is `autoHideDuration`, MUI's name and type (`number | null`, in milliseconds, `null` for never), mapped to Base UI's `timeout` (`null` as `0`): MUI's Snackbar names it so, ADR 0001 shapes props as MUI's, `timeout` reads as a failure in a transit app, and `null` says "never" where Base UI's `0` reads as "at once".

`autoHideDuration`'s default is 5000 ms, Base UI's own, and `null` when the toast has an `action`, so a toast that offers something to do stays until it is closed: five seconds reads a short sentence twice, and the timer pauses while the pointer or the keyboard is in the region; but a toast's action that leaves on a timer is a time limit on that action (WCAG 2.2.1), which a person on a screen reader, still hearing the toast, can miss; a caller that wants an action toast to leave gives `autoHideDuration` itself.

A Toast shows each time `open` turns true and leaves when `open` turns false without calling `onClose`; once it closes itself (its timer, a swipe, Esc or its close button), it calls `onClose` and stays closed until `open` turns false and true again. Base UI's list, not Toast, closes a toast that hides itself, and no Toast can hold it open, so `onClose` reports the close and the caller sets `open` to `false` there, as MUI's Snackbar asks; a Toast that keeps `open` true after it closed would otherwise have no edge to show again on.

`onClose` is called as `onClose(event, reason, details)` with the reason `'close-press'`, `'escape-key'` or `'swipe'`, Base UI's names, or `'timeout'`, MUI's Snackbar's name for a toast that hid itself; `details` is `{ reason, event }` and `event` the press's, the key's or the pointer's native event, or a new `Event('timeout')` for a timer. Base UI's toast calls its `onClose` with no arguments, so Toast tells the reasons apart itself (CR-6), and the contract's shape needs an `event`; this is an exception to the contract's State and events rule, which passes Base UI's details unchanged, since Base UI gives a toast's close none; Base UI cannot cancel a toast's close, so `details` has no `cancel()`.

## Tokens

One row per part, state and property. The toast's own rows are Alert's, at rest, each naming the `data-color` it applies to, with the floating panel's shadow added and the transitions a message that comes and goes needs; the close button's hover and pressed rows are the `CloseButton` part's, and the action's controls keep their own states. Every `.pn-Alert…` value in Alert's Tokens table is the same value here under `.pn-Toast…`.

The toasts stand in one column at the bottom of the screen, centred, `size.panel-gap` above the bottom edge, `space.200` apart, the newest at the top of the column, so a new toast appears above those already there and none of them moves (CR-8). The column is as wide as the smaller of the toast width and the screen less `size.panel-gap` at each side. `shadow.panel` is the shadow [Elevation](../foundations/elevation.md#shadows) gives every floating panel, and `z-index.dialog` the stacking the contract gives everything in a portal.

The toasts stand in one column, every one in full, rather than Base UI's demo's collapsed pile (the toasts behind the newest peeking out, smaller, until the pointer or the keyboard spreads them): Base UI's `limit` keeps at most three, a pile hides two of them from anyone who doesn't hover or press F6, a column reads calmly and in order, and it needs none of Base UI's offset variables, only a flex column.

The column sits at the bottom of the screen, centred: on a wide screen the bottom centre is open map between the overview sheet on the start side and the detail panel on the end side, a toast at the top would cover the top bar's brand, filters and clock, and Base UI's default swipe, down and to the right, suits a toast at the bottom; on a phone it covers the top of the bottom sheet for a few seconds, above it by `z-index.dialog`.

The toast column's width is a new token, `size.toast-width`, 360px, "Toast width on wide screens", added through the `design-tokens` skill: `size.dialog-width` (440px) is a dialog's and wider than a few words need, `size.detail-width` (364px) is the detail panel's, and Base UI's demo sets 360px.

A toast moves as it comes and goes, sliding up from below its place and fading in, and sliding down and fading out, or out in the direction of its swipe, on a new `duration.toast` of 200ms, added through the `design-tokens` skill, with `easing.standard`, which reduced motion takes to 0.01ms as it does every transition token: [Motion](../foundations/motion.md) says motion explains a change of place, and a toast that appears from nothing at the screen's edge is easy to miss; no duration token fits (`duration.sheet`, 320ms, is the sheet's longer slide); and the token's reduced-motion value stops the slide where the system asks, with no rule of Toast's own. The swipe itself follows the pointer with no transition.

Base UI's starting, ending, swiping and limited states, which its `Toast.Root` produces and the contract's design states don't name, have rows below as the answers to the column and motion questions above give them; their selectors are Base UI's attributes.

From the Base UI reference and its source, `node_modules/@base-ui/react/toast/`. Every key below works while at least one toast is open; with none, the region takes no keys.

A toast is read as it arrives because the region is a polite live region already on the page (CR-2): its title, its sentences, its action's names and "Close", in that order. It interrupts nothing. Toast adds no hidden word for its intent, as Alert adds none: the caller's words say what the colour and the icon show.

With no `title`, the toast is named by its description, the root's `aria-labelledby` pointing at the description and its `aria-describedby` left off: a `dialog` with no name fails axe's `aria-dialog-name` rule, which the stories run in error mode, a toast such as "Link copied." often has a sentence and no title, and naming it by the sentence and not describing it by the same sentence reads it once.

The close button is never `aria-hidden`, where Base UI's `Toast.Close` hides it from screen readers while the region is neither hovered nor holding focus: Toast sets `aria-hidden={false}` after Base UI's, since a focusable button inside `aria-hidden` fails axe's `aria-hidden-focus` rule, which the stories run in error mode, and a person reading the region with a screen reader, without F6, must find the button that closes a toast that stays; the cost is "Close" read after each toast's words as it arrives.

What axe won't catch, from the contract, each with how this component meets it:

- [ ] Everything the eye is told, the ear is told, for every shape each prop accepts: the colour, the tint and the icon repeat what the caller's words say, and the icon is `aria-hidden`; the `color` JSDoc asks for words that say the intent, as Alert's does. A toast that hides itself is read by the region as it arrives, so the ear hears it even where the eye looks elsewhere; one that leaves before it is read pauses while focus or the pointer is in the region.
- [ ] Every landmark and named region has an accessible name: the region is named "Notifications" from the locale, or `PerronProvider`'s `notificationsLabel` (CR-3); each toast, a `dialog`, by its title or its description (CR-9).
- [ ] Every default label can be overridden: `closeLabel` on each Toast, `notificationsLabel` on `PerronProvider` for the shared region.
- [ ] Every shape the type accepts renders, in every variant: `title`, `children`, `icon` and `action` each render a string, an element and an array, as Alert's do; `icon` as `null` or `false` renders no icon part.
- [ ] A hidden copy kept for animation is `aria-hidden`, and a collapsed region is `inert`: a toast past Base UI's `limit` is `inert` and not displayed; a leaving toast is gone from the list once its transition ends, and Toast keeps no copy of its own.
- [ ] Native semantics first: Base UI's `region` and `dialog` roles, a `p` for the title, a native `<button type="button">` to close, the caller's own `button` or `a href` in the action; Toast adds `aria-labelledby` when there is no title (CR-9) and `aria-hidden="false"` on the close button (CR-7), and no other ARIA.
- [ ] Focus moves in reading order and returns on close: a toast never takes focus when it arrives; F6 reaches the region, Tab walks the toasts from the top, as they stand, newest first, and inside each its action, then its close button, as on screen; closing a focused toast moves focus to the next toast, or back to where it was before F6 (Base UI).
- [ ] Every target is at least `size.target-min` square: the close button is `size.control`, 34 px; the action's targets are the caller's components, a small Button `size.button-sm`.
- [ ] Loops stop when the system asks for less motion: none here; the slide in and out is a transition on `duration.toast`, which the token's reduced-motion value takes to 0.01 ms.

## Component rules

Rules for this component alone, numbered so the build and the review can cite them.

- **CR-1.** Toast takes Alert's parts, look and decisions whole, by Alert's CR-12: its props `color`, `title`, `children`, `icon`, `action` and `closeLabel` mean what Alert's mean, with Alert's JSDoc; its `icon`, `content`, `title`, `description`, `action` and `close` parts are Alert's, built the same way, with Alert's CR-1 (`data-color` written after the caller's, every colour read from it), CR-3 (the optional parts render only when given, and the icon part by the same test), CR-4 (the intent's icon is the `IntentIcon` shared part), CR-5 (the icon part's `aria-hidden` after the caller's), CR-9 (long words wrap) and CR-10 (the transparent edge for forced colours). Toast's CSS writes Alert's values again under `.pn-Toast…`: a component's CSS reads no other component's classes. Toast differs from Alert only where a transient toast must: it floats in a shared region, closes itself, swipes, stacks, pauses and moves, as the rules below say.
- **CR-2.** `PerronProvider` (`packages/perron/src/PerronProvider.tsx`) renders one `Toast.Provider` around its children, inside its locale context, and beside them `Toast.Portal` holding `Toast.Viewport`, which renders every toast in the provider's list, newest first, in the list's order (`Toast.useToastManager().toasts`). That region, a component internal to Toast's folder and not exported from the barrel, imports `Toast.css`; Toast's folder holds every `pn-Toast` class. A Toast reads, through a context of Perron's own, whether a `PerronProvider` is around it; with none, it renders a `Toast.Provider` and the same region of its own around itself.
- **CR-3.** The region's `aria-label` is `useOwnedStrings({ notifications: notificationsLabel }).notifications`, the new key `notifications` in all four locale files, with `PerronProvider`'s new optional prop `notificationsLabel` (`string`, JSDoc "Overrides "Notifications", the name of the region that holds the toasts", `@default The locale's`). Base UI's English "Notifications" never reaches the page.
- **CR-4.** Toast passes no `priority` and no `type` to Base UI: every toast is `'low'`, polite, read by the region as it arrives. Base UI's `'high'` makes a toast's root `aria-hidden` while it is in the tab order, which axe's `aria-hidden-focus` fails, and copies its words into an `alert` that interrupts; a failure that must interrupt is an AlertDialog, or an Alert with `role="alert"` in the page. A `priority` prop can join later without a break.
- **CR-5.** A Toast renders nothing where it is written. When it opens (`open` turns `true`, or it mounts with `open` `true` or `defaultOpen`), it adds itself to the provider's list with an id from React's `useId`, its `timeout` (`autoHideDuration`, `null` as `0`, and `null` by default when `action` is given), an `onClose` of its own (CR-6), its `title` and `children` as Base UI's `title` and `description`, and its props as the toast's `data`; while open, it updates that toast's `data` when its props change; when `open` turns `false`, or it unmounts while open, it closes that toast without calling `onClose`. It reaches the list through `Toast.useToastManager()` in an internal child that re-renders with the list, never through `Toast.createToastManager()`, whose events `Toast.Provider` subscribes to only after its children's effects have run, so a toast open at first render would be lost; and its own render, which re-renders on every change of its props, never reads the list, so an update to the list never loops back into another. The region renders each toast's parts from its `data`: `Toast.Root` with the caller's `ref`, `className`, `style`, `render`, `swipeDirection` and rest props, and the parts of CR-1 inside it.
- **CR-6.** `onClose` is called only when the toast closes itself, as `onClose(event, reason, { reason, event })`. Base UI calls the toast's own `onClose` with no arguments, so Toast records the reason first, in its handlers on the parts it renders: `'close-press'` in the close button's `onClick`, with the click's native event; `'escape-key'` in the root's `onKeyDown` for Escape, with the key's; `'swipe'` in the root's pointer handlers once the root has `data-swiping`, with the pointer's; and, with none recorded, `'timeout'`, with `new Event('timeout')`. A close Toast makes itself (CR-5) calls no `onClose`. Toast never shows a toast again that closed itself while `open` stayed `true`: it shows again when `open` turns `false` and then `true`.
- **CR-7.** The close button is the `CloseButton` shared part, rendered through `Toast.Close`'s `render`, `<Toast.Close render={<CloseButton label={strings.close} />} />` with `const strings = useOwnedStrings({ close: closeLabel })`, always, so a toast that stays can be closed by touch and by a screen reader. It is never disabled: `slotProps.close` is typed `Omit<Toast.Close.Props, 'children' | 'disabled'>` and Toast passes no `disabled`. It is never `aria-hidden`: Toast sets `aria-hidden={false}` after Base UI's own, which hides it while the region is neither hovered nor focused. Its props are merged with `mergeProps`, Toast's own last, so its class and handler stay while the caller's join; Toast's CSS sets only its two margins.
- **CR-8.** The region is a flex column at the bottom of the screen, centred, the newest toast at the top, so the list's order, the DOM order, the tab order and the order on screen agree, and a new toast appears above the others without moving them. Toast styles none of Base UI's pile: no `--toast-index` scale, no `--toast-offset-y`, no `--toast-frontmost-height`, and `Toast.Content`'s `data-behind` hides nothing. A toast past Base UI's `limit` of 3 is `display: none`, as well as `inert`.
- **CR-9.** With no `title`, the root's `aria-labelledby` is the description's `id` and its `aria-describedby` is left off, set after Base UI's, so the toast is named by its sentence and reads it once; with neither `title` nor `children`, the root keeps Base UI's attributes, and the stories never render one.
- **CR-10.** The toast takes the region's width, not its content's, and long words wrap (`overflow-wrap: anywhere` on the root, the title and the description, `min-inline-size: 0` on the content), so a long Danish word fits a 320 px screen and the close button stays at the row's end.
- **CR-11.** The root's `translate` and `opacity` move on `duration.toast` with `easing.standard`: from `0 100%` and `0` at `[data-starting-style]`, to `0 100%` and `0` at `[data-ending-style]`, or `100%` further in the swipe's direction after a swipe; while `[data-swiping]` it has no transition, and its `translate` is Base UI's `--toast-swipe-movement-x` and `-y`. Base UI waits for the transition to end before it takes a toast out of the list, so the token's reduced-motion value, 0.01 ms, takes it out at once. Nothing loops.
- **CR-12.** `color`, `title`, `children`, `icon`, `action`, `open`, `defaultOpen`, `onClose`, `autoHideDuration`, `closeLabel` and `slotProps` are taken out of the rest props before they reach the root, so the HTML `title` attribute never reaches the element; `swipeDirection`, `render`, `className`, `style`, `ref` and the rest reach `Toast.Root`, `className` merged after `pn-Toast`. Each inner part's props are its `slotProps` value merged with `mergeProps`, the component's own props last.
- **CR-13.** The portal renders nothing on the server, so the contract story's owned-strings check, which renders to static markup, sees nothing of a toast. Toast's own stories check the open toast's and the region's words in the live DOM: `expectOwnedStrings(region.outerHTML, locale, callerWords)` in English, and in Danish with no override.
- **CR-14.** The stories' meta sets `parameters: { docs: { story: { inline: false, height: '480px' } } }`, as the contract's [Stories](README.md#stories) asks of an overlay, so each story renders in its own frame and its fixed region sits at that frame's bottom. Each story shows its toast at first render with `autoHideDuration={null}`, so the docs page and the audits see it and it does not leave while they look; the subject story's args set `defaultOpen`, and each story's render keeps `open` in its own state, starting from `defaultOpen`, beside a Button that shows the toast again. A behaviour that needs a toast that hides itself, a timer or a toast past the limit is mounted beside the story in its `play`, with `mounted`.

## Do and don't

For a caller using the component, with the reason.

| Do                                                                                                                                                            | Don't                                                                                                                                     |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| Confirm what just happened, in a few words: "Link copied", "Filters cleared"                                                                                  | Write "Success!" or "Something went wrong": content design has no exclamation marks, and the words should say what happened               |
| Keep the app inside one `PerronProvider`, so every toast stacks in one region at the bottom of the screen and is read by one live region                      | Render Toasts with no provider: each gets a region of its own, and two at once overlap                                                    |
| Set `open` to `false` in `onClose`, so the next `true` shows the toast again                                                                                  | Leave `open` `true` after the toast has closed itself: it doesn't show again until `open` turns `false` and `true`                        |
| Give a toast an action only for what can't wait, such as "Undo", and let it stay until it is closed                                                           | Give an action toast a short `autoHideDuration`: a person still hearing the toast can miss the action, and it may be the only way to undo |
| Put an app-wide context an action needs, such as a router's, around `PerronProvider`: the toast renders in `PerronProvider`'s region, not where it is written | Rely on a context between `PerronProvider` and the Toast in the action: the region renders outside it                                     |
| Show a message that must stay while its cause lasts, such as a signal fault, as an Alert in the panel                                                         | Use a toast for something the person needs later: it leaves after five seconds                                                            |
| Use an AlertDialog for a failure that must stop the task                                                                                                      | Use a toast to interrupt: every toast is polite, and waits for the screen reader to finish                                                |
