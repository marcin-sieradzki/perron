# Dialog

A modal panel over the map and a `color.scrim` backdrop, such as the help with the keys or a question before clearing every filter, which holds focus until it closes and then gives it back to the button that opened it.

The design is deferred (ADR 0010, `docs/adr/0010-unattended-runs-with-design-deferred.md`): there is no read-back, code map or export, and this spec decides what the drawing would, from the contract, the foundations, the tokens and the Base UI reference. The extracted prototype component is not in any branch this run can reach. The `CloseButton` shared part gives the close button its look, as the Sheet build (branch `component/sheet`) draws it, and the [Button](button.md) spec the trigger and the actions in the stories.

## Anatomy

Penpot page `Components/Dialog`. Family: Panels (the contract's [Families](README.md#families): a dialog is a panel, glass like the Popups, over `color.scrim` when modal, `radius.xl`). Shared parts: `CloseButton`, which the contract's [Shared parts](README.md#shared-parts) table composes in `Dialog.Close`.

Dialog is one component that takes its words and controls as props, `title`, `description`, `children`, `actions` and `trigger`, and renders every Base UI part itself, with the popup as its root, the element `ref`, `className`, `style` and the rest props reach: the registry gives Dialog one entry for all eight parts, `Dialog.Root` renders no element of its own, and the popup is the one element a caller would style or measure, while a compound would need the Toolbar spec's exception to "one component per folder" with no part a caller needs to place.

The close button is the `CloseButton` shared part, rendered through `Dialog.Close`'s `render`, its `label` the dialog's owned "Close" or `closeLabel`. When its folder, `CloseButton/` under `packages/perron/src/parts/` (`CloseButton.tsx` and `CloseButton.css`), does not exist on `main` yet, the Dialog build adds it exactly as the Sheet build (branch `component/sheet`) draws it, file for file: a `<button>` in a `size.control` square with `radius.md`, the `close` icon at `icon.size.400` in `color.text.secondary`, `color.text.primary` on `color.surface.hover`, `color.surface.selected` while pressed, its label in the `VisuallyHidden` part. Dialog takes no dependency on IconButton: one part, drawn once, serves Dialog, Sheet, Popover and Toast, and whichever of Dialog and Sheet merges second finds the same files.

Base UI already does: it opens the dialog on a press of `Dialog.Trigger` and gives the trigger `aria-haspopup="dialog"`, `aria-expanded` and `aria-controls`; it portals the backdrop and the popup to `<body>`, and renders nothing there, on the server or the client, while the dialog is closed, unless the portal's `keepMounted` is set; it names the popup from `Dialog.Title` and describes it from `Dialog.Description` through ids it generates; when the dialog opens it moves focus to the first tabbable element in the popup, or to the popup itself when opened by touch, so no virtual keyboard opens, unless `initialFocus` says otherwise; while a modal dialog is open it traps focus in the popup, so Tab and Shift+Tab wrap inside it, hides everything outside it from assistive technology with `aria-hidden`, blocks the pointer outside it and locks the page's scroll; Esc closes the topmost dialog only; a press outside the popup, on the backdrop, closes it; `Dialog.Close` closes it; on close it returns focus to the trigger, or to the element focused before it opened, unless `finalFocus` says otherwise; it reports each change with its reason (`trigger-press`, `outside-press`, `escape-key`, `close-press`, `focus-out`, `imperative-action`, `none`) and a `cancel()` that keeps the dialog as it is; a dialog opened inside another's popup is nested: Base UI marks both with `data-nested` and `data-nested-dialog-open` and renders no second backdrop unless its `forceRender` is set.

## Props

In MUI's layout, as MUI's Dialog takes `open` and `onClose`, with the trigger, the words and the actions as props in place of MUI's `DialogTitle`, `DialogContent` and `DialogActions` children. Every prop the component declares gets this description as its JSDoc; the inherited rows keep Base UI's. Slots come last.

Dialog is always modal, and leaves out `Dialog.Root`'s `modal`, `disablePointerDismissal`, `actionsRef`, `handle`, `onOpenChangeComplete`, `triggerId` and `defaultTriggerId` (the last two set by Dialog itself from the trigger, CR-5): [Accessibility](../foundations/accessibility.md#what-a-person-checks) says only an open dialog traps focus and [Layout](../foundations/layout.md#stacking) puts a dialog over a scrim, a panel that leaves the page usable is a popover or a sheet, and no Mylder screen asks for the rest yet; each can join later as a new optional prop, which the contract's [Change](README.md#change) rule allows.

An action that closes the dialog, such as "Cancel" or the confirming button, closes it by the caller's controlled `open`, setting it to `false` in the action's `onClick`, and no `DialogClose` component is exported for the actions: the actions are the caller's Buttons, a pattern may not import Base UI's `Dialog.Close` (the contract's [Patterns](README.md#patterns)), and a second exported component would need a spec and a registry entry of its own for one behaviour the `open` prop already gives.

## Tokens

One row per part, state and property. States are the contract's design states: rest is no selector, open is `[data-open]` on the backdrop and the popup, hover is `:hover` inside `@media (hover: hover)`, pressed is `:active`, focus is `:focus-visible`. The trigger is the caller's element and keeps its own tokens in every state, open included: Dialog styles no `[data-popup-open]`. The portal is never seen and has no tokens.

The popup takes the Panels family's treatment ([Families](README.md#families)): the Popups' glass, `color.surface.overlay` with a `backdrop-filter` of `effect.glass-blur` and `effect.glass-saturate` and `shadow.panel`, a `border.width.025` edge in `color.border.subtle`, and `radius.xl`, over the `color.scrim` backdrop. [Elevation](../foundations/elevation.md#surfaces) gives text-heavy panels on phones an opaque `color.surface.default`, but a component sizes to its container and has no width query ([Media queries](README.md#media-queries)), and the scrim and the blur already stand between the dialog's text and the moving map.

The popup is at most 440 px wide, written in `Dialog.css` as a raw length with a `perron-allow(component-css)` comment that gives the reason, rather than a new `size.dialog-width` token, and never wider than the viewport less `size.panel-gap` at each side: [Layout](../foundations/layout.md#other-layout-properties) and the `design-tokens` skill keep a measure only one component's CSS reads in that CSS, and 440 px less the `space.600` padding holds about 60 characters of `typography.body` a line, while a 320 px screen gets a 296 px dialog.

The popup is padded `space.600`, its parts `space.300` apart, with the actions a further `space.300` from the content (`space.600` in all, the distance between blocks), end-aligned and `space.200` apart, wrapping; the title is in `typography.heading-lg`, the description in `typography.body-sm` in `color.text.secondary`, the content in `typography.body`; the close button is pulled `space.100` up and `space.200` towards the end, so its icon lines up with the title's first line and the padding's edge; and the popup is at most the viewport's height less `size.panel-gap` at each end, scrolling as a whole, header included: [Semantic spacing](../foundations/semantic-spacing.md) sets a panel's parts 12 px apart and its blocks 24 px, [Typography](../foundations/typography.md) gives `heading-lg` to dialog titles and `body-sm` to "the line under a title", and a popup that scrolls as one keeps its close button, the first tabbable element, inside the scrolling region, which axe's `scrollable-region-focusable` rule asks for.

Highlighted, selected, invalid and disabled don't apply to the dialog: it holds no rows, no choice and no value, and Base UI gives `Dialog.Popup` no disabled state.

Base UI's `Dialog.Close` takes `disabled`, a state the `CloseButton` part, drawn file for file as the Sheet build draws it, gives no look. Dialog leaves `disabled` out of `slotProps.close` (typed `Omit<Dialog.Close.Props, 'disabled'>`), so its close button is never disabled: the close button is always rendered so touch screen readers can leave the modal dialog (CR-6), a disabled one would shut them in while Esc and the backdrop still close it, and the shared part then needs no disabled look; a dialog that must stay open cancels the close in `onClose` with `details.cancel()`.

Base UI marks a dialog opened from inside another's popup `data-nested`, and the one beneath it `data-nested-dialog-open`, which the deferred design doesn't show. Both keep the rest look, the nested popup painting over the first at the same `z-index.dialog` with no second scrim, Base UI's default: no Mylder screen opens a dialog from a dialog, and a stacked look, such as the one beneath shrinking, needs motion no `duration.*` token gives.

What axe won't catch, from the contract, each with how this component meets it:

- [ ] Everything the eye is told, the ear is told, for every shape each prop accepts: the dialog is announced with its `title` as its name and its `description`, the close button's `aria-hidden` icon has the owned "Close" as its text, and the scrim only dims what the `aria-hidden` outside the popup already removes.
- [ ] Every landmark and named region has an accessible name: the dialog is named by its own heading, the `title`, through `aria-labelledby`, and `title` is required.
- [ ] Every default label can be overridden: `closeLabel`.
- [ ] Every shape the type accepts renders, in every variant: `title`, `description`, `children` and `actions` render a string, an element and a list alike; a long word in the title or the description wraps (CR-9).
- [ ] A hidden copy kept for animation is `aria-hidden`, and a collapsed region is `inert`: none here; the closed dialog renders nothing, and Base UI hides the page behind the open one with `aria-hidden`.
- [ ] Native semantics first: Base UI's `dialog` role, a native `<h2>` for the title, native `<button>`s for the trigger and the close button, and no ARIA of Perron's own.
- [ ] Focus moves in reading order and returns on close: the header comes first in the DOM, then the description, the content and the actions, as on screen; opening moves focus into the popup and closing, by any reason, returns it to the trigger, also for a dialog open at first render (CR-5).
- [ ] Every target is at least `size.target-min` square: the close button, `size.control` (34 px) square.
- [ ] Loops stop when the system asks for less motion: none here; the dialog has no loop and no transition (CR-10).

`close` is the key `packages/perron/src/locale/en.ts` already has, "A button that closes a dialog, panel or notice", so Dialog adds no key. Every other word is the caller's, through `title`, `description`, `children`, `actions` and `trigger`.

## Component rules

Rules for this component alone, numbered so the build and the review can cite them.

- **CR-1.** Base UI's dialog already gives the focus trap, the initial focus, the focus return, Esc, the outside press, the scroll lock, the `aria-hidden` on the page behind and the popup's name and description, so the component rebuilds none of it and adds no key or pointer handlers.
- **CR-2.** Dialog renders `Dialog.Root` around `Dialog.Trigger` (only when `trigger` is given, with `render={trigger}`) and `Dialog.Portal`, which holds `Dialog.Backdrop` and then `Dialog.Popup`. The popup holds, in this order: the header (`Dialog.Title`, then `Dialog.Close`), `Dialog.Description` when `description` is given, the content when `children` is given, and the actions when `actions` is given. The DOM order is the reading order and the order on screen.
- **CR-3.** `{...rest}` reaches `Dialog.Popup` before Dialog's own attributes, and Dialog's own props are taken out of `rest` first (`title`, `description`, `children`, `actions`, `trigger`, `open`, `defaultOpen`, `onOpen`, `onClose`, `closeLabel`, `slotProps`), so none reaches the DOM; `initialFocus`, `finalFocus` and `render` stay in `rest`, keeping Base UI's defaults. `ref`, `style` and `data-testid` land on the popup, and `className` is merged after `pn-Dialog`. Each `slotProps` value is merged with Base UI's `mergeProps` (`@base-ui/react/merge-props`), Dialog's own props last, so a caller's class sits beside the part's `pn-Dialog-<part>`.
- **CR-4.** Dialog turns Base UI's `onOpenChange(open, details)` into `onOpen(details.event, details)` when `open` is `true` and `onClose(details.event, details.reason, details)` when it is `false`, and exposes neither `onOpenChange` nor Base UI's `modal`.
- **CR-5.** When `trigger` is given, Dialog gives `Dialog.Trigger` an id (the `slotProps.trigger.id`, or one from React's `useId`) and passes it to `Dialog.Root` as `defaultTriggerId`, or as `triggerId` when `open` is set, as the Base UI reference says for a dialog open at first render or controlled, so focus returns to the trigger when such a dialog closes.
- **CR-6.** The close button is always rendered, in a modal dialog as the Base UI reference asks, so touch screen readers can leave the popup: `<Dialog.Close render={<CloseButton label={strings.close} />} />`, with `const strings = useOwnedStrings({ close: closeLabel })`. It is never disabled: `slotProps.close` is typed `Omit<Dialog.Close.Props, 'disabled'>`, and Dialog passes no `disabled` of its own, so the `CloseButton` part needs no disabled look; a dialog that must stay open cancels the close in `onClose` with `details.cancel()`. `CloseButton` is the shared part of the contract's [Shared parts](README.md#shared-parts) table, and only its folder holds `pn-CloseButton` and the `close` icon.
- **CR-7.** The backdrop and the popup are `position: fixed`, the backdrop at `inset: 0`, both at `z-index.dialog`, the popup after the backdrop in the portal so it paints on top. Dialog's CSS never redefines a token: the portal sits outside every themed container but `<body>`.
- **CR-8.** The popup is centred in the viewport (`inset-block-start` and `inset-inline-start` at 50%, `translate: -50% -50%`), as wide as the smaller of 440 px and the viewport less `size.panel-gap` at each side, at most the viewport's height less `size.panel-gap` at each end, and scrolls as a whole (`overflow-y: auto`, `overscroll-behavior: contain`) when its content is taller.
- **CR-9.** The header is a flex row aligned to the start of the block axis, the title growing (`flex: 1`, `min-inline-size: 0`) and the close button keeping its square (`flex: none`). The title and the description have no margin of their own (the browser's `<h2>` and `<p>` margins are reset), the popup's `gap` spacing the parts, and long words wrap (`overflow-wrap: anywhere`), so a long Danish word fits a 320 px screen.
- **CR-10.** The dialog opens and closes at once: no `duration.*` token fits a dialog's entrance, so the CSS has no transition and styles neither `data-starting-style` nor `data-ending-style`.
- **CR-11.** The popup draws its `border.width.025` edge as a border, so Windows' forced colours keep an edge round the dialog when they drop its glass and its shadow.
- **CR-12.** The close button keeps the `CloseButton` part's look and states; Dialog's CSS sets only its margins (Tokens) and never its colours or its size.
- **CR-13.** The portal renders nothing on the server, so the contract story's owned-strings check, which renders to static markup, sees only the trigger. Dialog's own stories check the open popup's words in the live DOM instead: `expectOwnedStrings(popup.outerHTML, locale, callerWords)` in English, and in Danish with no override.
- **CR-14.** The stories' meta sets `parameters: { docs: { story: { inline: false, height: '480px' } } }`, as the contract's [Stories](README.md#stories) asks of an overlay, and each story opens its dialog at first render with `defaultOpen` or `open`, beside the trigger that opens it again.

Dialog's root, the popup, portals to `<body>`, and only after the portal mounts, so it is not inside the story's canvas. Dialog meets the contract story's Root rule with no exception, and the Dialog build doesn't change `storybook/contract/root.tsx` or any other shared check: the check is made portal-aware for every portalled component, Sheet and Popover too, in a change of its own to the shared tooling, which the Dialog branch takes from `main`.

## Do and don't

For a caller using the component, with the reason.

| Do                                                                                                                              | Don't                                                                                                                                           |
| ------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| Give every dialog a short `title` in sentence case, such as "Keys" or "Clear all filters?", which names it for screen readers   | Leave the title empty or hide it: the dialog then has no name                                                                                   |
| Pass the button that opens the dialog as `trigger`, so it is announced as opening a dialog and gets focus back                  | Open a dialog from a button placed beside it with `open` alone, when a `trigger` would do: the button loses `aria-haspopup` and `aria-expanded` |
| Set `slotProps.trigger.nativeButton` to `false` when `trigger` is not a `<button>`, as Base UI warns                            | Pass a link as the trigger for a dialog: a link goes somewhere, and a dialog opens over the screen                                              |
| Keep the description to one sentence, and put lists, steps and controls in `children`                                           | Put block content, such as a list, in `description`: it renders in a `<p>`                                                                      |
| Put the main action last in `actions`, the one `brand` Button, and close the dialog from an action by setting `open` to `false` | Mark more than one action `brand`, or put a second close button in the actions: the header already has one, and Esc closes too                  |
| Use a dialog for a question that must be answered or help that interrupts, kept short                                           | Use a dialog for a vehicle's or a stop's details: they belong in the detail panel beside the map, which leaves the map usable                   |
| Keep a dialog open, such as while it saves, by calling `details.cancel()` in `onClose`                                          | Try to disable the close button: it is never disabled, so touch screen readers can always leave                                                 |
| Leave the close button's label to the locale, or override it with `closeLabel`                                                  | Hide the close button with a `className`: Base UI asks for it in a modal dialog, so touch screen readers can leave                              |
| Let the dialog take `z-index.dialog` and its place in the middle of the screen                                                  | Set a `z-index`, a position or an opacity on the dialog: it would fall under another overlay or leave its scrim                                 |
