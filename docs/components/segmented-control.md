# SegmentedControl

A row of two to five segments on an inset track, one of them selected, that picks how one view shows its content, such as a stop's departures by mode.

The design is deferred (ADR 0010, `docs/adr/0010-unattended-runs-with-design-deferred.md`): there is no read-back, code map or export, and this spec decides what the drawing would, from the contract, the foundations, the tokens, the Base UI reference and the ROADMAP line that names it (`ROADMAP.md`, "Wave 3, interactive, on Base UI": "SegmentedControl (ToggleGroup)"). The extracted prototype component is not in any branch this run can reach. The foundations already name its look: [Elevation](../foundations/elevation.md#surfaces) puts the track on `color.surface.inset` and the selected segment on `color.surface.raised` with `shadow.thumb`, the only shadow outside a floating panel; [Layout](../foundations/layout.md) gives a segment `size.segment`; and [Semantic spacing](../foundations/semantic-spacing.md) gives segments `radius.md`.

## Anatomy

Penpot page `Components/SegmentedControl`. Family: none (the contract's [Families](README.md#families) have no inset track of choices; its surfaces come from [Elevation](../foundations/elevation.md#surfaces)). Shared parts: none (every word is the caller's, and the selected segment is told by `aria-pressed`, not by a hidden word).

The control is written as two components, `SegmentedControl` for the track and `Segment` for each choice, both exported with their props types from `SegmentedControl.tsx`, an exception to the contract's "one component per folder", as Tabs and Toolbar are. Base UI's `Toggle` reads `ToggleGroup`'s context for its pressed state, so a segment can't be shown apart from its control; the caller writes a segment many times, so it is a component of its own; a child component takes a `ReactNode` label where an `options` array would need a shape of its own; and the registry's one entry, with `baseUiParts` `ToggleGroup` and `Toggle`, stays one entry. The `props` check reads both props types, and the `api-compatibility` check only `SegmentedControlProps`, so the review holds `SegmentProps` to the contract's Change rules.

| Part (Penpot layer) | What it is                                                                                                                       | Base UI part  | Class                 | `slotProps` key |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------- | ------------- | --------------------- | --------------- |
| `root`              | `SegmentedControl`: the track, an inline flex row on `color.surface.inset` that holds the caller's `Segment`s and owns the value | `ToggleGroup` | `pn-SegmentedControl` | none            |
| `segment`           | `Segment`: the native `<button>` of one choice, an inline flex row, centred, that holds the caller's `children`                  | `Toggle`      | `pn-Segment`          | none            |
| `focusRing`         | The keyboard focus ring on a segment: the `:focus-visible` outline `perron.css` draws, not an element                            | `Toggle`      | none                  | none            |

`Segment` holds its `children` directly, with no label span: a segment is one line or two of label text, its typography and its long-word rule sit on `.pn-Segment` itself, and a span would be a part with nothing of its own to style.

Base UI already does: one tab stop for the whole group, a roving `tabIndex` that rests on the first enabled segment until another one is focused and then stays where focus last was (not on the selected segment: `ToggleGroup` keeps no link between the two and exposes no `highlightedIndex`); Left and Right move focus between segments, wrapping at the ends while `loopFocus` is on, and Home and End go to the first and the last enabled segment (`enableHomeAndEndKeys` is fixed on in the installed `ToggleGroup`); moving focus doesn't select, and Enter, Space or a click toggles the focused segment; with `multiple` off, pressing one segment unpresses the others; a disabled segment is natively `disabled` (`focusableWhenDisabled` is fixed off in the installed `Toggle`), so it leaves the tab and arrow-key order and ignores clicks; a disabled group disables every segment in it; `aria-pressed` follows the group's value; `onValueChange` passes `details` whose `cancel()` stops both the group's and the toggle's change (the installed `Toggle` checks `details.isCanceled` after the group's handler); Left and Right swap only under Base UI's `DirectionProvider` set to `rtl`, not from the `dir` attribute, and Perron doesn't set one up yet, as all four locales run left to right.

## Props

In MUI's layout. Every prop here gets this description as its JSDoc. Slots come last.

The control holds one choice, its value a `string` rather than Base UI's `string[]`, with Base UI's `multiple` and `orientation` left out, so it only runs horizontally. A segmented control picks one of a few ways to show one view, and FilterChip (on Base UI's `Toggle`, in the same wave) is the on-and-off filter that takes several; a `string` narrows in the caller's `onChange` where a one-item array has to be unpacked; Mylder's controls sit across a panel or a sheet, where a vertical stack of segments would read as a list; and the API only grows, so a later `orientation` costs nothing now.

With neither `value` nor `defaultValue` given, no segment is selected, with no fallback to the first one. Base UI's `ToggleGroup` has no fallback, unlike Tabs, and building one would mean reading the segments' values out of `children`; every story and the Do and don't table give `defaultValue` or `value`, so a control with nothing selected is the caller's choice, such as before a person has picked a mode.

The control takes no `name` and renders no hidden input, so its value never reaches a native `<form>`. Base UI's `ToggleGroup` renders no input to submit, unlike the composite controls the contract's Forms line names; Mylder's segmented controls change how a view shows its content, not what a form sends; and a later `name` with a hidden input only grows the API.

The control takes no `fullWidth`, so it is as wide as its segments' labels, up to its container's width. Tabs takes none for the same reason: a control sized to its labels keeps each segment's target as wide as its word, the API can grow one, and leaving it out keeps the CSS to one layout. A control in a narrow container still fits it (CR-9).

Each segment is a `ReactNode` label and no icon prop: Mylder's segments are words such as "Bus" and "Metro", and an icon-only segment would need a name of its own, so `startIcon` waits until a screen needs it. No `variant`, `size` or `color`: the tokens give one look, an inset track and a raised selected segment at `size.segment`, as the brand keeps colour for the map and the one main action. No `slotProps`: each component renders one Base UI part as its own root. No label-override props: the control owns no strings.

`Segment` leaves out Base UI's `pressed`, `defaultPressed` and `onPressedChange`: inside a group the installed `Toggle` reads its pressed state from the group's value and ignores `pressed`, so the root's `value`, `defaultValue` and `onChange` are the one way in.

## Tokens

One row per part, state and property. States are the contract's design states: rest is no selector, hover is `:hover` inside `@media (hover: hover)`, pressed is `:active`, focus is `:focus-visible`, disabled is `[data-disabled]`, and selected is Base UI's `[data-pressed]` on the segment. The contract's Design states table lists `[data-pressed]` under Pressed, but Base UI's `Toggle` sets it for as long as the toggle is on, which in a segmented control is the selected segment, so here the press itself is `:active` alone. Every `color` row on `segment` sets the segment's `color`, which its label takes.

The track is `radius.lg` with `space.100` padding and a `space.100` gap between segments, each segment `radius.md` with `space.300` inline padding. A segment's `radius.md` plus the track's `space.100` padding is `radius.lg` (8 + 4 = 12 px), so the corners nest, each token used as its description says ("Cards and inset boxes", "segments"); the padding is `focus.offset` plus `focus.width`, so a focused segment's ring reaches the track's edge and no further; the track is 40 px tall, `size.segment` plus the padding; and `space.300` is a tab's inline padding, the label sizing the target as it does there. The other way, a `space.050` padding with `radius.sm` segments, would make the track `size.button` tall but give segments the line badges' radius.

A selected segment that is disabled, alone or with its whole control, keeps its `color.surface.raised` fill and `shadow.thumb`, with only its label turning `color.text.tertiary`. The contract makes disabled a colour, never an opacity, and the choice a disabled control holds is still worth seeing, such as a mode that can't change while the map follows a vehicle; dropping the fill would leave a disabled control showing no choice at all.

What axe won't catch, from the contract, each with how this component meets it:

- [ ] Everything the eye is told, the ear is told, for every shape each prop accepts: the selected segment, which the raised fill and the shadow show, is `aria-pressed="true"` and every other segment `"false"`; a disabled segment's tertiary colour is the native `disabled`, announced as dimmed; a disabled control shows it on each of its segments, which Base UI disables.
- [ ] Every landmark and named region has an accessible name: the control is a `group`, not a landmark, named by the caller's `aria-label` or `aria-labelledby`, which every story sets, so a screen reader says what the choice is about before its segments.
- [ ] Every default label can be overridden: none here; the control owns no strings.
- [ ] Every shape the type accepts renders, in every variant: a segment's `children` render a string, an element and a list alike, the list's nodes `space.150` apart.
- [ ] A hidden copy kept for animation is `aria-hidden`, and a collapsed region is `inert`: none here; the control keeps no copy and collapses nothing.
- [ ] Native semantics first: native `<button>`s from `Toggle`, with `aria-pressed`, in Base UI's `group`, with ARIA from the caller only for the group's name.
- [ ] Focus moves in reading order and returns on close: the arrow keys move through the segments in document order, and Tab leaves the control after its one stop; the control opens and closes nothing, and focus stays on the segment it selects.
- [ ] Every target is at least `size.target-min` square: the smallest target is a segment with a one-letter label, `size.segment` (32 px) tall and its label plus `space.300` on each side (at least 24 px) wide.
- [ ] Loops stop when the system asks for less motion: none here; the control has no loop and no transition.

## Component rules

Rules for this component alone, numbered so the build and the review can cite them.

- **CR-1.** Base UI's toggle group already gives the one tab stop, the roving `tabIndex`, the arrow, Home and End keys, the wrap, the single selection, `aria-pressed` and the disabled segments leaving the key order, so the components rebuild none of it and add no key handlers.
- **CR-2.** `Segment` only renders inside a `SegmentedControl`: outside one, Base UI's `Toggle` is a lone toggle with a pressed state of its own, which no story shows. Every story renders segments in a control, and the `Default` story's args hold a whole control, its `aria-label`, its `defaultValue` and its segments, so the contract story renders it alone.
- **CR-3.** Each of the two takes `{...rest}` before its own attributes and its own props out of `rest` first (`value`, `defaultValue`, `onChange`, `disabled`; an inherited Base UI prop such as `loopFocus` or `nativeButton` stays in `rest`, keeping Base UI's default), and merges `className` after its own `pn-` class; `ref` reaches its one element.
- **CR-4.** `SegmentedControl` adapts between its `string` and Base UI's `string[]` inside itself and exposes neither `onValueChange`, `multiple` nor `orientation`. It passes `value` as `[value]` and `defaultValue` as `[defaultValue]`, each only when given, so a control given neither is uncontrolled with nothing selected. Its `onValueChange(next, details)` calls `details.cancel()` and returns when `next` is empty, the one change Base UI makes when the selected segment is pressed again, so the selection stays and `onChange` isn't called; otherwise it calls `onChange(details.event, next[0], details)`.
- **CR-5.** The states keep the segment's geometry: hover, pressed, focus, selected and disabled change the fill, the shadow and the colour only, never the height, padding, radius, typography or weight, so selecting a segment never moves its neighbours.
- **CR-6.** Hover is read inside `@media (hover: hover)`; pressed (`:active`) takes the hover fill and colour in a rule outside it, so a touch press shows. Neither applies to a selected or a disabled segment: both rules exclude `[data-pressed]` and `[data-disabled]`. Selected is `.pn-Segment[data-pressed]`, one class then attributes.
- **CR-7.** Focus uses the ring `perron.css` draws on `:focus-visible`; the component draws no ring of its own and never removes the outline. The ring sits inside the track's padding (CR-9's container clips nothing).
- **CR-8.** Changes of state are immediate: no `duration.*` token fits a segment's state change or the selected fill's move, so the CSS has no transition, and the raised fill jumps to the selected segment.
- **CR-9.** The control is `display: inline-flex` with `max-inline-size: 100%`, so it is as wide as its segments and never wider than its container. When the labels outrun the container, the segments shrink and each label wraps inside its segment, centred, with `overflow-wrap: anywhere` on `.pn-Segment`, the segment growing taller than `size.segment`, rather than the labels being cut off or the control scrolling sideways. [Accessibility](../foundations/accessibility.md#what-a-person-checks) lets nothing be cut off at 320 px and only the map scroll sideways; a Danish compound is longer than its English word; and a segment that grows keeps every segment on one track, where segments wrapping onto a second row, as tabs do, would read as two controls.
- **CR-10.** In `@media (forced-colors: active)`, where the fill and the shadow are dropped, the selected segment takes `Highlight` with `HighlightText` and a disabled segment `GrayText`, so the selected and disabled states still show, as [Accessibility](../foundations/accessibility.md#what-a-person-checks) asks.
- **CR-11.** The tab stop is Base UI's: the first enabled segment, then the one focused last, not the selected one. The component doesn't move it, since `ToggleGroup` exposes no `highlightedIndex`, and `aria-pressed` tells which segment is selected wherever focus lands.

## Stories

Each story is named by its variant name (`penpot/README.md`, "Conventions"); the segment's are prefixed `Segment`, as `SegmentHover`, beside the control's `Default`, since the conventions name a variant by its property values alone.

Every story names its control with `aria-label` ("Mode"). ## Do and don't

For a caller using the component, with the reason.

| Do                                                                                                                                                     | Don't                                                                                                                                                      |
| ------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Use a SegmentedControl to pick how one view shows its content, such as departures by mode or a chart by day or week                                    | Use it to switch between views of one thing: [Tabs](tabs.md) change which view shows, a segmented control changes how one view shows                       |
| Use it for one choice of two to five                                                                                                                   | Use it for filters that turn on and off apart, or for more than five choices: filter chips take several, and a long row of segments outgrows a phone       |
| Name the control with `aria-label` or `aria-labelledby`, such as "Mode", so a screen reader says what the choice is about                              | Leave the control unnamed: its segments' words alone don't say what they choose between                                                                    |
| Give it a `defaultValue` or a `value`, so one segment is always selected                                                                               | Leave nothing selected without a reason: a control with no raised segment reads as broken                                                                  |
| Keep each label to a word or two, in sentence case: "Bus", "Planned works"                                                                             | Write a sentence in a segment, or rely on a label's colour or an icon alone to say what it chooses                                                         |
| Show a segment whose view is empty, and say so in the view with an [EmptyState](empty-state.md) or a [DataStatePanel](../patterns/data-state-panel.md) | Disable a segment because its view has no data: a disabled segment can't say why, and leaves the key order                                                 |
| Run an action with a [Button](button.md), and group actions in a [Toolbar](toolbar.md)                                                                 | Use a segment as an action or as navigation: pressing one selects it and keeps it selected, and a link to another screen is a [LinkButton](link-button.md) |
