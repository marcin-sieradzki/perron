# Review: Tabs, round 1

## P1

- **P1-1.** `packages/perron/src/components/Tabs/Tabs.tsx:99` `TabsList` spreads `slotProps.indicator` onto `Tabs.Indicator` (`{...indicator}`) and then sets `className` by hand. It does not merge them with `mergeProps` from `@base-ui/react/merge-props`, the component's own props last. That breaks the contract's Customising rule, CR-5 (`docs/components/tabs.md:181`) and the spec's own Base UI parts row (`docs/components/tabs.md:32`), and the rubric counts it as a lost slot. Nothing is lost today, because the only own prop is the class. The fix keeps the class resolved as it is now, takes `className` out of the slot first, and passes the rest through `mergeProps<'span'>(indicator, { className: (state) => ... })`. The comment at lines 95-97 then reads as the reason the class is resolved first, not as the reason `mergeProps` is skipped.

## P2

- **P2-1.** `packages/perron/src/components/Tabs/Tabs.tsx:34` The `onChange` JSDoc, and the Props row it copies (`docs/components/tabs.md:54`), list the change reasons as a click, Enter or Space, or a disabled or removed tab. Two cases are missing. One is the call at mount with `details.reason` `'initial'` when `defaultValue` is left out, which the `Default` story asserts and the spec's prose at `docs/components/tabs.md:46` states. The other is arrow-key selection when `activateOnFocus` is on. A caller reading only the docs page's `onChange` row would not expect a call at mount. Content audit, docs accuracy: the prose at line 46 holds, and the row and the JSDoc should say what it says.
- **P2-2.** `docs/components/tabs.md:181` CR-5 places the indicator "`position: absolute` at the list's block end". CR-11 (`docs/components/tabs.md:187`), the `Wrapping` story row (`docs/components/tabs.md:208`) and the CSS (`packages/perron/src/components/Tabs/Tabs.css:22-31`) instead put the underline under the selected tab on whichever row that tab sits. Rendered in `Wrapping` with "Lines" selected on the first row, the underline sits at y 51-53, not at the list's block end (89). The spec contradicts itself. CR-11 and the code hold, so CR-5's wording should be changed to say the underline sits under the selected tab's row and covers the hairline only on the last row.
- **P2-3.** `packages/perron/src/components/Tabs/Tabs.tsx:73` The JSDoc on `className`, `style` and `ref` of `TabsList` (lines 73-78), `Tab` (lines 124-129) and `TabsPanel` (lines 168-173) says "Reaches the list", "Reaches the tab" and "Reaches the panel". Every sibling says "Reaches the root", as the contract's Props table does, including Toolbar's own part components (`ToolbarButton`, `ToolbarGroup`, `ToolbarSeparator`). The `slotProps` JSDoc at line 79 ("Props for the inner parts, merged with the component's own, which win.") also differs from the siblings' "Props for each inner part, merged with the part's own, which win". This breaks the api-consistency rule that one prop is described the same way in every member. The Props rows at `docs/components/tabs.md:69`, `:84` and `:94` need the same wording.

## P3

- **P3-1.** `docs/components/tabs.md:206` The Stories table gives `Count` as counts of "0, 2 and 12", but the story (`packages/perron/src/components/Tabs/Tabs.stories.tsx:221-236`) renders 12, 0 and 2, in that order. The spec line should match the story.
- **P3-2.** `packages/perron/src/components/Tabs/Tabs.tsx:153` `Tab` draws its own count pill (`pn-Tab-count`, `typography.data-sm` on `color.surface.inset`), while the registry plans a `Count` component (Display, `designing`, Wave 1). A question for the maintainer: should `Tab` compose `Count` once it is built, so every count in the library has one shape, or should the tab's pill stay its own?
- **P3-3.** `packages/perron/src/components/Tabs/Tabs.tsx:133` The four exports mix two naming schemes. `TabsList` and `TabsPanel` follow Base UI and Toolbar's `Toolbar<Part>` prefix, while `Tab` follows MUI, whose own names are `Tab`, `TabList` and `TabPanel`. The next compound component will copy one of these. A question for the maintainer: keep `Tab` beside `TabsList` and `TabsPanel`, or settle on one scheme now, while the API can still change for free?
