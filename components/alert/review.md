## P2

- **P2-1.** `docs/components/alert.md:157` The line opens "The status text and mark tokens reach 4.5:1 on their own tinted surfaces, which the build measures", but that is not true of the mark tokens, and the line contradicts Accessibility (`docs/foundations/accessibility.md:7`), which holds. The build measures only status and brand text on their own tints, and measures `color.status.*` at 3:1 on `default`, `raised` and `inset` only. Measured on the tints, `color.status.success` is 3.68:1 on light `color.surface.success` and `color.status.warning` is 3.85:1 on light `color.surface.warning`. The sentence ships in `packages/perron/data/docs.json`, so a reader who trusts it could set mark tokens as text on a tint and fail 1.4.3. Fix: drop "and mark", or give the mark tokens' measured 3.7:1 floor against the 3:1 non-text rule.

## P3

- **P3-1.** `docs/components/alert.md:122` The icon rows (122 to 125, and `packages/perron/src/components/Alert/Alert.css:57`) draw the intent icon in `color.text.*`. The contract's Intents table (`docs/components/README.md:80`) gives icons the Mark column, `color.status.*`, which measures 3.7:1 or more on each tint here. Question 6 approved the look in the Tokens table, so the maintainer chooses: keep `color.text.*` and give the reason in the spec, or move to the Mark column. Carried from round 1.
- **P3-2.** `packages/perron/src/components/Alert/Alert.css:50` The icon part is `1lh` of `body-sm` (19.5 px), but a title's line is `heading-sm` (18.2 px). In the Danger and Success stories the icon's centre measures 38.75 px against the title line's 38.1 px. So Tokens row `docs/components/alert.md:118` ("the icon sits on the middle of the first line") holds only when there is no title; in Info the two centres match. The gap is under a pixel, but Toast inherits it. Carried from round 1.
- **P3-3.** `packages/perron/src/components/Alert/Alert.css:106` The close button is pulled up `space.200`, so its focus ring's outer edge lands on the alert's 1 px transparent edge. In the Success story, in both themes, the ring's outer edge measures y=17 against the alert's top at 16, so an `overflow: hidden` container would clip it. The pull is part of the approved Tokens table; a smaller pull such as `space.150` is the maintainer's call. Carried from round 1.
- **P3-4.** `docs/components/alert.md:211` CR-6 merges Alert's `onClick` first, so the caller's handler runs first. Base UI's `mergeEventHandlers` (`node_modules/@base-ui/react/merge-props/mergeProps.js:170`) confirms that order. But it goes against the contract's Customising rule, "the component's own props last". Also, `slotProps.close` is typed with React's button props, so `event.preventBaseUIHandler()` is not in the caller's type without a cast. The contract should say which order handlers merge in, and how a close slot's handler is typed when there is no Base UI root. Carried from round 1.
- **P3-5.** `packages/perron/src/parts/IntentIcon/IntentIcon.tsx:18` The contract's Shared parts section says each part is drawn in `<Part>.tsx` and `<Part>.css`. IntentIcon has no `IntentIcon.css`, and its `pn-IntentIcon` class styles nothing. Either the contract allows a part with no CSS, or the class has no job yet. Carried from round 1.
- **P3-6.** `docs/components/alert.md:210` CR-5 ends "so a caller that swaps the icon's element leaves `aria-hidden` off it". That is not what happens. Base UI's `useRender` merges the props in the order `mergeProps(props, render.props)` (`useRenderElement.js:132`), so a plain `render: <span />` keeps `aria-hidden="true"`. Only an element that sets `aria-hidden={false}` itself, or a function `render` that drops the props, takes it off. EmptyState CR-2 and StationIcon CR-3 use the same words, so the shared wording could say "can take `aria-hidden` off it with its own props". Carried from round 2.
