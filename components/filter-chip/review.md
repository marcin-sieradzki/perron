# Review: FilterChip, round 1

## P1

- **P1-1.** `packages/perron/src/components/FilterChip/FilterChip.css:101` In forced colours a disabled selected chip draws exactly like a disabled off chip: both have a GrayText edge and GrayText words on Canvas (components-filterchip--selected-disabled and --disabled, light and dark, `forcedColors: 'active'`), so the selected state disappears. This breaks `docs/foundations/accessibility.md:96` ("the focus ring and the selected state still show") and the accessibility-audit's forced-colours step. CR-11 (`docs/components/filter-chip.md:177`) and the Forced colours row at `docs/components/filter-chip.md:123` say "a disabled chip, on or off, ... take `GrayText`", which contradicts the foundation. The foundation holds, so both spec lines and the CSS need a look for `[data-pressed][data-disabled]` that still shows the chip is on, for example a `GrayText` fill under `forced-color-adjust: none`.

## P2

- **P2-1.** `packages/perron/src/components/FilterChip/FilterChip.css:90` `forced-color-adjust: none` is inherited, so the Count inside a selected chip that is not disabled keeps the theme's colours instead of the system's. In light it stays an `rgb(235, 238, 235)` pill with an ink figure, and in dark an `rgb(40, 50, 55)` pill, both inside the `Highlight` fill (components-filterchip--selected, light and dark, forced colours). This goes against the contract's Media queries rule that forced colours draw in system colours, and the design-qa Token use line. The spec's Forced colours table (`docs/components/filter-chip.md:118`) has no row for the count of a selected chip, and line 125 says the Count keeps its pill "in every state but disabled" without making an exception for forced colours.
- **P2-2.** `packages/perron/src/components/FilterChip/FilterChip.css:103` The forced-colours rule sets `border-color: GrayText` on the Count, but the Count has no border. Its forced-colours edge is an `outline` in `CanvasText` (`packages/perron/src/components/Count/Count.css:57`). So a disabled chip's count keeps a black ring next to the GrayText words and edge (components-filterchip--disabled and --selected-disabled, forced colours). The Tokens row at `docs/components/filter-chip.md:123` names a property that draws nothing, which breaks CR-11's "its count take `GrayText`".
- **P2-3.** `docs/components/filter-chip.md:175` CR-9 says "no other rule reaches inside the Count". But CR-11 (line 177), the Forced colours row (line 123) and `packages/perron/src/components/FilterChip/FilterChip.css:102` all set the count's `color` and `border-color` in forced colours. CR-9 needs to name the forced-colours rule as its exception.
- **P2-4.** `packages/perron/src/components/FilterChip/FilterChip.stories.tsx:83` No `play` test presses Enter. The spec's Keyboard table (`docs/components/filter-chip.md:136`) promises that Enter turns the filter on or off and calls `onChange`. That breaks the contract's Stories rule "A `play` test for every behaviour the component promises (… keyboard)". The Stories row for `Default` (`docs/components/filter-chip.md:189`) also leaves Enter out, so the row and the test both need it. When I pressed Enter in the browser, it did toggle the chip.

## P3

- **P3-1.** `docs/components/filter-chip.md:68` The spec reads Toggle's `[data-pressed]` as the selected state (CR-4). The contract's Design states table (`docs/components/README.md:147`) files `[data-pressed]` under Pressed. The spec is right for Base UI's Toggle, so the contract row is what should change. The brief already raised this, and it is still open for the maintainer.
- **P3-2.** `docs/components/filter-chip.md:206` The label stays the same on and off, and the state reaches the ear only through `aria-pressed`. `docs/foundations/accessibility.md:73` asks that "Toggles say their state in words as well as in looks". No rule settles which side holds for a chip whose label stays the same, so the maintainer decides; the brief raised this too.
- **P3-3.** `packages/perron/src/components/FilterChip/FilterChip.tsx:25` `selected`, `defaultSelected` and `onChange(event, value: boolean, details)` are new names that HighlightChip and Switch will copy. The contract's State and events section names only `value`, and MUI's ToggleButton pairs `selected` with an `onChange` that passes the button's own `value`. The maintainer can either name the boolean case in the contract or keep `value` for every control, as the build note asks.
- **P3-4.** `packages/perron/src/components/FilterChip/FilterChip.tsx:107` The same `count?: number` prop has two looks and two behaviours. FilterChip composes Count and leaves out numbers that are not finite. Tab draws its own `pn-Tab-count` pill and shows `NaN` or `Infinity` as text (`packages/perron/src/components/Tabs/Tabs.tsx:155`). Moving Tab onto Count would give one look and one rule.
- **P3-5.** `docs/components/filter-chip.md:112` The disabled selected chip's `color.surface.inset` fill is the same colour as the Count's pill, so the pill disappears and only the tertiary figure is left (components-filterchip--selected-disabled, light and dark). This is a design question: a different pill for the count when disabled, or a different fill for the chip, as the build note says.
