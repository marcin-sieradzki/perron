# Review: SegmentedControl, round 1

## P1

- **P1-1.** `packages/perron/src/components/SegmentedControl/SegmentedControl.css:24` `.pn-Segment` is `display: inline-flex` and holds the caller's `children` directly, with no label span (spec `docs/components/segmented-control.md:19`). So a label given as text plus an element, such as `<Segment>Data feed <span>problems</span></Segment>`, becomes two flex items. In the 320 px `LongLabels` track they render as two side-by-side columns, "Data / feed" beside "probl / ems", broken mid-word, where they should wrap as one centred label. This breaks CR-9 ("each label wraps inside its segment, centred") and the checklist line "Every shape the type accepts renders … a string, an element and a list alike", which the spec ticks at `docs/components/segmented-control.md:134` although no story renders an element or a list label; the fix wraps `children` in a label part, as `Tab` does with `pn-Tab-label`, and adds a story that shows that shape.

## P2

- **P2-1.** `packages/perron/src/components/SegmentedControl/SegmentedControl.css:32` `padding-block: 0`, and the spec's Tokens table (`docs/components/segmented-control.md:80-105`) gives `segment` no block padding. So in `components-segmentedcontrol--long-labels` (light and dark) a two-line label ("Planned works", "Data feed problems") fills the whole 33.8 px segment, and its ascenders and descenders touch the raised fill's top and bottom edges. This is a crowded part (design-qa Spacing and Polish); a Tokens row such as `space.050` would leave one-line segments at `size.segment`.
- **P2-2.** `packages/perron/src/components/SegmentedControl/SegmentedControl.stories.tsx:12` `rendered` and `:25` `onHover` are a third copy of the helpers already written in `Tabs.stories.tsx:11,24` and `Toolbar.stories.tsx:58,71`. The contract's Shared helpers section says a helper a second component needs joins its table first: here, `packages/perron/src/testing/stories.ts`, imported by all three.

## P3

- **P3-1.** `docs/components/segmented-control.md:11` The spec exports `Segment` from `SegmentedControl.tsx` as "an exception to the contract's 'one component per folder', as Tabs and Toolbar are". The contract's Files rule (`docs/components/README.md:23`) names no such exception, so the maintainer may want to write the compound-component exception into the contract or move the children into folders of their own.
- **P3-2.** `packages/perron/src/components/SegmentedControl/SegmentedControl.css:59-63` The selected segment is told from the rest by `color.surface.raised` on `color.surface.inset`, which measures 1.17:1 in light and 1.20:1 in dark, by a faint `shadow.thumb`, and by text going from secondary to primary (2.26:1 and 1.96:1 between the two). The foundations' Non-text contrast line (`docs/foundations/accessibility.md:8`) asks 3:1 for what shows a state, while Elevation (`docs/foundations/elevation.md:17-18`) names exactly this pairing for the selected segment. The maintainer decides whether the selected segment takes an edge, such as `color.border.control`, or the foundations record the exception.
- **P3-3.** `docs/components/segmented-control.md:159` (CR-11) Base UI's `ToggleGroup` gives a single-choice control `aria-pressed` toggle-button semantics, and its one tab stop rests on the first enabled segment, not the selected one (verified: in `segment-selected`, Tab lands on "All" while "Bus" is pressed). A screen-reader user is not told that the choices exclude each other and must arrow to find the selection. Keeping `ToggleGroup`, as the ROADMAP names it, or moving to radio semantics is the maintainer's call.
- **P3-4.** `packages/perron/src/components/SegmentedControl/SegmentedControl.css:25` With `flex: 1 1 0` and `overflow-wrap: anywhere`, a five-segment Danish control in the 320 px track ("Afgange", "Ankomster", "Forsinkelser", "Aflysninger", "Driftsforstyrrelser") gives every segment an equal 59 px. Every word breaks mid-word ("Afga/nge", "Anko/mste/r"), against the comment at lines 19-22 that a short label keeps its whole width. The spec allows five segments of a word or two (`docs/components/segmented-control.md:186`). Should the spec cap segments by their width in Danish, or accept mid-word breaks as the fallback?
- **P3-5.** `packages/perron/src/components/SegmentedControl/SegmentedControl.css:76` `forced-color-adjust: none` on the selected segment also keeps its `shadow.thumb`, measured under forced colours. CR-10 (`docs/components/segmented-control.md:158`) and the comment at line 72 say the shadow is dropped; `box-shadow: none` in that rule would make both true.
- **P3-6.** `packages/perron/src/components/SegmentedControl/SegmentedControl.tsx:30` `value?: string` gives a controlled caller no way to select nothing except a value no segment has, where its sibling `Tabs` takes `value: string | null`. The spec itself names "before a person has picked a mode" as a reason for nothing selected (`docs/components/segmented-control.md:38`). Should `null` be added now, so the two siblings say "none" the same way?
- **P3-7.** `packages/perron/src/components/SegmentedControl/SegmentedControl.stories.tsx:276` `LongLabels` sets the Danish "Omkørsler" beside two English labels in one control, with no `lang`, so a screen reader reads it with English rules. No screen would show such a control, and none of the three words is longer than its segment, so the long-word case is not exercised. An all-Danish set from content design's table, such as "Problemer med realtidsdata", would test it as a screen would show it.
