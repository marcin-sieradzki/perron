# Review: DataStatePanel, round 1

## P1

- **P1-1.** `packages/perron/src/patterns/DataStatePanel/DataStatePanel.tsx:133` CR-6 says DataStatePanel "never moves focus otherwise", but the code does. If the focused element in the message part goes away without a status change, `focused.current` keeps the detached node, and the next change of `status` moves focus into the message part even though focus was then on the page's body. Reproduced on the Empty story: focus "Clear filters", replace `action` while `status` stays `'empty'`, click the page, then set `status` to `'loading'`, and focus lands on `pn-DataStatePanel-message`. The fix is to forget a disconnected element when no status change removed it, for example by recording the `status` at focus time.

## P2

- **P2-1.** `packages/perron/src/patterns/DataStatePanel/DataStatePanel.stories.tsx:111` The Error story's `play` test ends in the loading status, with focus and a focus ring on the message part. In story mode, which `scripts/visual.ts` loads, the `Error` export therefore always renders "Loading" and never the error status. This breaks the contract's Stories rules that a play test ends in the resting state and that each variant's story pairs with its export for the visual check. The spec's `Error` row (`docs/patterns/data-state-panel.md:129`) asks for this test, so the fix is in both: keep `Error` static and move the retry and CR-6 test to a story of its own.
- **P2-2.** `packages/perron/src/locale/en.ts:10` `loading`'s JSDoc still says only "Announced while content loads.", but DataStatePanel now shows it as a visible title. The new `noData` and `loadFailed` JSDocs (lines 12 and 14) describe the situation, not where the string is seen or heard, as the content-audit reads each key's JSDoc to say. Better: "The title of a data view's message while its data loads; announced" and the like.

## P3

- **P3-1.** `docs/patterns/data-state-panel.md:114` CR-6 also applies when `status` becomes `'ready'`. When a status change removes the focused action, focus lands on the empty, zero-height message part, which draws its 2 px focus ring as a thin bar above the data view (seen on the Empty story after setting `'ready'`). Question for the maintainer: should a change to `'ready'` focus the empty region, or should focus go to the start of `children` or stay with the caller?
- **P3-2.** `docs/patterns/data-state-panel.md:75` The ARIA table says the region announces "the empty or error title with the sentence". But EmptyState renders the action inside the `role="status"` region, so its label ("Clear filters", "Try again") is announced too, and a control sits inside a live region. Options: accept this and say so in the spec, or render the action outside the message part, which means splitting it from EmptyState.
- **P3-3.** `docs/patterns/data-state-panel.md:41` The stories are named by `status` "as `penpot/README.md` names variants", so `status` works as this pattern's Penpot variant property. The contract's Props table makes the Penpot variant property `variant`, with `data-variant` on the root. ReportStrip, VehicleTable and DayProfileChart (all still designing) will copy this, so the maintainer should decide now: either `status` with `data-status` stays as a second, allowed name for a variant property, or the contract names the case.
- **P3-4.** `packages/perron/src/patterns/DataStatePanel/DataStatePanel.stories.tsx:14` The stories write stations as "Buddinge st" and "Ballerup st". DetailHeader writes "Nørreport St." and EmptyState's JSDoc writes "Nørrebro st", and neither `docs/content-design.md` nor `docs/glossary.md` says which spelling is right. Content design should pick one form for station names.
