# Review: DayProfileChart, round 1

## P1

- **P1-1.** `packages/perron/src/patterns/DayProfileChart/DayProfileChart.tsx:239` If the plot does not have focus, Escape cannot close the tip that hovering shows. `onPointer` shows the tip on hover, but the only Escape handler is the plot's `onKeyDown` (line 266), so it runs only while the plot has focus. In `patterns-dayprofilechart--default`, hovering the plot with focus on `<body>` and pressing Escape leaves the tip showing. At its peak it covers the line, and at 00:00 it covers the scale. This breaks `docs/foundations/accessibility.md:71` ("A hover card ... closes with Esc", WCAG 1.4.13 Dismissible). Two spec lines need to change with the code: CR-7 (`docs/patterns/day-profile-chart.md:226`) and the Escape row of the Keyboard table (line 180), which limits Escape to a focused plot.

## P2

- **P2-1.** `docs/patterns/day-profile-chart.md:227` CR-8 puts the tip along the plot's top edge, at `top: 0` (`DayProfileChart.css:109`), so it covers what it describes. In `patterns-dayprofilechart--keyboard` at 08:00, in light and dark, the tip spans x 109–205 and y 40–67 and hides the 1 260 peak at y ≈ 60 under its own guide. At 00:00 (Home) and 03:00 (`unknown-hours`) it covers the scale's "1 500". This is a design-qa Polish finding. Placing the tip beside the guide rather than across it would keep the point visible, for example starting a gap after the guide and flipping to its left side past the middle.
- **P2-2.** `packages/perron/src/patterns/DayProfileChart/DayProfileChart.tsx:376` CR-8 places each tick with `translateX(-p%)`, so the labels at 25 % and 75 % are not centred on their times. In `default`, "06:00" is centred at x 118 where 06:00 is at x 110, and "18:00" at x 290 where 18:00 is at x 298. That is about 34 minutes off on a time axis with no tick marks. This breaks design-qa's Alignment line. The fix is to centre the inner ticks (`translateX(-50%)`) and keep only 00:00 and 24:00 flush with the edges, rewriting CR-8 (`docs/patterns/day-profile-chart.md:227`) to say so.
- **P2-3.** `docs/patterns/day-profile-chart.md:183` This prose still says the pointer leaving clears the highlight unless the plot has focus, "so a tap keeps the tip". CR-7 (line 226) and the code (`DayProfileChart.tsx:245`) instead keep a touch's highlight on `pointerleave` whether or not the plot has focus. The CR-7 fix did not reach this line, and CR-7 holds.
- **P2-4.** `docs/patterns/day-profile-chart.md:238` The Stories row for `Default` says its play checks that "The figure is named 'Vehicles in service'". The play (`DayProfileChart.stories.tsx:115-120`) instead checks that the figcaption is the figure's first child and holds the label. The row needs to say what the play actually checks, as the build note on the testing library's name computation explains.

## P3

- **P3-1.** `docs/patterns/day-profile-chart.md:223` CR-4 draws a lone known count as a dot made by the line's round cap, and its area has no width. In `unknown-hours` (12:00), in both themes, that dot is 2 px and hard to see next to the broken line. The question for the maintainer is whether a marker size token should give a lone count a visible mark.
- **P3-2.** `docs/patterns/day-profile-chart.md:225` CR-6 points the plot's `role="group"` at a `listitem` through `aria-activedescendant`. Chromium's tree exposes this correctly, but this pass could not check in a real screen reader whether VoiceOver or NVDA announce active-descendant changes on a non-composite role. If they don't, the arrow keys are silent. The maintainer may want this tested in a real screen reader before `stable`.
- **P3-3.** `docs/patterns/day-profile-chart.md:221` CR-2 counts any finite number as known, so a negative count, which the `number` type accepts, plots below the baseline. Because `overflow: visible` (`DayProfileChart.css:35`), that line runs into the axis labels, and `grouped` writes a hyphen-minus. A fractional count is written with a "." in every locale. The question is whether CR-2 should treat a negative or fractional count as unknown, or clamp it.
- **P3-4.** `packages/perron/src/locale/en.ts:54` The JSDoc for the `unknown` key still names only "Stat, FactList, Count". It does not list DayProfileChart's point list, where the word is heard after a time, so translators don't see that place.
- **P3-5.** `packages/perron/src/patterns/DayProfileChart/DayProfileChart.css:38` The forced-colours block leaves the gridline at `color.border.subtle`, which computes to `rgba(235, 238, 235, 0.1)` under dark forced colours. The scale's "1 500" is therefore left with almost no visible line to mark. The Tokens table has no forced-colours row for it, such as `GrayText` as the baseline uses.
- **P3-6.** `packages/perron/src/patterns/DayProfileChart/DayProfileChart.tsx:70` `slotProps.points` (the `<ol>` part) has the same name as the `points` prop (the data), which goes against api-consistency's "One idea, one name". ReportStrip and VehicleTable will copy whichever form this sets, so the maintainer may prefer a part name such as `list`.
- **P3-7.** `docs/patterns/day-profile-chart.md:234` The Stories intro calls the 376 px container "the overview sheet's width". The Tokens row on line 107 says the plot is "115 px in the overview sheet", which assumes the sheet's padding, while every story renders a 125 px plot. One of the two lines should say which width the chart really gets inside the sheet.
- **P3-8.** `docs/foundations/semantic-colours.md:14` The foundations still keep `color.text.tertiary` for axis labels. This chart moves its axis and scale to `color.text.secondary` because axe fails tertiary on visible text (`docs/patterns/day-profile-chart.md:165`), and the next chart will hit the same failure. The maintainer should decide whether the foundations change the axis-label colour.
- **P3-9.** `docs/components/README.md:113` The contract keys `slotProps` by Base UI part, and patterns have none. This spec gives one key per HTML part, as DataStatePanel and KioskBar do, while StopTimeline has none. The contract could say which form applies to patterns, as the brief asked.
