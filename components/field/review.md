## P2

- **P2-1.** `docs/components/field.md:13` The sentence "The help is read before the box, as a hint about what to type should be, and stays where it is when an error appears" doesn't parse ("what to type should be"). That breaks the content-audit Docs rule, which asks for plain, short sentences in the house voice. Rewrite it as, for example, "as a hint about what to type".
- **P2-2.** `packages/perron/src/components/Field/Field.stories.tsx:236` The spec's What axe won't catch line (`docs/components/field.md:136`) and its `RichContent` row (`docs/components/field.md:191`) say that `label`, `description` and `error` each render a string, an element and a list alike, and that Base UI's several messages render as a list. The stories cover only some of this. `RichContent` gives the label as an element only, never as a list. It gives the description as a fragment only, and the error as an array only, never as a single element. No story has a `validate` that returns several messages, so the `ul` rows of the Tokens table (`margin` `0`, `padding-inline-start` `space.400`, `docs/components/field.md:106-107`) never render and can't be checked. This leaves the contract's checklist line "Every shape the type accepts renders, in every variant" untested. It also leaves the spec's Stories row unmet.
- **P2-3.** `packages/perron/src/components/Field/Field.stories.tsx:260` `LongWords` doesn't test CR-8 for the description or the error. At `typography.body-sm` the 47-letter compound `Hovedstadsområdetsbuslinjestoppestedsoversigten` fits on one 320 px line. The description and the error therefore wrap only at the space before it, and the compound itself never breaks. The play would still pass with `overflow-wrap: anywhere` removed from `.pn-Field-description` or `.pn-Field-error` (`Field.css:30`, `Field.css:37`). Only the label's `Stoppested…` compound breaks inside a word. Under the contract's CSS rule "Long words" and CR-8, each part's text should hold a compound longer than its line.

## P3

- **P3-1.** `packages/perron/src/components/Field/Field.tsx:125` When `error` is given together with `invalid={false}`, the error still shows in `color.text.danger`, because `match={true}` comes from `error` alone. Yet the root, the control and the error carry no `data-invalid` and no `aria-invalid`. The eye sees an error in red, while the ear hears the words only as a description, with no invalid state. CR-4 asks for exactly this behaviour. The prose at `docs/components/field.md:43` says "a caller's `invalid={false}` still wins" without saying that the message stays on show. Question for the maintainer: keep this, or give `match={invalid !== false}` so the two agree.
- **P3-2.** `packages/perron/src/components/Field/Field.stories.tsx:181` The build's Direction note asks whether to keep turning off axe's `label-title-only` story by story. The comment's reason is off. axe's `title-only` check counts only visible label text and fails when `aria-describedby` is present. A hidden label alone doesn't trip it: SearchField's `HiddenLabel` has no description, and its input has no `aria-describedby`. Every hidden-label field that has help will trip this rule. Settling it once in `.storybook/preview.ts`, or with a reworded per-story reason, is the maintainer's choice.
- **P3-3.** `packages/perron/src/components/Field/Field.stories.tsx:101` The build's Direction note asks about turning off `color-contrast` for the `Disabled` story. axe flags only the description's `color.text.tertiary` (4:1). The override also turns the rule off for the label, the optional mark and the error in that story, and TextField, Select and the other dependents will need the same exception. Options: settle one rule for disabled fields, or keep a disabled description in `color.text.secondary`.
