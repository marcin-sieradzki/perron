## P2

- **P2-1.** `docs/patterns/detail-panel.md:156` CR-5 makes the pattern's CSS use two classes in one selector, `.pn-Sheet.pn-DetailPanel[data-anchor='right']` and `.pn-DetailHeader-action.pn-DetailPanel-action` (shipped at `packages/perron/src/patterns/DetailPanel/DetailPanel.css:7` and `:22`). The contract's Styling section says a selector is "one class, then attributes". These are the only two-class selectors in the library's CSS, and no gate catches them. The contract holds over the CR, so the build should rewrite CR-5 and the CSS to follow it. For the width, `.pn-DetailPanel[data-anchor='right'][data-variant]` works, because CR-5 always sets `data-variant`. For the action, the panel can give that part an attribute of its own through the `slotProps.header.slotProps.action` it already merges, and select `.pn-DetailPanel-action[...]`. The other way out is for the maintainer to change the contract so a pattern may combine its class with the class of a part it composes.

## P3

- **P3-1.** `packages/perron/src/patterns/DetailPanel/DetailPanel.tsx:9` This is still open from round 1. The `perron-allow(patterns)` reason says "the contract does not yet say whether a pattern may compose another". But the contract's Patterns section (`docs/components/README.md:270`) does list everything a pattern may import, and other patterns are not on that list. Meanwhile `dependsOn` and CR-1 name DetailHeader. No rule settles which side holds, so it needs the maintainer: either the Patterns line allows the patterns an entry's `dependsOn` names, or the reason is corrected to say this departs from that line.
- **P3-2.** `packages/perron/src/patterns/DetailPanel/DetailPanel.tsx:154` This is still open from round 1. The Sheet's title part, rendered as a `div`, passes `.pn-Sheet-title`'s `typography.heading-md` down to DetailHeader's action. In every story with an action, its computed font is 20 px weight 600, so a plain-string `action` (a shape the WithAction `play` test renders) now shows as a second heading in its own row under the subheader. Neither spec gives the action a typography role, so the maintainer may want the panel or DetailHeader to give it one.
- **P3-3.** `packages/perron/src/patterns/DetailPanel/DetailPanel.tsx:56` This is still open from round 1. The `children` JSDoc (lines 56-59) and the `anchor` JSDoc (lines 65-67) end with design reasoning copied from the spec's Props rows (`docs/patterns/detail-panel.md:57`, `:58`), and that reasoning lands in the docs page's props table. The maintainer may prefer to keep it in the spec's prose.
- **P3-4.** `packages/perron/src/patterns/DetailHeader/DetailHeader.tsx:41` DetailHeader's `action` JSDoc, and its spec's Anatomy row and Props row (`docs/patterns/detail-header.md:19`, `:50`), still place the panel's controls "at the end of the row". DetailPanel, the pattern built to use DetailHeader, moves them into a fifth grid row with `grid-row: 5`, which depends on DetailHeader's internal four-row template (`DetailHeader.css:13`). The maintainer may want DetailHeader to have an action-below layout of its own, documented on its side, instead of DetailPanel overriding DetailHeader's grid from outside.
- **P3-5.** `docs/patterns/detail-panel.md:24` The Anatomy note still ends with an instruction to the build ("The build then rewrites what still says otherwise...", citing DetailHeader's spec by line numbers 19, 50, 63, 123 and 158). That work is done, and the text ships on the `Specs/DetailPanel` page, where the line numbers will go stale. The maintainer may want it cut to the decision alone.
