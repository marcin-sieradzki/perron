# Review: AlertDialog, round 1

## P1

None.

## P2

- **P2-1.** `docs/components/alert-dialog.md:64` The `open` row, and its JSDoc at `packages/perron/src/components/AlertDialog/AlertDialog.tsx:41-45` (with `defaultOpen` at spec:65 and tsx:46-50), says "leave it out for an alert dialog its trigger opens". But the buttons in `actions` close the alert dialog only through `open` (spec:52, spec:62, CR-6, and the maintainer's answer to brief question 2). An alert dialog left uncontrolled therefore has a Cancel that does nothing: in `components-alertdialog--default`, Enter on Cancel leaves it open. Only Esc closes it, so a touch screen reader user, who has no Esc, has no way out, which is the trap CR-6 says a required `actions` prevents. CR-6 and the Props rows for `actions` hold. Rewrite the `open` and `defaultOpen` rows and their JSDoc to say that an alert dialog whose actions must close it is controlled with `open`.
- **P2-2.** `docs/components/alert-dialog.md:127` The Keyboard row says "focus never leaves while open", and line 44 says Base UI "traps focus in the popup". Base UI's behaviour contradicts both. After a mouse press on the backdrop, focus moves to `<body>`, and the next Tab lands on the last action, "Clear filters", not on Cancel. This was measured in `components-alertdialog--default`, light and dark. It also breaks the spec's copy of the checklist line "Focus moves in reading order" (spec:150). The spec lines must say what Base UI does (rubric: the spec against Base UI's own source). Whether to change the behaviour is P3-1.
- **P2-3.** `docs/components/alert-dialog.md:164` CR-3 says "Each `slotProps` value is merged with Base UI's `mergeProps`". The code merges only `slotProps.trigger` that way (`packages/perron/src/components/AlertDialog/AlertDialog.tsx:132`). It spreads `portal`, `backdrop`, `title` and `description` as they are and sets each class after them with `withClass` (`AlertDialog.tsx:140-164`). The contract's Customising section allows that for a part the component sets nothing on but its class. The contract and the code hold: rewrite CR-3 to say which value is merged and which are spread.
- **P2-4.** `docs/components/alert-dialog.md:78` This line says Base UI's `data-open`, `data-closed`, `data-nested` and `data-nested-dialog-open` are the root's "only data attributes", and the Popup row at spec:40 lists the same four. Base UI's `AlertDialog.Popup` also sets `data-starting-style` and `data-ending-style` (`dialog/popup/DialogPopupDataAttributes.d.ts`, and `get_reference` for `AlertDialog` `Popup`). Line 118 and CR-10 (spec:171) name both of them. Lines 40 and 78 should list them too.

## P3

- **P3-1.** `docs/components/alert-dialog.md:162` After a backdrop press (P2-2), a stray Tab then Enter confirms the destructive action. The question for the maintainer: keep Base UI's behaviour and document it, or add a `CR-n` that sends focus back to Cancel. The second option would need the pointer handling that CR-1 now rules out.
- **P3-2.** `packages/perron/src/components/AlertDialog/AlertDialog.stories.tsx:42` The `Default` story, the subject story and the first one on the docs page, is uncontrolled (`defaultOpen`), as spec:186 asks, so its Cancel and Clear filters do nothing when pressed. That goes against the Do row at spec:200, "Control the alert dialog with `open`". The question for the maintainer: should AlertDialog support uncontrolled use at all (`defaultOpen`, or `trigger` alone), or should its subject story show the controlled shape that `Actions` shows?
- **P3-3.** `packages/perron/src/components/AlertDialog/AlertDialog.css:52` In `components-alertdialog--long-words`, in both themes, `overflow-wrap: anywhere` breaks the Danish compound in `typography.heading-lg` mid-word with no hyphen ("trafikinformationsovers" / "igten?"). The contract's Long words rule allows this. `hyphens: auto` with the locale's `lang` would read better, but that is a choice for the whole contract.
