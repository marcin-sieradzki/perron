# Review: SearchField, round 1

## P1

- **P1-1.** `packages/perron/src/components/SearchField/SearchField.tsx:277` The item's `mergeProps` puts SearchField's own `onClick`, which calls `onItemSelect`, first and `slotProps.item` after it. Base UI runs the rightmost handler first, so a caller's `slotProps.item.onClick` runs before `onItemSelect` and can cancel it with `event.preventBaseUIHandler()`. This breaks the contract's Customising rule that each `slotProps` value is merged with the component's own props last (the Base UI misuse: a lost slot). CR-5 (`docs/components/search-field.md:243`), the `slotProps.item` Props row (`docs/components/search-field.md:112`) and the JSDoc at `SearchField.tsx:145` all promise the reversed order. The contract holds over CR-5, so those three lines must be rewritten to say `onItemSelect` runs first, then the caller's `onClick`.

## P2

- **P2-1.** `packages/perron/src/components/SearchField/SearchField.tsx:99` The `onClose` JSDoc, and the matching Props row at `docs/components/search-field.md:93`, list the close reasons as a complete set: `'escape-key'`, `'outside-press'`, `'focus-out'`, `'item-press'`, `'input-clear'` and `'close-press'`. Base UI 1.9.0 also closes the list with reason `'none'` when Enter is pressed with no row highlighted (`node_modules/@base-ui/react/combobox/input/ComboboxInput.mjs:326`), and the Keyboard table's Enter row (`docs/components/search-field.md:190`) names no reason for that close. A caller who switches on `reason` misses this case, so the spec and the JSDoc disagree with Base UI (rubric, the spec against the code and Base UI's source).
- **P2-2.** `packages/perron/src/components/SearchField/SearchField.tsx:134` `slotProps.clear` is typed as the whole of `Autocomplete.Clear.Props`, `disabled` included. A caller can therefore disable the `CloseButton`, a part with no disabled look (spec line 37, Dialog CR-6). Dialog, the sibling that composes the same part, takes `Omit<BaseDialog.Close.Props, 'disabled'>` with the JSDoc "all but `disabled`: the close button is never disabled". The spec's `slotProps.clear` row (`docs/components/search-field.md:106`) should change with it (api-consistency: one part, one form across siblings).
- **P2-3.** `packages/perron/src/components/SearchField/SearchField.stories.tsx:109` `hoverRules` writes again what the shared `onHover` helper in `packages/perron/src/testing/stories.ts` already does: it reads what the `(hover: hover)` rules set on an element. The `outline` probe at line 94 likewise stands in for the shared `rendered` helper. This breaks the contract's Shared helpers rule that a story imports a helper from its file, not a copy under a new name.
- **P2-4.** `packages/perron/src/components/SearchField/SearchField.stories.tsx:522` The `Controlled` play ends with focus left on the input, where it started on the page. The contract's Stories rule asks every `play` to end with popups closed and focus back where it started, and so does the spec's own Stories intro (`docs/components/search-field.md:264`). The `Controlled` row (`docs/components/search-field.md:278`, "ends closed, focus on the input") contradicts both; the contract holds, so the row is rewritten and the play blurs the input at the end.

## P3

- **P3-1.** `packages/perron/src/components/SearchField/SearchField.tsx:112` `onItemSelect(event, item)` is a new event name that later list components will copy, while MUI's Autocomplete reports a chosen option through `onChange`. The contract could settle the name for choosing a row in a list that keeps no selection.
- **P3-2.** `packages/perron/src/components/SearchField/SearchField.tsx:55` `hiddenLabel` (MUI's boolean) gets past the props gate's `<key>Label` rule only through `perron-allow(props)`. The contract's Props table could name it as an exception, so the next field does not need the same allowance.
- **P3-3.** `docs/components/README.md:219` The Shared parts row now lists `Autocomplete.Clear` under `CloseButton`, but the bullet below it still says the part's label is the owned "Close" overridden by `closeLabel`; SearchField gives "Clear" through `clearLabel`. The `close` icon's `use` in `packages/perron/icons/icons.json` also still says only "Close a panel, a dialog or a highlight". The maintainer decides how the part's role is worded.
- **P3-4.** `docs/components/search-field.md:78` The default filter is Base UI's collator in the runtime's locale, and it ignores accents. In an English runtime that also treats ø as o, so typing "Nør" matches "Nordhavn St." (seen while pressing ArrowUp in the Default story), which a Danish reader would not expect. Only a PerronProvider locale reaching components, or a caller's `filter`, avoids it.
- **P3-5.** `docs/components/search-field.md:83` With `hiddenLabel`, the placeholder is the only text the eye gets to name the field, and it is drawn in `color.text.tertiary` (4.0:1 on `color.surface.raised`). `docs/foundations/accessibility.md:7` keeps tertiary for hints next to stronger text, yet the spec recommends this setup for the top bar.
- **P3-6.** `packages/perron/src/components/SearchField/SearchField.stories.tsx:394` In `WithMarks`, a LineBadge `startIcon` repeats the item's label, so the option is heard as "5C 5C Bus, Husum Torv to Lufthavnen". The spec's Do and don't could tell callers how to avoid saying the same words twice.
- **P3-7.** `packages/perron/src/components/SearchField/SearchField.tsx:237` The clear button is left out only when SearchField's own `disabled` prop is set. If a Base UI `Fieldset` around the field disables it instead, Base UI still renders the `CloseButton`, disabled but with no disabled look.
