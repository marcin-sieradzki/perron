# Review: Select, round 2

## P1

None.

## P2

- **P2-1.** `docs/components/select.md:99` The `onChange` row, and the JSDoc copied from it at `packages/perron/src/components/Select/Select.tsx:56`, name `'none'` only for letters typed on the closed box. Base UI 1.9.0 also calls `onValueChange` with `'none'` in two other cases. First, when the chosen option leaves `items`, it resets the value to `defaultValue` or `null` (`SelectPositioner.js` `onMapChange`). Second, when the browser autofills the hidden input (`SelectRoot.js`, "Handle browser autofill"). So a caller who filters `items` gets an `onChange(event, null, details)` the spec never mentions. This breaks rubric 6 (the spec against Base UI's source on which reasons an event gives), as `onClose`'s row did in round 1. The row and the JSDoc should name these cases, or end "or another of Base UI's reasons" as `onClose` now does.
- **P2-2.** `docs/components/select.md:300` CR-16 sets the docs frame to `360px`, and `packages/perron/src/components/Select/Select.stories.tsx:53` follows it, but the `Groups` list does not fit. In an 800 × 360 viewport its popup runs from 79 px to 351 px and its list scrolls, showing 270 of its 355 px, so the docs page shows the list cut short. This breaks the contract's Stories rule, which asks an overlay's meta for "a height that fits the open overlay" (its example is `480px`). The contract holds over CR-16. Round 1 raised this as P3-4; it is raised again here as a P2 because it breaks a written contract rule.
- **P2-3.** `docs/components/select.md:308` The Stories table, and so the plays, test none of four behaviours that the Keyboard table (`:237`, `:239`, `:241`) and line 71 promise. Tab in the open list closes it (`onClose`, `'focus-out'`) with focus back on the trigger. A second press of the trigger closes it (`'trigger-press'`). Letters typed in the open list move the highlight ("r" reaches "Regional train"). ArrowUp on a closed trigger with nothing chosen opens on the last option. I checked all four by hand in Storybook. This breaks the contract's Stories rule, "a `play` test for every behaviour the component promises (dismissal, focus, keyboard)". Popover's stories already test `'focus-out'`.

## P3

- **P3-1.** `packages/perron/src/components/Select/Select.stories.tsx:60` The `color-contrast` exception for `[data-placeholder]` still lives in Select's meta (CR-16, `docs/components/select.md:300`), not in `.storybook/preview.ts` as the build's question 1 recommended. Each later Field dependent that draws a text placeholder (Combobox) would repeat it, so the maintainer may want to settle where it lives.
- **P3-2.** `docs/components/select.md:241` The Tab, Shift+Tab row says Tab in the open list closes it. It does not say that Base UI then puts focus on the trigger rather than moving on, so a second Tab is needed to leave the field (seen in Storybook). The checklist's focus line (`:267`) lists choosing, Esc and a press outside as returning focus to the trigger, but leaves Tab out.
- **P3-3.** `docs/components/select.md:62` The `Select.Popup` row says Base UI "moves focus into the list on open". The checklist line `:267` says "opening moves focus to the chosen row". But line 71, which holds and matches Storybook, says that opened by a press or by `defaultOpen` with nothing chosen, focus goes to the popup and no row is highlighted. The two lines could say the same.
- **P3-4.** `docs/components/select.md:315` The `Invalid` story's error, "Choose a transport mode", repeats the placeholder shown in the box above it word for word. The eye reads it twice, and the ear hears it as both the value and the description. Content design asks an error to say "what is wrong and how to put it right", so an error that does would read better.
- **P3-5.** `packages/perron/src/components/Select/Select.tsx:86` `required` and `readOnly` have JSDoc of Select's own, while Checkbox and Switch inherit Base UI's wording for the same props. The api-consistency rule says "one prop is described the same way in every member that has it". As the build's direction note says, the Inputs family could settle on one wording.
- **P3-6.** `docs/components/select.md:111` Some JSDoc Select inherits through `FieldProps` will read oddly on Select's docs page. `error` gives the example "Enter a stop name", which is a text field's error, not a select's. `name` and `disabled` (`:112`, `:113`, Base UI's) say they take precedence over "the `<Field.Control>` component", which Select never renders. The Field dependents may want wording that fits every control.
