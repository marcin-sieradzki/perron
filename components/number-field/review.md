## P2

- **P2-1.** `docs/components/number-field.md:230` Round 5's fix for the pen press went into lines 57 and 202, which now say only "a mouse press" focuses the input. The "What axe won't catch" line still says, with no qualifier, "a press on a button leaves focus on the input". Base UI's source disagrees. `useNumberFieldStepperButton.js` calls `focusInput()` only when `isTouchLikePointerType(event.pointerType)` is false. `usePressAndHold.js:23-27` counts touch and pen as touch-like and calls `preventDefault()` on pointerdown only for a mouse. So a touch or pen press leaves focus where it was, or on the button. Line 230 should say "a mouse press" as lines 57 and 202 do. This breaks the spec-against-code rule that one line may not deny what another now says, and Base UI's source holds.
- **P2-2.** `docs/components/number-field.md:200` The Tab row says leaving "clamps it to `min` and `max`" with no exception. Base UI's source has one. `NumberFieldRoot.js` `setValue` sets `shouldClampValue = !allowOutOfRange || !isInputReason`, so a leave with `'input-blur'` does not clamp while `allowOutOfRange` is set. That contradicts line 57 ("unless `allowOutOfRange` is set"), the `allowOutOfRange` Props row at line 94, and the `OutOfRange` Stories row at line 289 ("Tab out keeps 25, unclamped"). The row should add "unless `allowOutOfRange` is set". This breaks the spec-against-code rule (a line saying what Base UI does matches Base UI's source), and Base UI's source and the `OutOfRange` row hold.
- **P2-3.** `docs/components/number-field.md:276` All seven round-5 gaps now have a `play` step, and so do every Keyboard row, every Stories `play` promise and every visible `CR-n`. One line of the test-coverage checklist is still unticked: **autofill reaches the value (line 57).** Line 57 lists this among the Base UI behaviours the component keeps. Base UI's hidden `<input type="number">` handles a browser autofill in its own `onChange` (`NumberFieldRoot.js`, reason `'none'`). No play sets the hidden input's value, through the native value setter and an `input` event, and checks that the box shows the number and `onChange` gets it. `InForm` only reads `FormData` after a button press. A Stories row and its play need that step.

## P3

- **P3-1.** `packages/perron/src/components/NumberField/NumberField.css:60` `font-variant-numeric: tabular-nums` (the Tokens row at `docs/components/number-field.md:159`, answer 6) sets the group separator a full figure wide. In both themes `LongWords` reads "100,000,000,…" spaced out, and `Danish` reads "1.500" spaced apart beside the description's proportional "5.000". Should the input keep tabular figures, which hold the digits still while a button is held, or use proportional ones?
- **P3-2.** `packages/perron/src/components/NumberField/NumberField.css:38` A mouse press on a stepper makes Base UI focus the input, and a text input always matches `:focus-visible`. So the box draws its ring after every pointer press, as measured in `components-numberfield--steppers`, light and dark: while Increase is held, the group's outline is solid 2px. TextField and SearchField do the same. Should the ring show after a pointer press?
- **P3-3.** `packages/perron/src/components/NumberField/NumberField.tsx:76` `onChangeCommitted(event, value, details)` (answer 4) is the library's first commit event, and the contract's State and events section does not name it. Slider will copy whatever NumberField sets, so the event may belong in the contract's list.
- **P3-4.** `packages/perron/src/components/NumberField/NumberField.tsx:16` `name`, `required` and `readOnly` keep Base UI's JSDoc, as the contract's Props rule asks, so they read differently from TextField's own JSDoc for the same props. For `name`, Base UI says "Identifies the field when a form is submitted." and TextField says "The name the words are submitted under in a form's `FormData`." That breaks api-consistency's "one prop, one description", and no rule says which wins.
- **P3-5.** `docs/components/number-field.md:125` The prose says `space.050` at the box's end puts a `size.control` button "1 px inside the edge". As rendered, the group is 320 × 38 px with a 1 px edge and 2 px of `padding-inline-end`, and the increment button runs from x 299 to 333 inside an edge at 335. So the button sits 2 px inside the edge at the inline end, and 1 px inside at the top and bottom.
- **P3-6.** `docs/components/number-field.md:105` The `numberFieldLabel` Props row ends with "(Owned strings)", but its JSDoc at `packages/perron/src/components/NumberField/NumberField.tsx:103` does not. Line 61 says each declared prop takes its row's description as its JSDoc, so the trailing section reference should come out of the row.
- **P3-7.** `docs/components/number-field.md:201` A form holding a NumberField and no submit button isn't submitted on `Enter`, because Base UI's hidden `<input type="number">` counts as a second field, while a lone TextField's form is submitted. The contract's Forms section does not say so. The maintainer may want it to, or to tell callers always to give such a form a submit button.
- **P3-8.** `docs/components/number-field.md:255` CR-3 says "Each inner part takes its `slotProps` value merged with Base UI's `mergeProps`". The code spreads `slotProps.group` (`packages/perron/src/components/NumberField/NumberField.tsx:240`) and the frame's `label`, `description` and `error` (`NumberField.tsx:214-225`) with only their class set. The contract's Customising rule allows that for a part the component sets nothing on but its class, so the code holds. CR-3 should say that the input and the two buttons are merged while the class-only parts are spread.
- **P3-9.** `docs/components/number-field.md:204` "A paste is spliced in at the caret when the result parses" hides how loosely Base UI parses: `parseNumber` ends in `parseFloat`. Measured in Storybook with the box holding 18: pasting "two" after the 1 leaves "1two8" in the box and 1 in the hidden input, until leaving rewrites it as "1". This is the build's direction note. Should the spec say so, or should NumberField refuse such a paste, which CR-1's "rebuilds none of it" would have to allow?
- **P3-10.** `docs/components/number-field.md:84` The `onChange` row, and its JSDoc at `NumberField.tsx:60`, list the reasons it is called with as if the list were complete. They leave out `'none'`, which Base UI gives when the browser autofills the hidden input, as line 57 says it can. A caller who switches on `details.reason` would miss it.
- **P3-11.** `packages/perron/src/components/NumberField/NumberField.css:29` A read-only box takes the family's hover layer, because the rule excludes only `[data-disabled]`, as the Tokens row at `docs/components/number-field.md:149` asks. The contract's Pointer feedback says neither hover nor pressed applies to a read-only part, and it counts a text box among the parts it covers ("`text` on a text box"). TextField and SearchField hover the same way when read-only. Does a read-only field's box keep the Fields hover, or drop it on `[data-readonly]` across the family?
