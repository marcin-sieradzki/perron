## P2

- **P2-1.** `docs/components/number-field.md:175` This round's edit put the group's pointer-feedback allowance into the `decrement` hover row as well as the group's (line 148). The row now reads "not on `[data-disabled]`; no pressed look and no pointer (`perron-allow(pointer-feedback)`), since a press focuses the input, whose ring and text cursor answer it or `[data-readonly]`". That row contradicts the `decrement` rows for `cursor: pointer` (line 174) and for the pressed look on `:active` (line 177). It also contradicts the CSS at `NumberField.css:96` and `:108`, and CR-15, and it garbles the `[data-readonly]` exclusion. Through the `increment` hover row at line 181, it says the same of the increment button. The Tokens table must agree with the code and with CR-15, which hold, so the row should go back to "not on `[data-disabled]` or `[data-readonly]`".
- **P2-2.** `docs/components/number-field.md:125` The new prose says "a press anywhere in the box but on a button focuses it". The Tokens row at line 154 and the comment at `NumberField.css:50` say the same. As rendered, that is still not so. I measured `components-numberfield--hover` in light and dark at the points listed. Four places are still the group's: the `space.050` (2 px) strip between the input and the decrement button (x 262), the same strip between the two buttons (x 298), the end padding (x 334.5), and the 1 px above and below each button. Each takes the group's `auto` cursor, and a mouse press there leaves `document.activeElement` on `body`. Round 7's P2-1 named these gaps round the buttons, and they are the part of it still unfixed. The contract's Pointer feedback allows the box's allowance only for a box "which a press focuses". So either the input takes the strip before the buttons (move that gap into the input's `padding-inline-end`) and the spec says exactly which strips stay dead, or the strips go. Either way, line 125, line 154 and the CSS comment must stop claiming more than the code does.

## P3

- **P3-1.** `packages/perron/src/components/NumberField/NumberField.css:64` `font-variant-numeric: tabular-nums` (Tokens row `docs/components/number-field.md:160`, answer 6) sets the group separator and the decimal point a full figure wide. `LongWords` and `Danish` read spaced out next to the description's proportional figures. Should the input keep tabular figures, or use proportional ones?
- **P3-2.** `packages/perron/src/components/NumberField/NumberField.css:38` A mouse press on a stepper makes Base UI focus the input, and a text input always matches `:focus-visible`. So the box draws its ring after every pointer press, as TextField and SearchField do. Should the ring show after a pointer press?
- **P3-3.** `packages/perron/src/components/NumberField/NumberField.tsx:77` The contract's State and events section still does not name `onChangeCommitted(event, value, details)` (answer 4), the library's first commit event. Slider will copy whatever NumberField sets.
- **P3-4.** `packages/perron/src/components/NumberField/NumberField.tsx:16` `name`, `required` and `readOnly` keep Base UI's JSDoc, as the contract's Props rule asks. So they read differently from TextField's own JSDoc for the same props, against api-consistency's "one prop, one description", and no rule says which wins.
- **P3-5.** `docs/components/number-field.md:125` The prose says `space.050` at the box's end puts a `size.control` button "1 px inside the edge". As rendered, the button sits 3 px inside the edge at the inline end (inc right 333, group right 336, minus the 1 px border), and 1 px inside at the top and bottom.
- **P3-6.** `docs/components/number-field.md:105` The `numberFieldLabel` row ends with "(Owned strings)", and its JSDoc at `packages/perron/src/components/NumberField/NumberField.tsx:104` does not. Line 61 makes each declared prop's row its JSDoc, so the section reference should come out of the row.
- **P3-7.** `docs/components/number-field.md:202` Enter doesn't submit a form that holds a NumberField and no submit button, because Base UI's hidden `<input type="number">` is a second field. A lone TextField's form is submitted. The contract's Forms line (`docs/components/README.md:99`) does not say so.
- **P3-8.** `docs/components/number-field.md:256` CR-3 says each inner part's `slotProps` value is merged with `mergeProps`. The code spreads `slotProps.group` (`NumberField.tsx:241`) and the frame's `label`, `description` and `error` (`NumberField.tsx:215-226`), setting only their class. The contract's Customising rule allows that, so the code holds and CR-3 should say so.
- **P3-9.** `docs/components/number-field.md:205` "A paste is spliced in at the caret when the result parses" hides that Base UI parses with `parseFloat`: pasting "two" after the 1 in "18" leaves "1two8" in the box and the value 1. Should the spec say so, or should NumberField refuse such a paste, which CR-1 would then have to allow?
- **P3-10.** `docs/components/number-field.md:311` The Do row tells callers to save on `onChangeCommitted`. The `InForm` row (line 298) proves that a browser autofill calls `onChange` with `'none'` and never calls `onChangeCommitted`. A caller who follows the row loses an autofilled number the person never touches.
- **P3-11.** `packages/perron/src/components/NumberField/NumberField.css:29` A read-only box still takes the Fields hover layer, since the rule excludes only `[data-disabled]`, as the Tokens row at `docs/components/number-field.md:148` asks. The contract's Pointer feedback says neither hover nor pressed applies to a read-only part. TextField and SearchField hover the same way when read-only. Does the family drop the hover on `[data-readonly]`?
