## P2

- **P2-1.** `docs/components/number-field.md:57` The "Base UI already does" line says Base UI focuses the input "on a mouse or pen press", and the Keyboard row at line 202 says the same ("a mouse or pen press focuses the input"). Base UI's own source says otherwise: `useNumberFieldStepperButton.js:146` calls `focusInput()` only when `isTouchLikePointerType(event.pointerType)` is false, and `internals/usePressAndHold.js:26` counts `'pen'` as touch-like, "to avoid forcing the software keyboard on stylus taps". So a pen press leaves focus where it was. Both lines should say "a mouse press". This breaks the spec-against-code rule that a line saying what Base UI does matches Base UI's source, and Base UI's source holds.
- **P2-2.** `docs/components/number-field.md:276` Every round-4 gap now has a `play` step. These lines of the test-coverage checklist (one line per Keyboard row, per `play` promise and per Base UI behaviour the spec says the component keeps) still have no `play` step proving them, so a regression in any of them would still pass `npm run test:stories`. Each needs a `play` step in a Stories row and in the stories:
  - (1) **A plus sign (line 57).** No play types "+", and none shows that a second sign is refused ("one of each"). Only the second decimal point is tried, in `Keyboard`.
  - (2) **The symbols a `format` renders (line 57).** No play types a unit or a percent sign. `Units` only steps with `ArrowUp`.
  - (3) **A minus sign with `min` below zero or with `allowOutOfRange` (line 57).** Only the no-`min` case is typed, in `Keyboard`, and `OutOfRange` types "0", never "-".
  - (4) **A paste that doesn't parse (line 204).** It is not spliced in. `Typing` pastes only "1", which parses.
  - (5) **Leaving after a change to `value` while the input had focus (line 200).** It calls `onChangeCommitted` (`hasPendingCommitRef` in `NumberFieldInput.js:140`). No play changes `value` from outside while the input has focus.
  - (6) **Leaving when `format` rounds a value set from outside (lines 84 and 200).** Leaving writes the rounded number and calls `onChange` and `onChangeCommitted` with `'input-blur'`. `Typing`'s rounding case is the after-typing branch, where the rounded number arrives as `'input-change'`, so the `'input-blur'` rounding path is never driven (for example, a controlled 2.6 with `maximumFractionDigits: 0`, focused and left).
  - (7) **The input's `required` (ARIA table, line 210).** It is announced, but `Validation` never reads it on the input, for example with `toBeRequired()`.

## P3

- **P3-1.** `packages/perron/src/components/NumberField/NumberField.css:60` `font-variant-numeric: tabular-nums` (the Tokens row at `docs/components/number-field.md:159`, answer 6) makes the group separator a full figure wide: in both themes `LongWords` reads "100 ,000 ,000 …" and `Danish` reads "1 . 500" beside the description's proportional "5.000". Should the input keep tabular figures, which hold the digits still while a button is held, or use proportional ones?
- **P3-2.** `packages/perron/src/components/NumberField/NumberField.css:38` A mouse press on a stepper makes Base UI focus the input, and a text input always matches `:focus-visible`, so the box draws its focus ring after every pointer press. Measured in `components-numberfield--steppers`, light and dark: while Increase is held, the active element is `pn-NumberField-input` and the group's outline is solid 2px. TextField and SearchField do the same. Should the ring show after a pointer press?
- **P3-3.** `packages/perron/src/components/NumberField/NumberField.tsx:76` `onChangeCommitted(event, value, details)` (answer 4) is the library's first commit event, and the contract's State and events section does not name it. Slider will copy whatever NumberField sets, so the event may belong in the contract's list.
- **P3-4.** `packages/perron/src/components/NumberField/NumberField.tsx:16` `name`, `required` and `readOnly` keep Base UI's JSDoc, as the contract's Props rule asks, so they read differently from TextField's own JSDoc for the same props. For `name`, Base UI says "Identifies the field when a form is submitted." and TextField says "The name the words are submitted under in a form's `FormData`." That breaks api-consistency's "one prop, one description", and no rule says which wins.
- **P3-5.** `docs/components/number-field.md:125` The prose says `space.050` at the box's end puts a `size.control` button "1 px inside the edge". As rendered, the box is 38 px with a 1 px edge and 2 px of `padding-inline-end`, so the increment button sits 2 px inside the edge at the inline end and 1 px inside at the top and bottom. The sentence should say so.
- **P3-6.** `docs/components/number-field.md:105` The `numberFieldLabel` Props row ends with "(Owned strings)", but its JSDoc at `packages/perron/src/components/NumberField/NumberField.tsx:103` does not. Line 61 says each declared prop takes its row's description as its JSDoc, so the trailing section reference should come out of the row.
- **P3-7.** `docs/components/number-field.md:201` A form holding a NumberField and no submit button isn't submitted on `Enter`, because Base UI's hidden `<input type="number">` is a second field, while a lone TextField's form is. The contract's Forms section does not say so, and the maintainer may want it to, or to tell callers always to give such a form a submit button.
- **P3-8.** `docs/components/number-field.md:255` CR-3 says "Each inner part takes its `slotProps` value merged with Base UI's `mergeProps`". The code spreads `slotProps.group` (`packages/perron/src/components/NumberField/NumberField.tsx:240`) and the frame's `label`, `description` and `error` (`NumberField.tsx:214-225`) with only their class set. The contract's Customising rule allows that for a part the component sets nothing on but its class, so the code holds, and CR-3 should say that the input and the two buttons are merged while the class-only parts are spread.
