# Review: NumberField, round 7

## P1

None.

## P2

- **P2-1.** `packages/perron/src/components/NumberField/NumberField.css:29` This round adds an allowance that excuses the box from the pressed look and the pointer, on the grounds that "a text box takes the focus ring and the text cursor on press". That premise does not hold for NumberField's group. The group is 38 px tall and the input inside it 21 px. The group's 8 px strips above and below the input, its `space.300` start padding and the gaps round the buttons all show the `auto` arrow, measured in `components-numberfield--hover`: the group's computed cursor is `auto` and the input's is `text`. Base UI's `NumberField.Group` has no press handler, unlike the Combobox `InputGroup` behind SearchField's box, which also sets `cursor: text`. So a mouse press in that padding focuses nothing: `document.activeElement` stays `body`, under a box whose hover layer invited the press. The contract's Pointer feedback allows the allowance only for "a box of the Fields family, which a press focuses, so the focus ring and the text cursor answer it", and it asks for `text` on a text box. The box must meet that premise before the allowance can hold. One way is to let the input fill the group: stretch it to the group's height and move the start padding onto it. That stays within CR-1, which adds no pointer handler.

## P3

- **P3-1.** `packages/perron/src/components/NumberField/NumberField.css:61` `font-variant-numeric: tabular-nums` (Tokens row `docs/components/number-field.md:159`, answer 6) sets the group separator and the decimal point a full figure wide. `LongWords` and `Danish` read spaced out next to the description's proportional figures. Should the input keep tabular figures, which hold the digits still while a button is held, or use proportional ones?
- **P3-2.** `packages/perron/src/components/NumberField/NumberField.css:39` A mouse press on a stepper makes Base UI focus the input, and a text input always matches `:focus-visible`. So the box draws its ring after every pointer press, as TextField and SearchField do. Should the ring show after a pointer press?
- **P3-3.** `packages/perron/src/components/NumberField/NumberField.tsx:77` `onChangeCommitted(event, value, details)` (answer 4) is the library's first commit event, and the contract's State and events section still does not name it. Slider will copy whatever NumberField sets.
- **P3-4.** `packages/perron/src/components/NumberField/NumberField.tsx:16` `name`, `required` and `readOnly` keep Base UI's JSDoc, as the contract's Props rule asks, so they read differently from TextField's own JSDoc for the same props. That breaks api-consistency's "one prop, one description", and no rule says which wins.
- **P3-5.** `docs/components/number-field.md:125` The prose says `space.050` at the box's end puts a `size.control` button "1 px inside the edge". As rendered, the button sits 2 px inside the edge at the inline end, and 1 px inside at the top and bottom.
- **P3-6.** `docs/components/number-field.md:105` The `numberFieldLabel` row ends with "(Owned strings)", which its JSDoc at `packages/perron/src/components/NumberField/NumberField.tsx:104` does not. Line 61 makes each declared prop's row its JSDoc, so the section reference should come out of the row.
- **P3-7.** `docs/components/number-field.md:201` Enter doesn't submit a form that holds a NumberField and no submit button, because Base UI's hidden `<input type="number">` is a second field. A lone TextField's form is submitted. The contract's Forms line (`docs/components/README.md:99`) does not say so.
- **P3-8.** `docs/components/number-field.md:255` CR-3 says each inner part's `slotProps` value is merged with `mergeProps`. The code spreads `slotProps.group` (`NumberField.tsx:241`) and the frame's `label`, `description` and `error` (`NumberField.tsx:215-226`), setting only their class. The contract's Customising rule allows that for a part the component sets nothing on but its class, so the code holds and CR-3 should say so.
- **P3-9.** `docs/components/number-field.md:204` "A paste is spliced in at the caret when the result parses" hides that Base UI parses with `parseFloat`: pasting "two" after the 1 in "18" leaves "1two8" in the box and the value 1. Should the spec say so, or should NumberField refuse such a paste, which CR-1 would then have to allow?
- **P3-10.** `docs/components/number-field.md:310` The Do row tells callers to save on `onChangeCommitted`. The `InForm` row (line 297) now proves that a browser autofill calls `onChange` with the reason `'none'` and never `onChangeCommitted`. A caller who follows the Do row loses an autofilled number the person never touches. The row could say so, or point such callers at `onChange`'s `'none'`.
- **P3-11.** `packages/perron/src/components/NumberField/NumberField.css:30` A read-only box still takes the Fields hover layer, since the rule excludes only `[data-disabled]`, as the Tokens row at `docs/components/number-field.md:149` asks. The contract's Pointer feedback says neither hover nor pressed applies to a read-only part. TextField and SearchField hover the same way when read-only. Does the family drop the hover on `[data-readonly]`?
