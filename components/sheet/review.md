# Review: Sheet, round 1

## P1

- **P1-1.** `packages/perron/src/components/Sheet/Sheet.css:76` At the peek snap point, the bottom sheet's body below the fold can only be reached by dragging the sheet up. The popup is translated by `--drawer-snap-point-offset` without the matching `padding-bottom: max(0px, calc(var(--drawer-snap-point-offset) + var(--drawer-swipe-movement-y)))` from Base UI's snap-point recipe. So in the `Bottom` story `.pn-Sheet-content` measures 322px with `scrollHeight` equal to `clientHeight`, and its lower part sits off-screen below the viewport. Tab, the arrow keys, PageDown, End, Space and the mouse wheel all leave `scrollTop` at 0 and the sheet at its peek. This breaks the accessibility foundation's "Every action is reachable" (`docs/foundations/accessibility.md`, What a person checks: Keyboard) and WCAG 2.2 AA 2.1.1 and 2.5.7, the target the foundation sets. It also falsifies the spec's checklist line at `docs/components/sheet.md:143`, which counts the close button and Esc as the keyboard equivalent of the grab and snap, though neither expands the sheet.

## P2

- **P2-1.** `packages/perron/src/components/Sheet/Sheet.tsx:243` `Drawer.Content` gets `tabIndex: 0` and its own inset focus ring (`Sheet.css:149-159`), but the spec doesn't define either. The Base UI parts table says Perron sets only `className` and `children` on it, the Keyboard table has no stop for the body, and the Tokens table has no `content` focus row. So every sheet gets an extra Tab stop with no role or name, and a ring around the whole body even when nothing scrolls (`Left`, `Right`, `Modal`). The `{ tabIndex: 0 }` is also merged before `slotProps.content`, against CR-2's "the component's own props last". Either put the focusable scroll region into the spec (Keyboard, Tokens and Base UI parts tables), or drop it.
- **P2-2.** `packages/perron/src/components/Sheet/Sheet.stories.tsx:19` The stories' body is bare `<p>` elements with the browser's 14px (1em) margins. In every story and theme, the first line of text sits 26px below the header instead of the `space.300` the Tokens table and the geometry note (`docs/components/sheet.md:117`) give, and 26px matches no space token (design-qa Spacing). Either trim the first and last child's block margins in `.pn-Sheet-content`, or give the stories' paragraphs a token margin.
- **P2-3.** `packages/perron/src/components/Sheet/Sheet.tsx:96` The `snapPoints` JSDoc ends by describing `onSnapPointChange`'s arguments, which belong in that prop's own JSDoc at line 108. A reader of `snapPoints` gets a stray sentence, and a reader of `onSnapPointChange` misses its shape (content-audit: docs read plainly, one idea per place; the same sentence sits in the spec's Props row at `docs/components/sheet.md:58`).

## P3

- **P3-1.** `packages/perron/src/components/Sheet/Sheet.tsx:46` The spec says it decides the variant property, but names it `anchor` and puts `data-anchor` on the root. The contract's Props and Styling sections give the Penpot variant property the name `variant` and the attribute `data-variant`. Should a placement axis like this keep MUI's `anchor` (Drawer's name) as the family's form for Dialog and the other Panels to follow, or become `variant`?
- **P3-2.** `packages/perron/src/components/Sheet/Sheet.css:68` Every side sheet is `size.sheet-width` (376px), including `anchor` `right`, which the `anchor` JSDoc calls the detail panel. `docs/foundations/layout.md` gives the detail panel `size.detail-width` (364px). Should the right sheet read `size.detail-width`, or should the DetailPanel pattern override the width through `className`?
- **P3-3.** `docs/components/sheet.md:11` The Anatomy has no grab handle, so a bottom sheet at its peek gives no visible sign that it can be pulled up. Once P1-1 is fixed this matters for discoverability only; should the later design run add a handle part?
- **P3-4.** `packages/perron/src/components/Sheet/Sheet.css:62` `.pn-Sheet:focus-visible { outline: none; }` removes the outline from the popup, which holds focus when the sheet opens through `defaultOpen`, as in `Left`. The popup isn't a control, but `docs/foundations/accessibility.md` says "Never remove an outline without drawing the ring another way". Keep it as Base UI's demos do, or let the popup show the ring?
- **P3-5.** `packages/perron/src/components/Sheet/Sheet.css:124` The comment says a longer title "wraps below" the close button. In the render, a wrapped title stays in its own column beside the button (checked at 320px with a four-line Danish title), so the comment describes layout the CSS doesn't produce.
