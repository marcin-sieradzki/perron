## P2

- **P2-1.** `packages/perron/src/components/Sheet/Sheet.stories.tsx:183` `BottomExpanded`'s `play` leaves the sheet open when it ends: it scrolls the body, puts `scrollTop` back to 0 and stops, with no Esc and no check of where focus goes. Every other story closes its sheet. This breaks the contract's Stories rule that a `play` test ends "in the resting state: popups closed and focus back where it started". The spec's Stories row for `BottomExpanded` (`docs/components/sheet.md:191`) leaves the close out too, so both need it.
- **P2-2.** `packages/perron/src/components/Sheet/Sheet.tsx:60` The `trigger` JSDoc ends by listing Base UI Root props that Perron doesn't expose: `handle`, `triggerId`, `defaultTriggerId`, `actionsRef`, `onOpenChangeComplete` and `snapToSequentialPoints`. Three other comments carry build reasoning in the same way. `anchor` (line 43) explains its name ("Named `anchor`, MUI Drawer's name; `top` is left out until a screen needs it"). `snapPoints` (lines 95-96) and the `@default` of `defaultSnapPoints` say how the peek is read ("from its custom property `--perron-size-sheet-peek` with `getComputedStyle`"). So someone reading one prop gets reasons that belong to the spec's Base UI parts table (`docs/components/sheet.md:31`) and CR-9, which already state them. This breaks content-audit's "one idea per place", the same rule as round 1's P2-3. The matching Props rows at `docs/components/sheet.md:49`, `:52` and `:58` change with it.

## P3

- **P3-1.** `packages/perron/src/components/Sheet/Sheet.tsx:47` Still open from round 1. The spec says it decides the variant property, but it names it `anchor` and puts `data-anchor` on the root and viewport. The contract's Props and Styling sections name the Penpot variant property `variant`, with `data-variant`. Should a placement axis keep MUI Drawer's `anchor` as the form Dialog and later Panels copy, or become `variant`?
- **P3-2.** `packages/perron/src/components/Sheet/Sheet.css:68` Still open from round 1. Every side sheet is `size.sheet-width` (376px), including `anchor` `right`, which the `anchor` JSDoc calls the detail panel. `docs/foundations/layout.md` and the token's description give the detail panel `size.detail-width` (364px). Should the right sheet read `size.detail-width`, or should the DetailPanel pattern set its own width through `className`?
- **P3-3.** `docs/components/sheet.md:11` Still open from round 1. The Anatomy has no grab handle, so a bottom sheet at its peek gives no sign that it can be pulled up. Its body now scrolls and takes focus at the peek, so this is about discoverability only. Should the later design run add a handle part?
- **P3-4.** `packages/perron/src/components/Sheet/Sheet.css:62` `.pn-Sheet:focus-visible { outline: none; }` hides focus on the popup. Opening a sheet from the keyboard lands focus there: in `components-sheet--right`, Enter on "Show stop" leaves `document.activeElement` on `.pn-Sheet`, not on the close button. So a keyboard user sees no ring until the next Tab. The popup isn't a control, but `docs/foundations/accessibility.md` says "Never remove an outline without drawing the ring another way". Should the sheet keep it hidden, as Base UI's demos do, show a ring on the popup, or pass `initialFocus` so the close button gets focus?
- **P3-5.** `.storybook/preview.ts:41` The branch is behind `main`, which has since merged StationIcon. `git merge-tree HEAD main` conflicts in `.storybook/preview.ts`, `packages/perron/data/docs.json`, `packages/perron/src/index.ts`, `scripts/lib/pages.ts` and `scripts/lib/site.test.ts`: each is a registry-written block or the specs grouping. Rebase onto `main` and run `npm run registry` again before the PR, so the barrels and sort order hold both entries.
