## P2

- **P2-1.** `packages/perron/src/components/Slider/Slider.tsx:69` The JSDoc for `onChange` says it is called "by a drag, a press on the track or a key" and that "`details.reason` says which". The JSDoc for `onChangeCommitted` (`Slider.tsx:79`) and the spec's copies (`docs/components/slider.md:79`, `:80`, and the "Base UI already does" line at `:56`) say the same. All of them leave out Base UI's `'input-change'` reason: `SliderThumb`'s native `onChange` calls `handleInputChange`, which also commits, when a screen reader or the browser sets the hidden range input itself. The JSDoc also never says "`event` is `details.event`", which every sibling's `onChange` says (Select, RadioGroup, Switch, Checkbox, CheckboxGroup, SegmentedControl, FilterChip, SearchField). This breaks the review rubric's line on the reasons an event gives, and the `api-consistency` rule that one prop is described the same way in every member. Name the reasons (`'keyboard'`, `'drag'`, `'track-press'`, `'input-change'`) and add "`event` is `details.event`" in the JSDoc and in the matching spec rows.
- **P2-2.** `docs/components/slider.md:192` The target-size line of the What axe won't catch checklist says the control is `size.target-min` tall "across the field's width". The Anatomy row at `slider.md:28` says "across the first column", and that is what renders. In `components-slider--default` the control is 293.6 of 320 px wide, and in `Range` it is 257.6, because the figure takes its own column after a `space.300` gap. The spec contradicts itself, and the Anatomy row holds: rewrite line 192 to say the first column.

## P3

- **P3-1.** `docs/components/slider.md:165` The Keyboard rows at 165 and 166, and the "Base UI already does" line at `slider.md:56`, say Base UI swaps the left and right arrows in right-to-left text. Base UI's `SliderThumb` reads the direction only from its own `DirectionProvider` (`useDirection()`), and PerronProvider renders none. On a page with `dir="rtl"`, ArrowRight still raises the value (5 to 6, measured). No Mylder locale is right-to-left, so only the spec's claim is wrong. The maintainer may want these lines to say they need Base UI's `DirectionProvider`, or may want PerronProvider to carry one.
- **P3-2.** `packages/perron/src/components/Slider/Slider.tsx:194` In a range, `getAriaLabel` names each thumb "Minimum" or "Maximum" alone. When `aria-label` is set, Base UI's `SliderThumb` drops `aria-labelledby`, so the field's label is no longer part of the thumb's name. Two range sliders on one screen then show in a screen reader's list of controls as two "Minimum" sliders. The answer to question 9 binds this, but the maintainer may want each thumb named by the field's label together with the owned word, for example through `aria-labelledby`.
- **P3-3.** `packages/perron/src/components/Slider/Slider.css:78` The thumb's hover and pressed layers (`color.surface.hover`, then `color.surface.selected`) render as layers of 5% and 9% alpha in light, and 6% and 9% in dark, over a disc about 14 px across inside its edge (`components-slider--default`, both themes). This meets Pointer feedback as written. The design is deferred, though, and the maintainer may want a stronger step for a part this small.
