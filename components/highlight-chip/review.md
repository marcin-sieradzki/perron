# Review: HighlightChip, round 2

## P1

- **P1-1.** `packages/perron/src/components/HighlightChip/HighlightChip.css:32` A word longer than the line does not break inside the chip, and the text spills outside the pill. The root is an `inline-flex` container, so `children` is an anonymous flex item with `min-width: auto`. `overflow-wrap: break-word` adds no break points to min-content, so that item can never be narrower than the word. Rendered at 320 px, the Selected story with "Trafikinformationsforsinkelsesoversigtenforhovedstadsomraadet" gives a chip 288 px wide (container-wide, as `max-inline-size: 100%` asks) whose content has `scrollWidth` 346 against `clientWidth` 286. The word runs out of both sides of the pill and its start is off-screen. This breaks CR-7 ("never cuts its words off… a word longer than the line breaking within it"), the Tokens row at `docs/components/highlight-chip.md:85` ("breaks within the chip"), the contract's CSS "Long words" rule and the reflow line of the accessibility foundation. The `Default` play test misses it because it narrows only "Line 5C", which wraps at its space. The test should also narrow a single long word, and the spec row and CR-7 should name whatever wrap value is chosen (for example `anywhere`, which does lower min-content).

## P3

- **P3-1.** `docs/components/highlight-chip.md:43` "The chip takes no `name`" is still untrue for the code: `HighlightChipProps` inherits the native button's `name` through `Toggle.Props`, and it reaches the `<button>`. The sentence could say the chip takes no form `name` and renders no hidden input.
- **P3-2.** `packages/perron/src/components/HighlightChip/HighlightChip.css:25` The chip writes the glass fill, `backdrop-filter` and `shadow.panel` itself. The contract's Glass line (`docs/components/README.md:206`) exempts only "a Base UI popup or panel" from composing Surface with `variant='glass'`. The maintainer may widen that line to cover any element Base UI renders, such as a Toggle, or have the chip compose Surface through `render`.
- **P3-3.** `docs/components/highlight-chip.md:58` The spec reads Base UI's `[data-pressed]` as the Selected design state, as FilterChip does, but the contract's Design states table (`docs/components/README.md:147-150`) lists `[data-pressed]` under Pressed and only `[data-selected]` and `[data-checked]` under Selected. The contract could name a Toggle's `[data-pressed]` under Selected, so the Toggle-based chips rest on a written rule.
- **P3-4.** `packages/perron/src/components/HighlightChip/HighlightChip.css:96` `forced-color-adjust: none` is inherited. In a contrast theme, a LineBadge the spec suggests putting in `children` (line 41) therefore keeps its theme line colours inside a selected chip, and the chip keeps its theme `shadow.panel`. FilterChip, by contrast, hands its inner Count back to the system with `forced-color-adjust: auto`. The maintainer may want the chip's content returned to system colours too.
- **P3-5.** `packages/perron/src/components/HighlightChip/HighlightChip.css:89` A disabled chip at rest has no forced-colours rule and relies on the browser greying a natively disabled `<button>`. A `render` with `nativeButton={false}` gets only `aria-disabled` and `data-disabled`, so it is not greyed. FilterChip and SegmentedControl both set `GrayText` explicitly on `[data-disabled]`, and the three toggles could share that form.
